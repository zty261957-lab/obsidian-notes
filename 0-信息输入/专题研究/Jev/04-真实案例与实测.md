# Jev 真实案例与实测

> [!summary] 阅读结论
> 当前最有价值的案例不是炫技 Demo，而是把 Jev 放在“动作之前的判断门”或“循环中的下一步选择器”。共同结构是：代码负责候选集、预算、停止条件和兜底；Jev 只做一次窄判断。

## 1. Agent 工具调用风险分类

- **原文**：[I Benchmarked Jev on Agent Tool-Call Risk](https://webofmike.com/jev-benchmark/)
- **代码**：[themsquared/jev-benchmark](https://github.com/themsquared/jev-benchmark)
- **来源类型**：独立实测 + 可复现代码
- **价值等级**：A
- **核心结果**：60 个手工标注样本，包含清晰、模糊和对抗三类；一次公开运行中准确率 91.7%（55/60），清晰样本 100%，模糊样本 71.4%，对抗样本 91.7%。p50 约 422ms，p95 约 542ms。作者明确说明样本量小，不能外推。
- **适用场景**：在 Agent 执行 shell、数据库、云资源或外部发送工具之前，分类为只读、破坏性、提权或数据外传。
- **争议/限制**：没有同期 frontier LLM 基线；一个高置信错误达到约 0.97，说明“高置信”也不能替代不可逆动作确认。
- **企业启发**：风险门应输出分类 + 概率 + 规则命中；删除、提权、外传等动作无论模型多自信都进入人工确认或确定性策略。

## 2. Jev Browser：浏览器 Agent 的动作选择器

- **原文/代码**：[jkudish/jev-browser](https://github.com/jkudish/jev-browser)
- **来源类型**：独立开源案例
- **价值等级**：A-
- **核心设计**：应用先把页面转换为可点击、可输入、可选择的候选元素；Jev 每一步只选择一个动作，并评估“目标是否完成”“是否卡住”。代码掌握循环、预算、恢复和停止门。
- **公开案例**：项目称可在约 4 秒、约 0.0016 美元下从 Wikipedia 的 Coffee 页面导航到 Espresso，也演示了填表但不提交、读取价格和导出页面内容。
- **适用场景**：内部系统导航、重复性网页操作、测试辅助和受控信息采集。
- **争议/限制**：项目明确处于早期阶段；公开成功样例不代表复杂站点、登录、弹窗、动态页面和反爬环境下稳定。
- **企业启发**：浏览器 Agent 不应把整页和无限动作交给模型。先由代码剪枝候选元素，限制步数、域名和动作，再让模型判断。

## 3. Vercel AI Gateway：生态采用信号

- **原文**：[Jev is the fastest-adopted model in AI Gateway history](https://vercel.com/blog/ai-gateway-jev-model-launch)
- **模型页**：[Jev on Vercel AI Gateway](https://vercel.com/ai-gateway/models/jev)
- **来源类型**：平台合作方数据
- **价值等级**：B
- **核心结果**：Vercel 称 Jev 上线 24 小时内被接近 13% 的付费团队使用，首日采用速度超过其近期模型发布。
- **适用场景**：判断生态热度、SDK/Gateway 接入便利度、开发者试用意愿。
- **争议/限制**：首日采用率不等于留存、生产规模、准确率或商业价值；Vercel 同时是分发平台，有推广利益。
- **企业启发**：平台集成能降低试点门槛，但不能替代评测。应继续跟踪 30/90 天留存、调用量和真实生产案例。

## 4. TypeSafe 官方 Cookbooks：模式样例，不是独立证明

- **原文**：[Cookbooks 索引](https://docs.typesafe.ai/llms.txt)、[LLM Guardrails](https://docs.typesafe.ai/cookbooks/llm_guardrails)、[RAG passage 分类](https://docs.typesafe.ai/cookbooks/classifying_rag_passages)、[Skill suggestion](https://docs.typesafe.ai/cookbooks/skill_suggestion)
- **来源类型**：官方示例
- **价值等级**：A（学习实现）；C（证明效果）
- **核心模式**：
  - 输入/输出护栏：一次请求并行判断 jailbreak、伤害、医疗建议、自伤等风险，再由阈值决定通过、复核或拦截。
  - RAG 过滤：判断相关性、矛盾和提示注入，再由代码决定哪些片段进入生成模型。
  - Skill 路由：Choice 用于相对排序，Noul 用于判断是否真的应该调用某个 Skill。
- **适用场景**：快速设计企业 POC 的问题结构和控制流。
- **争议/限制**：示例由厂商设计，且部分使用旧模型版本；不能把 cookbook 结果当作本企业数据上的性能保证。
- **企业启发**：复用模式，不复用阈值；把问题、阈值和版本集中管理，纳入代码审查与回归测试。

## 从案例中抽出的通用模式

### 模式 A：决策门

`输入/动作 → Jev 判断风险与置信 → 代码规则 → 自动执行 / 二次验证 / 人工确认`

### 模式 B：候选选择器

`代码生成合法候选 → Jev 排序或选择 → 代码验证合法性 → 执行一步 → 记录结果`

### 模式 C：低成本前置筛选

`全量数据 → Jev 筛选/打分 → 仅把高价值或低置信样本送给昂贵 LLM/人工`

### 模式 D：并行质量检查

`同一 state → 多个原子问题并行 → 代码聚合 → 形成风险、质量和升级决策`

## 推荐的首个企业 POC

选择一个已有人工处理历史的“工单/需求路由”场景：

1. 从历史数据抽取 300–500 条，按正常、模糊、边界、对抗、缺失信息分层。
2. 只设计 3–5 个原子问题：业务域、紧急度、信息完整性、是否需要人工、风险等级。
3. 保留 `unknown / needs_review` 出口。
4. 以当前规则或现用 LLM 为基线，比较准确率、误报/漏报、覆盖率、校准、p50/p95、失败率和成本。
5. 第一阶段只旁路观测，不自动写回；达到验收门槛后再开放低风险动作。
