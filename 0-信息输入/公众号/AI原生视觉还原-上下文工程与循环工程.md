# AI Native 视觉还原的两个支点：上下文工程与循环工程

> **一句话结论**：**"不是 Agent 不够聪明，而是图书馆管理得不够好。"**
> **两个支点：① 上下文工程（在信息到达 Agent 之前，源头数据就要被治理）② 循环工程（一次性生成 ≠ 一次性做对）**

---

## ⭐⭐ 一、问题：提示词调不动的时候，往哪看

**现象**（一份真实业务设计稿）：
- **无论怎么调整提示词，Agent 都做不对关键区域**（元素缺失、位置偏移）
- **会把不可见的图层还原出来**（被隐藏的历史版本、被蒙版遮挡的底层元素出现在页面上）
- **耗时异常漫长**（应该 10 分钟的模块，跑了 30 多分钟）

**⭐⭐ 结论**：
> **"问题的根源不在提示词，不在模型能力，而在 —— 上下文被「脏数据」填满了。"** ⚠️

---

## ⭐⭐ 二、五个结构性问题（**通用性很强**）

| # | 问题 | 说明 |
|:--:|------|------|
| **1** | **层次嵌套过深** | 一个"价格"文字被 **8 层无意义的空分组**包裹<br>**"每多一层嵌套，Agent 遍历就多一次调用、多一段上下文占用、多一层需要理解的结构关系"** |
| **2** | **Flex 布局不一致** | 容器声明了 Flex，但子节点尺寸位置与语义不一致 → **Agent 会忠实按 Flex 推断**（错得更彻底）|
| **3** | **大量隐藏图层** | 历史版本、备份副本、被隐藏的替代方案 —— **"在视觉上完全不可见，在结构化数据中却真实存在"** |
| **4** | **图层规范度问题** | 图层宽 156px，实际文字只需 100px → **多出的空间意味着什么？对齐全靠猜** |
| **5** | **属性冗余** | 父节点白色背景，子节点也一模一样 → **子节点的背景是冗余的** |

**⭐⭐ 一个绝妙的类比**：
> **"如果你和一个人沟通，他唠唠叨叨讲了一堆，但重点信息非常少，你们的沟通效率就会非常低。**
> **当脑子被塞满大量无用信息时，消化和判断就变得极其困难。"** ✅

---

## ⭐⭐⭐ 三、支点一：上下文工程 = 降噪（**最反直觉的一条**）

> **"我们之前认为，上下文工程的讨论主要集中在'信息如何分层暴露给 Agent'。
> 三个月的实践让我们看到，上下文工程还有更深的一层：**
> ### **在信息到达 Agent 之前，源头数据本身就需要被深度治理。"** ✅

### 3.1 一个月的实际投入（很有说服力）

> **"在集中攻坚上下文工程的一个月里，Tarot Pixel 仓库新增了超过 50 次提交。
> 其中绝大多数不是在增加新功能，而是在做一件听上去不那么性感但极其重要的事（降噪）。"**

**提交信息长这样**：
```
refactor: 裁剪无可视样式的节点，包括图片 fill
refactor: 彻底重写导出逻辑，删除不必要的所有属性
refactor: 优化降噪，背景色跨节点清除 + 去除完全无视觉节点
支持 flex 单 child 裁剪 + 支持背景冗余去除 + 支持无用 radius 去除
支持多文本的容器尺寸超过所有文本时，将这个容器干掉
增加伪 flex 布局的去 flex 布局能力
refactor: 大幅提升降噪效率 + 修复透明 png 被误当不透明而过度裁剪
```

### 3.2 五阶段降噪流水线

```
① 结构解析（蒙版处理、矢量形状识别、坐标归一化）
② 降噪（深度裁剪、不可见图层清除、伪 Flex 矫正、联集处理）
③ 合并缩减（视觉上属同一装饰单元的图层合并标记）
④ 冗余清洗（跨节点重复背景、被裁剪的圆角、无效描边阴影）
⑤ （原文未完整列出）
```

**⚠️ 关键提醒**：
> **"降噪不是简单的'删除无用节点'。设计稿的每个图层都可能承载着某种视觉意义，
> 误删一个就会导致还原结果出现空洞。这是一个精确度要求极高的工程问题。"**

---

## ⭐⭐ 四、支点二：循环工程（Loop Engineering）

> **"即使上下文做到了极致，模型的输出依然有不稳定的时候。**
> ### **一次性生成不等于一次性做对。真正的质量收敛，需要一种新的工程范式。"**

**⭐ 核心思想**：
> **质量不是靠"一次调好提示词"，而是靠"生成 → 验证 → 修正"的循环收敛。**

---

## ⭐⭐ 五、核心理念："不建管道，建图书馆"

> **"不替 Agent（写代码），而是让 Coding Agent 自己看懂设计稿。"**

**⭐ 图书馆的比喻（贯穿全文）**：
> **"Agent 查阅设计稿信息的过程，本质上是在一棵树上做检索 ——
> 每一次 API 调用获取一个节点的信息，然后决定是继续深入还是转向兄弟节点。"**
>
> **"这棵树的深度和复杂度直接决定了检索效率：
> 树越深，API 调用越多、上下文占用越大；
> 节点越冗余，Agent 需要过滤的噪音越多；
> 结构越混乱，Agent 推断语义的难度越大。"**

---

## 六、对我们的启示

| # | 启示 | 怎么用 |
|:--:|------|-------|
| **1** ⭐⭐⭐ | **上下文工程的隐藏一层：源头降噪** | 我们灌知识库/传材料前，先治理源数据 |
| **2** ⭐⭐ | **"提示词调不动时，问题常在上下文"** | 排查顺序：先看数据，再看 prompt |
| **3** ⭐⭐ | **一次性生成 ≠ 一次性做对** | 工作台要有"生成 → 验证 → 修正"的循环 |
| **4** ⭐⭐ | **"不是 Agent 不聪明，是图书馆没管好"** | 汇报金句 |
| **5** ⭐ | **降噪是脏活但最见效** | 一个月 50 次提交，几乎全是降噪 |
| **6** ⭐ | **误删比不删更危险** | 降噪要精确，不能暴力 |

**⭐⭐ 一条可直接用的判断**：
> **"很多'AI 效果不好'的问题，不是模型不行，是喂进去的数据本身脏。"**
