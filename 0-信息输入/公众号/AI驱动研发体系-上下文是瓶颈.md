# AI 驱动研发体系的实践和思考

> **一句话结论**：**业务 AI 研发的真正瓶颈是上下文，不是模型能力。**
> **"模型决定通用能力，上下文决定它在具体项目中能走多远。"**

---

## ⭐⭐⭐ 一、核心公式（本文最值钱）

```
Agent = Model + Harness
```

**"模型之外都是 Harness。"**

| 层 | 提供什么 | 缺什么 |
|---|---------|-------|
| **Model** | 理解、推理、规划、生成 | — |
| **Coding Agent Harness** | Agent Loop、文件操作、工具使用、环境连接 | ⚠️ **缺业务知识、流程约束、完成标准** |
| **项目 Harness** | **业务知识 + 源代码 + 项目规则 + 流程 Skill** | — |

**⭐⭐ 完整公式**：
```
业务研发 Agent = Model + Coding Agent 通用 Harness + 项目 Harness
```

**⭐ 为什么需要"项目 Harness"**：
> **"AI 驱动的研发体系需要在通用 Coding Agent 之上增加项目 Harness。"**

---

## ⭐⭐ 二、真正的瓶颈是上下文

**模型进入真实业务系统后遭遇的信息缺口**：
- 它**不知道历史上为什么这样设计**
- 不知道**某个规则只适用于哪些业务**
- 不知道**某段代码是当前链路还是已废弃的实现**

**⚠️ 靠人讲解的后果**：
> **"如果每次都靠人在对话里重新讲解，AI 的表现就会受制于当前对话长度和个人表达能力。**
> **同一个问题，换一次会话、换一个人或换一个 Agent，结果可能完全不同。"**

**⭐⭐ 结论**：
> **"业务 AI 研发的上限不只由模型决定。"**

---

## ⭐⭐⭐ 三、本地优先：Agent + 文件夹 + Git

**做法**：
```
尽可能把项目需要的所有信息放进同一个文件夹
    ↓
用 Git 管理（版本、分支、评审、来源、回滚）
    ↓
Coding Agent 天然能操作文件系统和 Git
```

**⭐ 关键取舍**：
> **"不需要建设一套复杂平台和操作界面，所有的操作都通过 Coding Agent 打开文件夹对话进行，
> 不要尝试手动修改任何一个字。"**

**⭐⭐ 但"本地优先"≠"什么都放本地"**：
| 类型 | 放哪 |
|------|------|
| **稳定上下文**（业务知识、项目规则、源代码、迭代文档）| **进 Git** |
| **动态事实**（工单状态、测试环境、日志、数据库、配置中心）| ⭐ **从权威系统实时查询** |

**⭐ 一句话**：
> **"稳定上下文进入仓库，动态事实实时查询。"** ✅

---

## 四、老系统怎么冷启动（很实用）

**新项目**可以从第一天按 AI 友好的方式组织；**老系统不行**。

**Price360-KB 的做法**：
1. **用 Git submodule 把相关代码仓库关联**到项目目录
2. 人工编写的文档资料**关联**到文档目录
3. ⭐ **设计"采访稿"，通过钉钉 AI 听记对核心开发、产品人员做采访**
4. **把采访原稿给 Coding Agent，让它整理进项目知识库** ——
   **补齐只存在人脑海中的业务知识**

**⭐⭐ 一条极重要的心态**：
> **"不要等到知识库非常完善才开始使用起来，
> 核心是在 AI 研发体系的每次需求迭代过程中去完善知识库，形成一个知识飞轮。"**

---

## ⭐⭐ 五、知识飞轮：迭代过程本身就是沉淀

> **"这条链路里，每个阶段都在为下一个阶段生产上下文。"**

```
PRD        → 补充业务定义和验收标准
技术方案    → 记录系统链路
开发和测试  → 继续校验它们
归档        → 把确认后的长期知识回流到知识库
```

**⭐ 这跟我们做 Skill/规范是同一个道理**：
> **不是先建完美知识库再干活，而是干活过程中顺手沉淀。**

---

## 六、人的重心转移

> **"产品、开发、测试同学都在这套体系里共同提出目标、约束与决策，
> 人的重心也从逐步指导操作，转向业务判断、方案选择、结果验收和高风险授权。"**

| 以前 | 现在 |
|------|------|
| 逐步指导操作 | **业务判断** |
| 写提示词 | **方案选择** |
| — | **结果验收** |
| — | **高风险授权** |

---

## ⭐⭐ 七、对我们"研发工作台"的直接启示

| # | 启示 | 怎么用 |
|:--:|------|-------|
| **1** ⭐⭐⭐ | **工作台 = 项目 Harness 的载体** | 通用 Agent 缺的那块（业务知识/流程约束/完成标准），正是工作台要提供的 |
| **2** ⭐⭐⭐ | **上下文 > 模型能力** | 汇报时说"我们不是换个更强的模型，是把项目上下文喂给它" |
| **3** ⭐⭐ | **本地优先：Agent + 文件夹 + Git** | ⚠️ **这比"做一个复杂平台"更轻、更快见效** |
| **4** ⭐⭐ | **稳定上下文进仓库，动态事实实时查** | 工作台的数据分层原则 |
| **5** ⭐ | **采访式补知识** | 用 AI 听记采访业务专家 → 让 Agent 整理进知识库 |
| **6** ⭐ | **不要等知识库完美才用** | **边用边补，形成飞轮** |

**⭐⭐ 一个可能颠覆我们方案的判断**：
> **"不需要建设一套复杂平台和操作界面，所有操作都通过 Coding Agent 打开文件夹对话进行。"**
> —— **这跟我们"做一个七大模块的工作台"是两条路** ⚠️
> **值得在方案里正面回应这个选择：为什么我们要做界面，而不是文件夹+Git？**

---

## 八、一句话

> **Agent = Model + Harness；业务研发 Agent = Model + 通用 Harness + 项目 Harness** ⭐
>
> **⭐⭐ 三个核心判断**：
> **① 瓶颈是上下文，不是模型**
> **② 本地优先：Agent + 文件夹 + Git（最轻的方案）**
> **③ 知识飞轮：迭代过程本身就是沉淀**
