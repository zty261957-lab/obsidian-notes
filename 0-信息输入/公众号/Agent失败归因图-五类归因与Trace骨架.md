# 阿里云谈 Agent 可观测性之后，测试团队还要补一张"失败归因图"

> **一句话结论**：**目标不是铺满 Trace 页面，而是把"用户说 AI 不靠谱"缩短成
> "哪个节点、哪类原因、影响什么业务、谁来修、怎样证明已修好"。**

---

## 一、开篇的问题（很典型）

**退款 Agent 任务成功率从 92% 掉到 84%**：
- 模型团队说版本没变
- 接口团队说可用率正常
- 知识库只更新了两篇文档
- **日志有几十种字段，却没人能回答：错误发生在检索、理解、工具调用，还是最终话术？**

**⭐ 结论**：**下一步不是再多打一层日志，而是让一次业务失败能沿 Trace 归因。**

---

## ⭐⭐ 二、五类归因（**结束互相甩锅**）

| 类型 | 典型表现 |
|------|---------|
| **数据问题** | 检索到**旧政策**；权限裁剪丢失 |
| **模型问题** | 忽略"**工作日**"等限定条件 |
| **工具问题** | 返回**错租户**；Schema 变化 |
| **规则问题** | **允许取消前退款** |
| **环境问题** | 网络、缓存、区域与依赖漂移 |

**⭐⭐ 最重要的一句**：
> ### **"相同的错误答案可能来自完全不同的原因。"**

**⭐ 操作建议**：
> 让客服和研发**每周抽样 50 条**，按统一标签标注；
> **争议允许多标签，但必须指出"第一处偏离预期的节点"** ✅

---

## ⭐ 三、Trace 骨架（7 个节点）

```
session → turn → retrieval → model_call → policy_decision → tool_call → final_state
```

**每个节点记录**：父 ID、版本、开始/结束时间、输入摘要、输出摘要、**错误类型**

**⭐ 业务场景还要加**：
> **订单状态、证据文档版本、工具参数来源、真实副作用**
> ⚠️ **"否则 HTTP 200 只说明接口成功，不说明退款业务成功。"**

---

## ⭐⭐ 四、字段设计的铁律

> ### **"每加一个字段，都要能支持一条断言、一个告警或一个修复。"**

**⚠️ 反面例子**：
| 记了什么 | 缺什么 | 后果 |
|---------|-------|------|
| 记录 Token | 没有 `task_type` | **无法判断贵在哪里** |
| 记录工具名 | 没有参数来源 | **无法判断越权** |
| 记录最终答案 | 没有 `evidence_id` | **无法检查引用** |

**⭐ 确定性红线检查（可用规则先跑）**：
- 退款工具调用前**必须有订单归属证据**
- **策略拒绝后不能换工具绕行**
- 最终"已退款"**必须关联交易凭据**
- **人工接管不能仍产生副作用**

---

## ⭐⭐ 五、归因与严重度必须分开

> **"归因回答为什么，严重度回答先修什么。"**

| 级别 | 定义 |
|:----:|------|
| **P0** | 资金、隐私、**不可逆动作** |
| **P1** | 让用户作出**错误决定** |
| **P2** | 可恢复的体验问题 |
| **P3** | 表达瑕疵 |

**⚠️ 关键提醒**：
> **"高频文案问题不能压过一次跨用户退款。"**

---

## ⚠️ 六、观测本身也会制造新风险（隐私）

| 风险 | 措施 |
|------|------|
| 完整保存 Prompt/订单/文档会泄露隐私 | **普通任务采样，高风险动作全量** |
| — | 正文**短期加密**保存，**结构字段长期保留** |
| — | 同一订单使用**稳定匿名 ID** |
| — | 租户隔离 + 删除期限 |
| ⚠️ | **测试还要扫描 Trace 是否出现银行卡、Token、手机号** |

---

## ⭐ 七、采样策略不能把最重要的问题丢掉

> **"只采样慢请求，会漏掉快速越权；只采样失败状态，会漏掉 HTTP 成功但业务错误。"**

**建议**：
- **高风险副作用全量保留**
- 普通任务随机采样
- **异常模式动态加采样**
- **策略本身版本化，报表注明覆盖率**（避免把样本变化误认为质量变化）

---

## ⭐ 八、怎么验证"归因标签真的有用"（很妙）

> **随机抽取已关闭事故，让另一名工程师只看 Trace 重新归因。**
> **若一致率很低，说明字段或定义不清。**

**再检查**：每类标签是否能对应**明确负责人和修复动作**。

> ⚠️ **"一个名为'Agent 异常'的万能标签，即使占比精确，也无法推动任何改进。"**

**⭐ 验证闭环**：
> 修复发布**一周后**，观察同类标签和业务后果是否下降。
> **若没有，重新审视"第一处偏差"，而不是继续堆监控。**

---

## 九、归因示例（三个相似回答，修复路径完全不同）

**用户问"退款多久到账"**：

| 样本 | Trace 显示 | 归因 | 修复 |
|:----:|-----------|------|------|
| **1** | 检索命中**旧政策**，模型忠实复述，工具正常 | **数据** | 更新索引 + 加**有效期过滤**，**不是重写 Prompt** |
| **2** | 文档正确，模型**忽略"工作日"限定** | **模型** | 改 Prompt/模型 |
| **3** | 模型参数正确，工具**返回其他租户订单** | **工具 + 权限** | 修工具/权限 |

**⭐ 教训**：
> **"若只看最终答案，会归到模型"** —— 但第一处偏差其实是数据 ⚠️

---

## 十、对我们的启示

| # | 启示 |
|:--:|------|
| **1** ⭐⭐ | **失败必须有"第一处偏离节点"**，不能只说"效果差" |
| **2** ⭐⭐ | **五类归因**可直接作为工作台的失败分类表 |
| **3** ⭐ | **字段必须支持行动**（不能记了没用） |
| **4** ⭐ | **归因 ≠ 严重度**，先修什么按 P0-P3 |
| **5** ⭐ | **验证标签有效性：换个人盲审，看一致率** |
| **6** ⚠️ | **HTTP 200 不等于业务成功** |
