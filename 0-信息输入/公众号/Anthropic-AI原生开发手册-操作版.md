# Anthropic 官方指南：AI Native 开发手册（操作版）

> **来源**：微信公众号（编译自 Anthropic《The AI-Native SDLC Playbook》，作者 Louis Claxton）｜ 约 14,700 字，保留原代码示例与配置样板
> **⭐ 与「Anthropic-AI原生SDLC-工件驱动.md」同源** —— 那篇讲框架理解，**本篇讲具体怎么落地**
> **一句话结论**：**代码不再是瓶颈，约束来自构建两侧那些人速运行的环节** ——
> 解法是把流程从**线性**改成**循环**，每个阶段交一个**产物（committed artifact）**，下一个阶段从读这个产物开始。

---

## 一、前提变了：三个现实

| # | 现实 | 说明 |
|:--:|------|------|
| **1** | **瓶颈转移到构建阶段左右两侧** | 主要是**规划、审查/测试、部署** —— 这些还在以人的速度运行 |
| **2** | **管控手段和现实脱节** | 代码是人写的时候，逐行审查合理；**当 agent 产出大部分 diff，逐行审查跟不上了** ⚠️ |
| **3** | **治理成本上升** | 例外情况还要走会议和委员会，**而这些会每周或每月才开一次** |

**⭐ 安全审查的例子（很典型）**：
> 安全团队人力是按**人类产出量**配置的；
> agent 把代码产出量翻几倍后，**要么审查队列越积越长，要么代码没审就上线**。
> **受监管的组织两种结果都接受不了。**

**⭐ 结论**：
> **"传统 SDLC 需要经历和代码实现阶段同等程度的改造。"** ✅

---

## ⭐⭐ 二、AI 原生 SDLC 的定义

> **"一套重新设计的流程，把旧的管控目标和新的执行方式结合起来。
> 流程从线性变成了循环，AI 嵌入到每个节点。
> 它推动自动化的交接和后续步骤的触发，解决传统 SDLC 各阶段之间手动、笨重的衔接问题。"**

---

## ⭐⭐⭐ 三、核心概念：提交的产物（committed artifact）

**每个阶段结束时，往版本控制里写一个产物；下一个阶段从读取这个产物开始。**

| 阶段 | 产物 | 说明 |
|------|------|------|
| **规划** | `intent.md` | 意图 |
| **设计** | `spec.md` | 规格 |
| **构建** | `plan.md` + 代码 diff + 测试 | 计划与实现 |
| **测试** | 带审查结论的证据 | 测试日志/截图/评测结果 |
| **部署** | 带审查结论的 PR | 审批记录 |
| **运维** | 事故记录 | 回流成新的 intent |

**⭐ 关键设计**：
> **早期阶段的主要产物是 `.md` 文件，因为产品负责人和 agent 都能读、都能用。**
> **从构建阶段往后，产物就是代码和它的记录。**

**⭐⭐ 一句话价值**：
> **"这条 commit 链本身就是审计链：谁提了什么需求，agent 产出了什么，谁批准了它。"** ✅

**⭐ 人的角色**：
> **"人对每一个需要判断力的决策负责。
> 人的注意力随着需要审查的产物一起转移。"**

## 四、Play 的结构（这份手册的组织方式）

**每个 Play 包含五部分**：
1. **变化了什么**
2. **如何开始**
3. **具体实施步骤**
4. **治理考量**
5. **如何衡量效果**

**⭐ 模块化**：
> 步骤是模块化的，组织可以根据自身需要**优先改造不同阶段**。
> **一个阶段在提交产物时结束，这次提交同时启动下一个阶段。**

**⭐ 演进路径（很重要）**：
```
一开始：你手动触发每一步
        ↓
最终状态：每个通过审核的产物，自动触发下一个门禁
```

> **"人的注意力集中在门禁上，审查的是 agent 标记出来的内容，
> 不用从头开始每个阶段。"** ⭐

## ⭐⭐ 五、各阶段的具体做法（可直接借鉴）

### 1）intent.md：捕获意图

**入口可以有多条**：一个人有了想法 / 一个工单被提交 / 一个告警触发了事故

**具体做法**：
1. 发起人**用自己的话**向 Claude 描述问题（**不需要正式语言**）
2. 反复头脑风暴直到想法具体化 —— **Claude 会问分析师该问的问题**：
   **范围、用户、约束、怎样算成功**
3. 让 Claude 按**组织模板**把结果写成 `intent.md`
   ⭐ **模板可以编码为一个 skill**
4. 发起人修正 Claude 理解错的地方
5. `intent.md` 提交到共享仓库（**作者、时间戳、完整修订历史**）
6. **产品负责人审批**，接受或拒绝的决定记录为合并或关闭审查

**⭐ 价值**：
> **传统 SDLC 里，这个人接下来得说服产品团队帮他写或替他写。**
> **现在他自己就能产出一份人类可读、版本可控的 intent。** ✅

### 2）spec.md：需求与设计

**做法**：
- 产品负责人打开加载了**组织 skills** 的会话，附上 `intent.md`
- Prompt 指向 `intent.md`，列出约束条件，**要求标记关注点**
- **产品负责人审查这份规格说明，但不写它** ⭐
- 对照 idea 审查 spec，**先处理标记出来的关注点**
- 涉及高风险内容时**咨询技术负责人**
- **决定是否进入构建阶段 —— 这个决定始终由人来做**

**⭐⭐ 关键机制**：
> **"组织的 skills 作为约束条件应用在 spec 上。
> 不是等几周后在审查里才发现冲突，而是在 spec 编写时就读取并应用了现行策略。"** ✅
>
> **Spec、产生它的 prompt、以及生效的 skill 版本，全部记录在版本控制里。**

### 3）plan.md：Plan Mode 作为默认起点 ⭐

**做法**：
- 工程师在 **plan mode** 下启动 Claude Code，给它 `spec.md`
- 让它提问、讨论，反复迭代计划，直到工程师满意
- **要求一份实施计划**：列出要改的文件、工作顺序、**证明它 work 的测试**
- **质询计划**：问这个改动可能破坏什么、哪一步风险最大、为什么没选其他方案
- **标准**：**"直到一个从没看过这段对话的工程师，也能只凭这份计划完成改动"**
- 把通过审核的计划提交为 `plan.md`
- 接受计划，让 Claude 实施 —— **"有一份扎实的计划，实施通常一遍就完成了"**

**⭐⭐ 最重要的治理价值**：
> **"设计审查发生在任何代码生成之前，改方向还只是改文档的事。
> Plan mode 本身就强制执行了这一点，因为工程师接受计划之前 Claude 不能编辑文件。"** ✅

### 4）Auto Mode：注意力重心的转移

**演进**：
```
工程师审批计划 → Claude 自动逐个应用变更，不需要每次编辑都确认
```

**⭐ 前提条件（护栏成熟）**：
- 调好的 `CLAUDE.md`
- 编码了策略的 skills
- 拦截不安全操作的 hooks
- **Claude 能自己跑的测试套件**

**⭐⭐ 注意力的转移**：
> **从「看着 agent 做每一次编辑」→「在更长的自主会话之后审查产物」** ✅

## ⭐⭐ 六、CLAUDE.md：最实用的一条实践

**定位**：
> **"给 Claude 提供一个新人入职第一天需要知道的东西：
> 代码规范、命令、架构、团队最常见的错误。"**
>
> **"过去存在人脑里和 wiki 上的知识，变成了 agent 每次会话开头都会读的文件。"**

**做法**：
- 在仓库里跑 `/init`，Claude 从它发现的东西里生成初始版本
- **精简到新人第一天需要的内容**
- **控制在一页以内**

**⭐⭐ 一条极实用的规则**：
> ### **"Claude 犯同一个错两次，纠正就进 CLAUDE.md。"** ✅

**⭐ 为什么这条重要**：
> **这是"个人经验 → 团队资产"的最小闭环** ——
> **不用等写文档，犯错即沉淀** ✅

## 七、对"研发工作台"的直接借鉴（5 条）

| # | 借鉴点 | 怎么用 |
|:--:|-------|-------|
| **1** ⭐⭐ | **工作台 = 产物链的载体** | 每个任务结束必须**提交一个产物**，下一个任务从读它开始 |
| **2** ⭐ | **"门禁"而不是"审批流"** | 人只审**agent 标记出来的关注点**，不用从头看 |
| **3** ⭐ | **模板编码成 Skill** | intent 模板、spec 模板都做成 Skill，让 AI 按模板产出 |
| **4** ⭐ | **设计审查前置** | 像 Plan Mode：**计划没被接受前，不允许改动** |
| **5** ⭐ | **"犯错两次就写成规则"** | 对应我们的 Skill/规范沉淀机制 |

**⭐⭐ 一条可直接用于设计的原则**：
> **"每个阶段都要留下下游能读懂的状态，每次交接都要有明确的证据。"**
> —— **这比"做个好看的界面"重要得多** ⚠️

> **代码不再是瓶颈；约束来自构建两侧那些人速运行的环节。** ⚠️

> **⭐⭐ 三个核心机制**：
> **① 提交的产物（intent → spec → plan → diff+测试 → PR → 事故）**
