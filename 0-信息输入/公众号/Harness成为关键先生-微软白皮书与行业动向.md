# Harness 成为关键先生

> **一句话结论**：**同样的模型，只换 Harness，复杂任务通过率能差出 22 个百分点** ——
> 那个大模型背后的"运行系统"，正在成为比模型选型更关键的变量。

---

# ⭐⭐⭐ 一、最硬的一组数据（微软 2026-11-07 白皮书）

| 指标 | 结果 |
|------|------|
| **同样的 Claude Opus 4.8，只换掉 Copilot Studio 背后的 Harness** | **复杂任务通过率提高 22.1 个百分点** |
| 新系统每项任务调用模型的次数 | **几乎翻倍** |
| 折算后的输入 Token 消耗 | ⚠️ **反而减少 21%** |

**⭐⭐ 这组数据的颠覆性在于**：
> **"多调用几次模型"不等于"更贵"** ——
> **Harness 变好，可以用更多次调用换更准的结果，同时总 Token 还更省。**
> **→ 直接打脸"模型越强、harness 该越薄"的说法。**

---

# ⭐⭐ 二、更强的证据：换 Harness 能改变模型排名

| 测试 | 结果 |
|------|------|
| **FrontierHarness Eval**（同一个 Kimi K3） | **Codex 66.7%** ／ DeepSeek Harness Creator 63.3% ／ Kimi Code 56.7% |
| **新加坡南洋理工大学**（2026-10，66 种模型 × Harness 组合） | **更换 Harness 甚至可能改变模型之间的性能排名** |
| **斯坦福 Meta-Harness**（3 月底） | 让 AI 根据失败记录直接改 Harness 代码：准确率 **+7.7%**，上下文 Token 降至原来 **1/4** |
| **HarnessFlow**（11 月） | 自动搜索更好的 Harness 设计，六类任务平均 **+10.89 个百分点** |

**⭐ 结论**：
> **同一个模型，换个 Harness，表现能从倒数变第一。**
> **→ 选 Harness 比选模型更影响最终结果。**

---

# ⚠️ 三、但有一个必须知道的风险

> **11 月初一项研究发现：一个 Harness 经过新任务优化后，
> 原先在 SWE-bench 上的成绩从 94% 跌至 32%。**

**⭐ 含义**：
> **Harness 的优化很难一劳永逸** ——
> **为 A 场景调好的 Harness，可能在 B 场景崩掉；模型升级也可能让原来的设计失效。**

**⭐ 对我们的直接提醒**：
> **"项目 Harness"必须按业务线隔离**（高压/低压/竣工检验各自一套），
> **不要指望一套 Harness 通吃三条线。**

> **从 2 月（快手那篇的时点）到现在，这是最大的结构性变化之一。**

# ⭐⭐ 五、为什么模型公司愿意做不赚钱的 Harness

## 定价现实：Harness 本身几乎不赚钱

| 厂商 | 收费方式 |
|------|---------|
| **Anthropic Managed Agents** | **$0.08 / 活跃会话小时**，Token 另计<br>官方示例：一小时编程任务总费用 $0.58，**托管运行费只占约 14%** |
| **Kimi** | 模型 Token + 沙箱运行 + 付费插件<br>示例：投行法律分析约 30 元，**沙箱费用不足 0.1 元** |
| **OpenAI** | Agents API 公测期免收额外服务费，按模型和工具用量计费 |
| **DeepSeek** | MIT 开源，无直接收费逻辑 |

## 那图什么？两个理由

**理由 1：企业真正部署 Agent 后，对 Harness 的需求比对某个特定模型更稳定**

> 案例：美国法律服务公司 **ABC Legal** 原本把 Agent 部署在员工电脑上跑定时任务，
> 规模扩大后换成 Anthropic Managed Agents —— **一个月内 50+ Agent 投入生产，约 310 名员工日常使用**，
> **员工不需要会写代码，配置就能创建新 Agent。**

**理由 2：Harness 能拿到"工作轨迹"**

> **Harness 可以记录一项任务从开始到完成的工作轨迹** ——
> 模型调用、工具执行、失败重试、最终结果。
> 这些记录既能帮企业排障，也能为模型研发提供反馈。

**⭐⭐ 文章最后一句点题**：
> **"一个熟悉又老套的词：入口。"**
> **谁能提供可靠的运行系统，谁就有机会影响模型的选择，以及 AI 如何参与真实业务。**

# ⭐ 六、一个重要的市场事实（对我们有利）

> **VentureBeat 2026-08 调查 107 家企业**：
> - **85% 同时使用两套或更多 Agent 编排平台**
> - 选平台时 **29% 最看重模型与工具的灵活性**
> - **只有 10% 优先考虑与某个领先模型的原生适配**

**⭐⭐ 含义**：
> **企业不愿意被一家模型绑死，愿意同时用多套编排平台。**
> **→ 那我们自建一套面向项目组的 Harness，在这个数据面前是合理的，不是重复造轮子。**

# ⭐⭐ 七、对我们的用处（这是最重要的一节）

## 7.1 给"为什么要做工作台"提供了一个**实证级**答案

**我们原来的论证链**（来自 AI 驱动研发体系那篇）：
> 通用 Harness 缺业务知识、流程约束、完成标准 → 所以要加项目 Harness

**现在多了一个数据支撑**：
> **同样的模型，只换 Harness，复杂任务通过率相差 22.1 个百分点。**

**⭐⭐ 一句可以直接讲的表述**：
> **"微软 11 月刚发的白皮书里有个数据：同一个模型，只换外面的运行系统，复杂任务通过率差 22 个百分点。
> 所以决定效果的不只是模型，还有围绕模型的这一层。我们要做的就是这一层。"**

## 7.2 印证了腾讯那句"harness 该越薄是想当然"

> 腾讯深水区：模型越强只让产出更多更快，**而人的审查能力一点没涨**
> 微软白皮书：**还是要靠 Harness，而且 Harness 的投入产出比很高**（调用翻倍、Token 反而省 21%）

## 7.3 印证了"任务可中断续跑"不是花活

> Anthropic 改进 Harness 的起点就是"上下文耗尽接不上" ——
> **保存进度、下一轮读取继续** ——
> 这正是百炼 Session「可中断/续跑/审批」要解决的问题。

## 7.4 新提醒：Harness 要按业务线隔离

> 见第三节的风险：为 A 调好的 Harness 可能在 B 崩掉（SWE-bench 94%→32%）。
