# AI Agent 应用精细化评测：从黑盒到白盒

> **两个来源**：① 刘瑞洲《AI Agent 应用精细化评测》22,849 字（完整版）
> ② 玄姐《AI 智能体评测体系架构设计与落地实践》11,837 字
> **⭐ 同一套商品中心 Agent 评测体系的两个版本，本篇合并**
>
> **一句话结论**：**粗粒度的"通过/不通过"撑不起业务快速迭代 ——
> 我们要知道它在"哪个环节、因为什么问题、以多大的概率出错"。**

---

## ⭐ 开篇的转折点（一个真实的教训）

> **两个版本的 Agent 综合评分只差 2%，但上线后用户投诉量差了 3 倍。**
>
> 翻遍日志才发现：**A 版本在"意图识别"环节悄悄退化，
> 把大量本该走 Skill 链路的问题错误路由到了知识库。**

**⭐ 结论**：
> **"综合评分掩盖了 Agent 工作链路的真实表现。"**

---

## ⭐⭐ 一、传统评测的六个致命伤

| # | 问题 | 表现 |
|:--:|------|------|
| **1** | **评测粒度太粗** | 两版评分相近，但不知道差异来自"某环节提升、另一环节退化"还是"均匀波动" |
| **2** | **无法检测幻觉** | 文本相似度给"看似合理但编造"的答案打高分 —— **幻觉内容语法完美，LLM 看不到"内容是否准确"** |
| **3** | **忽略中间过程** | 只对比最终答案 → **看不到 Agent 是否走了弯路、是否"蒙对了"** |
| **4** | **掩盖成本效率** | 一个调 3 次工具耗时 2 秒，另一个调 15 次耗时 15 秒 —— **质量分完全掩盖资源差异** |
| **5** | **缺乏多轮评估** | 单轮问答测不出**上下文丢失、重复提问、固执己见** |
| **6** | **真实场景脱节** | 评测集是"干净问题"，用户输入充满**歧义和口语化** |

**⭐ 一句话总结**：
> **"传统评测只能告诉你'车能不能从 A 开到 B'，但车坏了你根本不知道修发动机还是换轮胎。"** ✅

## ⭐⭐⭐ 二、核心解法：评测面向架构（四模块逐层拆）

**Agent 由四个核心模块组成，评测也按同样结构逐层拆解**：

| 模块 | 职责 |
|------|------|
| **感知（Perception）** | 接收输入，判断能否被已注册 Skill 处理；**未命中降级到知识库检索** |
| **规划（Planning）** | 制定执行策略：是否调工具/检索/存记忆；**实现 Skill 场景与 RAG 场景自动分流** |
| **记忆（Memory）** | 短期：基于会话 ID 维护多轮上下文（**滑动窗口 + 用户画像**）；长期：对接 RAG |
| **工具（Action）** | 通过 **MCP 协议**自动发现注册远程工具；Skill 基于文件系统管理 |

**⭐⭐ 白盒 vs 黑盒（核心价值）**：
> **任务完成率从 85% 掉到 60%，端到端只能告诉你"车坏了"；
> 模块级能定位到**：
> · **感知**：把"查 Trace"错误识别为知识库问答（意图识别错误）
> · **规划**：该调 Skills 时选了 RAG 检索（路由决策错误）
> · **记忆**：多轮对话丢失上一轮的商品 ID（记忆丢失）
> · **工具**：错误调用 MCP 或参数填充错误（工具调用错误）

## ⭐⭐ 三、三条设计原则（可直接抄）

| # | 原则 | 含义 |
|:--:|------|------|
| **1** ⭐ | **评测面向架构** | Agent 由感知/规划/记忆/工具四模块组成，**评测按同样结构逐层拆解，让每层质量可独立观测** |
| **2** ⭐⭐ | **指标面向行动** | **"每一项指标都是一份'诊断报告'而非'成绩单'。**<br>**它的价值不在于给出多高的分数，而在于下降时能精准告诉开发者：是该修改 Skills、替换 MCP 工具、还是优化知识检索。"** ✅ |
| **3** | **能力面向产品** | **评测不应是上线前跑一次就扔的脚本**，而应像监控告警一样**可持续运行、可横向对比、可追溯演进** |

## 五、对我们的启示

| # | 启示 | 怎么用 |
|:--:|------|-------|
| **1** ⭐⭐⭐ | **评测要拆到模块级** | 不测"整体好不好"，测**感知/规划/记忆/工具**每一层 |
| **2** ⭐⭐⭐ | **指标要能指向行动** | 每个指标下降时，必须能回答"该改什么" |
| **3** ⭐⭐ | **综合评分不可信** | 两版差 2% 但投诉差 3 倍 —— **要看分项** |
| **4** ⭐ | **评测要可持续运行** | 不是一次性脚本，像监控一样常驻 |
| **5** ⭐ | **成本效率也是指标** | 工具调用次数、耗时要在评测里体现 |

**⭐⭐ 一条可直接用于我们评测设计的表述**：
> **"我们不要'成绩单'，要'诊断报告'—— 分数下降时必须能指出改哪一层。"**
