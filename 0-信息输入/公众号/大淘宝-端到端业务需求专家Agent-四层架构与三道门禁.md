# 一句话

**淘天跑通了一套"业务需求专家 Agent"闭环：四层架构（上下文输入 / 业务专家编排 / 工具执行 / 反馈学习）＋ 八阶段流程 ＋ 三道质量门禁，最核心的两个设计决策是"项目记忆不直接升级进长期知识"和"门禁不能只靠提示词，必须做成 git hook 这种绕不过去的硬卡口"；全文最有说服力的一句是——"AI 写测试最常见的失败模式不是写不出来，而是为了通过覆盖率而写"。**

> ⚠️ 属性说明：本文为**技术团队内部实践自述**（淘天集团用户&内容技术团队），非官方产品文档，不含第三方评测。

# 一、它定义的问题（跟我之前的判断一致，但它说得更准）

> 「AI 写代码本身已经不再是主要瓶颈。但一个业务需求从 PRD 到上线，中间要经过需求澄清、方案确认、实现、CR、验收、发布观察和结项沉淀——**代码生成只是其中最标准化的一段，真正贵的是代码之外的串联成本。**」

> 「每个环节 AI 都已经能参与一点，但如果这些能力只是散落在不同对话、不同工具和不同命令里，**最后真正负责串起来的还是人**。」

## 三个工程化问题（这个拆法比"提效"两个字有用得多）

| # | 问题 | 原文 |
|:--:|------|------|
| **1** | **上下文能不能被组织起来** | 「很多时候 **Agent 表现不好，不是模型不会推理，而是它拿到的上下文就不完整**」 |
| **2** | **工具能不能被串起来** | 「**每多切一次平台，就多一次上下文丢失和人工判断**」 |
| **3** | **反馈能不能产生复利** | 「如果只停留在聊天记录里，**下一个需求大概率还会再犯一次**」 |

**⭐⭐ 我的判断**：
**这三个问题的排列顺序本身就是答案——先上下文，再工具，最后反馈。**
**而我们之前讨论的时候，是从"功能"开始的（要做什么页面、什么模块）。**
**顺序反了，所以做出来的东西是功能拼盘，不是闭环。**

# 二、总体架构：四层（不是并列模块，是闭环）

> 「它负责把上下文组织好，把工具串起来，**把人工确认放在正确的位置**，再把过程反馈收回来。」

| 层 | 回答的问题 | 关键设计 | 金句 |
|:--:|-----------|---------|------|
| **1. 上下文输入层** | 「Agent 靠什么理解业务」 | **不是把所有资料一次性塞进 prompt，而是按阶段拉取**：长期业务知识、当前需求材料、代码事实、运行证据 | **「上下文错了，后面越努力越偏」** |
| **2. 业务专家编排层** | 「下一步该做什么」 | 判断当前阶段（澄清/方案/可实现）、哪些必须停下来等人、哪些可自主推进、证据不足时是回退补上下文还是请求人工 | **「这些判断如果都靠人盯着，成本很高，而且不可复现」** |
| **3. 工具执行层** | 「具体动作怎么落地」 | Aone、Code/CR、配置平台、SLS/HSF、监控、钉钉文档不再是一堆需要人手动切换的网站 | — |
| **4. 反馈学习层** | 「下次能不能更好」 | CR 评论、issue 对话、验收记录、自恢复日志、人工修正 → 结项时蒸馏 | **「没有这一层，系统就是无状态的，每个需求都得从零开始」** |

**⭐ 我以前一直把"编排层"理解成任务分发，这里给了更准确的定位：**
**编排层解决的是"什么时候必须停下来问人"——也就是决策，不是调度。**

# 三、⭐⭐⭐⭐ 最重要的机制：三个仓库 + "不直接升级"

## 3.1 三个仓库

| 仓库 | 分支策略 | 装什么 |
|------|---------|--------|
| **代码仓库** | 按需求拉 feature 分支 | 真实代码 |
| **项目记忆仓库** | **按需求拉 feature 分支** | requirements、plan、progress、CR 评论、验收证据 |
| **长期 wiki 仓库** | **始终在 master** | 业务知识、codemap、历史口径、系统边界 |

> 「需求进入时，Agent 从**长期 wiki** 加载业务知识；需求推进过程中，requirements、plan、progress、CR 评论、验收证据这些过程材料在**项目记忆的 feature 分支**上持续积累；结项时，再从这些过程材料里**筛选出稳定的业务知识，蒸馏回长期 wiki**。」

## 3.2 ⭐⭐⭐ "不直接升级"——这句话是整篇的核心设计

> 「这个设计的关键在于**"不直接升级"**：项目过程中产生的事实**先留在项目记忆层**，只有经过**结项审视和人工确认**，才会选择性地进入长期知识。」

> 「这样既**避免了噪声污染长期 wiki**，也保证了每次结项都能**沉淀出真正有复用价值的业务知识**。」

**⭐⭐ 我的判断：这一条直接解决了我们知识库设计里最大的隐患。**

**对比一下我们现在的做法**：
- 我们的 `~/知识库/raw`（31 份原始文档）→ `wiki`（71 页归纳）
- **归纳是怎么进去的？中间没有"结项审视"这道闸。**

**按这套标准，我们的知识库应该改成三段式**：

```
raw 原始文档（不可变）
   ↓ 使用时按需读取
项目记忆（每个需求一个分支/目录：需求材料、澄清记录、方案、验收证据）
   ↓ 结项时人工确认，只挑稳定的
长期 wiki（沉淀后的业务知识，能被下一个需求直接加载）
```

**→ 我们现在缺的正是中间那层「项目记忆」。**
**没有它，知识库只能装"通用业务知识"，装不了"这个需求当时为什么这么定"——而那恰恰是腾讯、淘天、网库三家都在强调的东西。**

## 3.3 跟之前两篇的直接呼应

| 来源 | 说法 | 本质 |
|------|------|------|
| **Looki Loom** | Moment 永不覆盖 / Snapshot 持续更新 | 原始经历 vs 当前理解 分开 |
| **本文** | 项目记忆 feature 分支 / 长期 wiki master，**不直接升级** | 过程事实 vs 沉淀知识 分开 |
| **腾讯 PUBG** | 「spec 可以删，事后沉淀的设计说明必须留」 | 过程 vs 结论 分开 |

**⭐⭐ 三家独立得出同一个结构：过程层不可变、沉淀层要过闸。**

# 四、纵向八阶段（每一阶段都对得上我们的流程）

## 3.1 需求进入：先组织上下文

**两类信息**：
- **当前需求材料**：Aone 工作项、钉钉 PRD、issue 评论、用户补充说明 → 回答"到底要做什么"
- **长期业务知识**：LLM Wiki、codemap、历史口径、系统边界 → 回答"怎么快速理解业务，不用每次从零讲背景"

**产出**：**上下文快照**
**人工确认**：正常情况下**不需要**；**只有事实源缺失或需求材料冲突时才停下来让人补充**

> **「起点歪了，后面每一步都在放大偏差。」**

**⭐ 这条对上领导 11-24 最重的那句话**：
> 领导：「我在做所有交付的时候，**我的基准是什么？你不得把他的可研和合同真正上传上去吗？**」

**→ 大淘宝把这件事做成了架构的第一层和第一步。**
**→ 我们的"可研 + 合同"就是它的"当前需求材料 + 事实源"。**

## 3.2 需求澄清：第一质量门

**关键点：结构化澄清，不是继续在聊天里追问**

> 「它不是继续在聊天里追问，而是把初始上下文整理成**可审阅的 requirements**：目标行为、非目标边界、验收标准、风险和待确认问题。」

**⭐⭐ 人确认的对象变了**：
> 「人需要确认的**不是一堆零散回答**，而是"**这份 requirements 是否准确表达了需求**"。」

**⭐⭐⭐ 硬门禁**：
> 「**确认前，不应该继续进入技术方案或实现**；确认后的 requirements 会成为后续 plan、实现和验收的**共同基准**。」

**协作留痕**：
> 「对 Agent 的反馈**不应该只停留在对话框里**，而应该尽量落到平台本身的评论体系里。」

## 3.3 技术方案：第二质量门（人工确认最密集）

**方案要回答的是一组完整问题**：
现状 / 目标行为 / 不做什么 / 影响范围 / 核心改动点 / 风险 / 怎么验证 / 出问题怎么回滚

**⭐⭐ 最容易被低估的一句**：
> 「方案阶段就应该把"**怎么验收**"定清楚。很多需求到了实现完才开始想怎么验证，结果发现验收条件不明确、配置状态没确认、边界场景没覆盖，又要回头补。」

> 「所以在方案阶段，**验收方式、测试策略和验证入口就应该写进 plan**。」

**验收不只是单测**：HSF 接口调用、SLS 日志查询、监控指标核对
**正反 case 都要在方案阶段定好**，否则「到了验收环节还在临时想"到底该查什么"」

**配置类需求的专门提醒**：
> 「方案阶段**不只是读取当前配置状态，还包括提前创建好配置的 schema、完成配置校验**，并把这些信息写进技术方案文档里。这样实现时直接对着 schema 写代码，验收时直接对着 plan 里的验收标准逐项核对。」

**硬门禁**：
> 「**没有确认的方案不进入编码。**」

**⭐ 这条对上领导 11-24 说的异常情况**：
> 「1.0 已经开发一半了，我强行改成 1.1，他后面的联动会不会跟着改？」

**→ 大淘宝的答案是：方案阶段就把"影响范围"和"怎么回滚"写清楚，而不是事后分析。**

## 3.4 实现与内部质量门：TDD、PMD、review

### ⭐⭐⭐ 关于 TDD 的那段判断，是全文最锋利的地方

> 「为什么要强调这一点？因为 **AI 写测试最常见的失败模式不是"写不出来"，而是"为了通过覆盖率而写"**——先写完代码，再补一堆只验证代码能跑通的测试，**本质上只是在用测试确认自己的实现，而不是用测试约束正确行为**。」

> 「真正有价值的 TDD 是反过来的：**先根据 plan 里已经定好的验收标准和业务行为写测试，让测试定义"什么是对的"，再让实现去满足测试**。这样测试才是真正的质量约束，而不是**事后的覆盖率装饰**。」

**⭐⭐ 这跟我前几天跟你说的"自检独立性已被削弱"是同一个问题：**
**AI 自己写完自己验，产出的断言会贴合自己的实现——包括实现里的错误假设。**

### pre-push quality gate（Agent 自己必须过，不需人工）

| 检查 | 内容 |
|------|------|
| **diff-to-test 映射** | 每一处生产代码的行为变化都要有**具体测试锚点**，「不能只靠'跑了一遍模块回归'证明」 |
| **PMD / lint** | 规则类问题由自动化工具捕获，失败就回到实现阶段 |
| **Agent 内部代码 review** | PMD 通过后，对完整待 push diff 做结构化 review，发现 actionable 问题就修、重跑、再 review |

### ⭐⭐⭐⭐ 最关键的设计取舍（这段能直接决定我们的技术方案）

> 「这里有一个关键的设计取舍：**这些门禁不能只靠提示词约束，必须变成 Agent 绕不过去的硬规则**。**提示词再怎么写"push 前必须跑 PMD"，Agent 在复杂任务中还是可能跳过。**」

> 「所以落地时，我们通过 **git pre-push hook** 把 PMD 校验和单元测试覆盖率检查注入到 push 流程里——Agent 执行 `git push` 时，hook 会自动触发检查，不通过就**直接拒绝 push**。」

> 「这样质量门禁就从"**Agent 应该做**"变成了"**不做就推不上去**"，是**真正的工程化卡口，而不是靠提示词的自觉**。」

**⭐⭐⭐ 这一段正好回答了领导 11-24 那个悬而未决的问题：**

> 领导：「约束这个东西我放在哪？**放到 Harness 里面吗？放到 skill 里面吗？不一定哦。**」
> 领导：「这个东西可能要跟环节和每个不同任务相关，那这东西要考一下**它的载体是什么**？」

**→ 大淘宝给的答案：约束的载体不是提示词，是"流程里绕不过去的那个钩子"。**

**对我们直接可用的三条**（呼应我之前提的 verify_prd.py）：
1. **能写成断言的，就做成出稿后自动跑的脚本**（不是写在 SKILL.md 里靠模型记得）
2. **能挂到必经动作上的，就挂成钩子**（比如"归档前必须过检查"）
3. **写在提示词里的约束，上下文一压缩就没了，而且事后无法证明它当时在不在**

## 3.5 CR / Issue 协同：把人机反馈留下来

**⭐⭐ 一个反直觉的观察（对我们排优先级极有用）**：
> 「实际跑下来会发现，**评论协作最密集的阶段恰恰是澄清和方案，而不是代码实现**。**需求理解对了、方案确认了，到了真正写代码的时候，以现在 Agent 的能力反而不需要那么多微操。**」

**→ 这解释了为什么"人审核跟不上"这个问题，应该从澄清和方案阶段解决，而不是在代码阶段加人。**

**机制**：
- Agent 主动读 CR 上的 **unresolved 评论** → 按评论改文档或代码 → 提交新 commit → 回复并 resolve
- **涉及需求语义或范围变更 → 回到 requirements 或 plan 阶段重新确认，而不是在当前层面硬改**
- 重大节点通过 milestone 回刷：澄清完成 / 方案确认 / 进入 TDD / 代码完成 / CR 反馈处理 / 验收通过
- **每条评论都带 commit link、CR link 和验证证据**

**为什么强调留痕**：
> 「哪些澄清反复出现、哪些代码模式被反复指出、**哪些人工介入本可以自动化**——这些信息只有留在平台上，结项时才能被系统性地回看和分析。**如果反馈只停在聊天框里，需求结束就蒸发了。**」

## 3.6 验收验证：用真实证据确认结果

> 「**单元测试通过不等于业务做对了。**」

**做法**：独立项目环境（**不是共享预发**）→ 部署 feature 分支 → HSF 泛化调用验证业务行为 → SLS 查询验证日志输出 → 监控/Sunfire 验证运行时指标

**三类验收标准（必须覆盖）**：
| 类型 | 查什么 |
|------|-------|
| **正例** | 核心业务场景是否按预期工作 |
| **反例** | 边界条件和异常路径是否被正确处理 |
| **回归** | 改动是否影响了不应该变化的行为 |

**⭐ 价值**：
> 「让验收从"**人肉点一下看看**"变成"**Agent 用可回读的证据证明结果**"。验收证据写入 progress 或 verification 文件，后续 CR 审阅和结项时都可以引用。」

**人工门仍在**：进主预发或线上发布前**必须人工确认**，Agent 不会自动执行。

## 3.7 发布与变更观察

> 「**上线是需求交付的一个节点，不是终点。** 只有观察期无异常，才算真正可以进入结项。」

**发布本身要**：变更材料、风险评估、回滚预案——Agent 协助准备，**发布动作仍由人工确认和执行**。

## 3.8 结项沉淀：让下一次需求更少依赖人工

**结项不是写一句"已完成"，而是回答三个问题**：

| 问题 | 内容 |
|------|------|
| **哪些知识是稳定的** | 业务规则、系统边界、验收规范、排障经验 → **CR 确认后进入长期 wiki 和 codemap** |
| **哪些流程可以改进** | Agent 在哪个环节犯错、走弯路、被人工反复纠正 → **skill 和提示词的迭代候选** |
| **哪些材料只需要归档** | 一次性实现细节、临时调试记录、中间状态 → 留在 closeout raw log 作审计底稿 |

**⭐ 一句判断标准**：
> 「**如果某个问题在多次需求里反复出现，就不应该继续靠人盯着。**」

**落地**：生成 closeout raw log（按分类列出所有过程材料和蒸馏判断）→ 分别准备长期 wiki 写入候选 + skill/提示词改进候选 → **每一类都需要人工确认才真正写入**

**闭环合上**：
> 「**每做一个需求，Agent 理解业务的基线就高一点，人需要解释的上下文就少一点。**」

---

# 五、⭐⭐⭐ 它自己承认的三个问题（这一节的价值不低于正文）

## 4.1 接入成本还需要降低

> 「当前 Agent 的首次接入成本偏高，主要在**鉴权和运行时初始化**环节。集团内不少平台工具**还只支持网页授权登录，没有对 Agent 的命令行沙箱环境做好适配**。」

**→ 这是一个"过渡态问题"，随着平台补齐 CLI/API 鉴权会缓解。**

**⭐ 对我们的提醒**：
**我们要走 CLI 路线（领导 11-24 定的），第一个会撞上的就是这个**——内部平台是不是都有 CLI/API？

## 4.2 ⭐⭐⭐ 缺少 Agent 效果的度量体系（最重要的一条自我批评）

> 「前面讲了 Agent 在结项时会把流程改进候选沉淀到 skill 和提示词里，形成自我迭代。**但一个更根本的问题是：怎么知道这些迭代改进是真的有效？**」
>
> 「**目前还缺少一套系统化的度量体系来回答这个问题。**」

**它给出的四个维度（可以直接当我们的看板指标）**：

| 维度 | 具体指标 |
|------|---------|
| **人力投入** | 人工介入次数、**评论轮次**、**人工修正比例** 是不是在下降 |
| **需求质量** | **方案返工率**、**验收一次通过率** 是不是在提升 |
| **线上稳定性** | 上线后的问题数、**回滚次数** 是不是在减少 |
| **协作效率** | **双事实源之间的同步成本**、**跨平台信息丢失率** 是否可控 |

> 「**有了这样的度量基线，才能判断每一轮 skill/提示词迭代到底是改进还是退化，Agent 的自我成长才有据可循，而不是靠感觉。**」

**⭐⭐ 我的判断**：
**这段直接回答了领导 11-24 说的"看板要设计好"和"指标一定会变"。**
**而且它给的四个维度比"token 用量、跑了多少任务"实在得多——**
**因为我们现在的看板指标，全是"机器做了多少"，没有一个"人少做了多少"。**

**→ 我们的看板应该改成这四类，核心是"人工介入次数"和"验收一次通过率"。**

## 4.3 从单 Agent 走向 Agent Team

**方向**：前后端各一个 Agent + 测试 Agent + 队长（需求拆解、派发、协调）

**⭐ 往上游延伸（对我们最相关）**：
> 「往上游看，需求产出本身也可以纳入：**一个 PD Agent 负责生成 PRD、梳理业务规则、输出验收标准**，它同样共享长期 wiki，了解过去的技术方案和业务需求历史。这样一来，前面 3.2 里**人工介入最密集的需求澄清环节，就可以变成 PD Agent 与业务专家 Agent 之间的直接对齐**，人只需要在关键歧义处做最终裁决，而不是全程逐条解释业务背景。」

**→ 这段几乎就是在描述你的岗位未来形态。**

**平行领域已验证**：数据专家 Agent 用同一套方法论（上下文组织 → 方案确认 → TDD → 验收取证 → 结项沉淀），只做离线数据开发、报表、分析
> 「它验证了一件事：**这套框架不是只能用在后端编码上，而是可以被不同领域的 Agent 复用的通用研发流程。**」

**⭐⭐⭐ 两条关键设计约束（这两句要划重点）**：

> 「这个 team 模式的关键设计约束是**共享长期 wiki，各自维护视角**。所有 Agent **共享同一份长期业务知识**，保证对业务理解的一致性；但每个 Agent 从整体需求中**只拆解出跟自己职责相关的部分**，各自维护自己的 requirements、plan 和过程产物。队长负责把各方产物对齐，确保前后端接口契约一致、测试覆盖完整。」

> 「不过 **Agent 拆分不应该按流程步骤机械切分，而应该看是否真的存在独立判断、独立产物、并行执行和责任隔离的需要**。**在还没有足够多的真实复杂需求验证之前，不急于提前铺设。**」

**⭐⭐ 最后那句正好是给我们的**：
**我们现在连单 Agent 都没跑稳，急着拆多 Agent 只会多出交接点。**
**（这跟阿里那篇"给成熟链路加速，不是给早期项目提效"是同一个判断。）**

# 六、结语那两段（可以直接引用的表达）

> 「**人不应该继续在每个需求里反复补位，而是把这些补位动作沉到系统里。Agent 缺上下文，就补知识和项目记忆；缺能力，就补工具接口；流程容易跑偏，就补确认门和质量门；反馈容易丢失，就补评论、验收和结项沉淀。**只有这些工作条件被系统化，需求交付才不会继续卡在人身上。」

> 「也许真的会有一天，**PD 提完需求之后，就能直接交给对应的业务 Agent 去研发、验收和上线。**」

**⭐⭐ 第一段这个句式（"缺什么就补什么"）特别好用**：
**因为它把抽象的"AI 原生转型"拆成了四个具体的补位动作，每一动作都有对应的产品模块。**

# 七、⭐⭐⭐ 对我们工作台/原型的 9 条直接可用判断

## ① 架构第一层就应该是「上下文输入」，不是首页

**它的四层顺序（上下文 → 编排 → 工具 → 反馈）比我们之前讨论的"入口/主区/方案区"更本质。**
**→ 我们的技术架构图应该按这四层画，而不是按"前端/后端/知识库"。**

## ② 我们缺的是「项目记忆」这一层，不是知识库不够大

**现在的链路是**：
```
raw 原始文档 → wiki 归纳页（71 页）
```

**应该改成**：
```
raw（不可变事实源）
   ↓
项目记忆（每个需求一个目录/分支：需求材料、澄清记录、方案、验收证据、CR 反馈）
   ↓ 结项时人工确认，只挑稳定的
长期 wiki（沉淀后的知识）
```

**→ "不直接升级"这一条，是我们知识库最该补的机制。**

## ③ 澄清的产出应该是「一份可审阅的 requirements」，不是「一堆问答」

**它把澄清从"聊天里追问"变成了"生成一份文档让人确认"。**
**→ 这正好解决领导 11-24 说的"没有人讲输入"——输入不是上传个文件，是要整理成可审阅的结构。**

**其结构可以直接抄**：目标行为 / 非目标边界 / 验收标准 / 风险 / 待确认问题

## ④ ⭐ 验收标准必须在方案阶段定，不能等实现完再想

**原文**：「很多需求到了实现完才开始想怎么验证，结果发现验收条件不明确、配置状态没确认、边界场景没覆盖，又要回头补。」

**→ 这一条对我们 PRD 写作直接有约束**：
**PRD 里的"验收标准"必须是可执行的（能跑的命令、能查的日志、能对的数据），不能是"功能正常"这种话。**

## ⑤ ⭐⭐⭐ 约束的载体：不要写在提示词里，要挂到必经动作上

**原文**：「提示词再怎么写"push 前必须跑 PMD"，Agent 在复杂任务中还是可能跳过。」

**→ 对我们的直接改造**：
| 约束类型 | 错误做法 | 正确做法 |
|---------|---------|---------|
| 文档格式 | 写在 SKILL.md 里 | **出稿后自动跑脚本检查** |
| 待确认项完整性 | 靠模型记得 | **比对正文与第 11 章的集合差异** |
| 归档前检查 | 靠"应该做" | **做成归档脚本的前置校验，不过不允许归档** |

**⭐⭐ 这就是领导 11-24 问"约束放哪"的一个可落地答案。**

## ⑥ 看板指标要换成"人少做了多少"

**它给的四个维度**：人力投入 / 需求质量 / 线上稳定性 / 协作效率
**核心指标**：**人工介入次数、评论轮次、人工修正比例、方案返工率、验收一次通过率、回滚次数**

**→ 我们现在想的"token 用量、跑了多少任务"全是"机器做了多少"，证明不了价值。**

## ⑦ CLI 路线是对的，而且它给了实证

**原文**：「这些 skill 调用的都是**平台已有的命令行工具和 API，Agent 不需要登录任何 Web 页面**。」

**→ 领导 11-24 定的"不考虑界面，走 CLI"不是拍脑袋，是有先例的。**
**⚠️ 但第一个坑它也说了：内部平台如果只支持网页授权，CLI 就卡住。**

## ⑧ 澄清和方案才是人工最密集的地方，不是代码

**原文**：「评论协作最密集的阶段恰恰是澄清和方案，而不是代码实现。」

**→ 我们要演示的"人机协作"应该放在澄清和方案，而不是放在"人改代码"。**

## ⑨ 不要急着拆多 Agent

**原文**：「Agent 拆分不应该按流程步骤机械切分……**在还没有足够多的真实复杂需求验证之前，不急于提前铺设。**」

**→ 跟我们现状一致：单 Agent 都没跑稳，先别拆。**

# 八、一个我必须指出的隐藏价值

**这篇里反复出现的一个模式，值得单独拎出来：**

> 「**如果某个问题在多次需求里反复出现，就不应该继续靠人盯着。**」

**这句话是一条判断标准，可以套在任何环节上**：
- 某个澄清问题问了三次 → 应该进 requirements 模板
- 某个格式错误犯了三次 → 应该进自动检查脚本
- 某类返工出现三次 → 应该进方案阶段的必查项

**⭐⭐ 它的价值在于：把"要不要做自动化"这个模糊判断，变成了"数一数出现几次"的可操作判断。**

# 九、一句话记住它

> **代码之外才是瓶颈，而代码之外的成本主要是三种：上下文组织、工具串联、反馈不产生复利。**
>
> **⭐⭐ 所以它做了四层架构（上下文/编排/工具/反馈）＋ 三个仓库（代码/项目记忆/长期 wiki）＋ 三道门禁（澄清/方案/内部质量）。**
>
> **⭐⭐⭐ 而全文最该抄的两条设计决策是：**
> **① 项目记忆不直接升级进长期知识 —— 必须先过结项审视，避免噪声污染；**
> **② 门禁不能只靠提示词 —— 要挂到 git hook 这种绕不过去的必经动作上，从"应该做"变成"不做就推不上去"。**
