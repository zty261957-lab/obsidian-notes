# 让 QA 真正用起来：测试用例生成 Agent 落地，我们做对了什么

> **一句话结论**：**不是替代 QA，而是把"测试意图"转译成"可执行用例"** ——
> **全流程无人干预，比单点智能更重要。**

---

## ⭐ 一、先看数据（这些数字很有说服力）

| 指标 | 数据 |
|------|------|
| **生成用例被集成到 CI/CD 的比例** | **85.4%** |
| 新增用例中来自 Agent 的比例 | 平均 **约 25%**，个别团队峰值更高 |
| **Agent 用户月活率** | **30.7%** |
| **每双周为部门节省** | **约 30 人天** |

---

## ⭐⭐ 二、六个做对的地方（可直接借鉴）

### 1｜选对场景：**不做替代，做"用例转译"**

**没有让 Agent 直接替代 QA 做测试设计，而是选了边界更清晰、确定性更高的任务**：
> **把 QA 用自然语言描述的测试场景，转化为可运行的回归测试用例。**

**⭐ 为什么这个场景好**：
- **输入和输出都有相对明确的约束**，更适合 LLM Agent 落地
- **业务价值明确**：QA 写场景不难，**真正耗时的是识别背后的后端 API + 写面向 API 的自动化用例**

> **"Agent 没有替代 QA 的判断，而是降低了 QA 把测试意图沉淀为自动化资产的成本。"** ✅

### 2｜⭐ **全流程无人干预，比单点智能更重要**

**测试用例生成是多阶段流程**：请求识别 → 依赖分析 → 参数处理 → 断言生成 → 代码生成

> **"如果某个环节失败后需要 QA 介入排查和修复，Agent 带来的效率收益就会被迅速抵消。"**

**核心设计目标**：
> ⭐ **"不是让每一步都生成'最优答案'，而是让整条链路具备足够强的容错能力。"**
> 对不确定或不合法结果：**结构校验 + 异常内容丢弃**，确保后续阶段能继续执行。

**⭐ 关键认知**：
> **"哪怕初版用例不够完美，也要尽可能自动生成一个可运行结果。
> 因为只有当 QA 不需要频繁介入，Agent 才能真正融入日常测试流程。"** ✅

### 3｜⭐ **能用程序解决的，就不要用 LLM**

| LLM 适合 | 程序更适合 |
|---------|-----------|
| 语义理解、模糊判断 | **字段查找、schema 校验、值匹配** |
| 业务步骤 → 具体请求的映射 | **请求过滤、参数替换、断言校验** |
| 根据意图推断预期结果 | — |

> **"这样做的结果是，模型的不确定性被限制在必要范围内。"**

### 4｜⭐ **把 LLM 任务拆小，小到可以校验**

**没有做成一次端到端的大模型调用**（端到端"看起来简单，但工程上很难控制"）。

**拆成多个小任务**：请求匹配、依赖关系提取、断言意图识别、受约束代码生成……

> **"每次 LLM 调用只负责产出一个小的结构化结果，并在进入下一阶段前完成校验。"**
> **"为了让每一步都可检查、可修正、可追踪。"** ✅

### 5｜**给必要的信息，而不是塞入完整流量**

> **"更多上下文不等于更好效果。"**

**原始测试流量里的噪声**：静态资源、轮询请求、重复流量、时间戳、trace id、诊断字段、运行时临时字段

**做法**：过滤无关请求 → 摘要响应结构 → 突出候选字段 → **排除不稳定字段**

> **"上下文不是越多越好，而是越相关越好。"** ✅

### 6｜⭐⭐ **用明确约束限制输出，不只靠自然语言指令**

> **"只靠 Prompt 告诉模型'不要编造字段'，并不可靠。"**
> LLM 仍可能生成不存在的字段、变量名、请求标识，**甚至编造辅助函数**。

**做法**：给**明确的 schema 和允许集合**
- 合法的请求标识
- 候选字段
- 支持的断言类型
- 已有变量名

**⭐ 处理超约束的策略（很关键）**：
> **"只有在存在唯一、确定性的修复方式时，才自动修复；否则直接丢弃。"**
>
> **→ 让模型输出从"自由生成"变成"受控生成"。** ✅

### 7｜**优先生成稳定断言，而不是追求断言数量**

**稳定断言** = 断言对象与业务结果直接相关，且多次执行保持相对一致，不因正常运行变化而波动。

> ⚠️ **"否则即使业务逻辑没问题，用例也可能误报失败，反而降低 QA 对自动化测试的信任。"**

## 三、对我们的启示

| # | 启示 | 用在哪 |
|:--:|------|-------|
| **1** ⭐⭐ | **选"转译型"任务切入**，不做"替代判断" | 我们的 Skill 设计 |
| **2** ⭐⭐ | **全链路容错 > 单步最优** | 工作台的任务编排 |
| **3** ⭐⭐ | **确定性逻辑优先，LLM 只做理解** | 每个 Skill 的设计 |
| **4** ⭐⭐ | **拆小 + 每步校验** | 避免端到端失控 |
| **5** ⭐ | **约束式生成（schema + 允许集）** | 比"Prompt 求它别编"有效得多 |
| **6** ⭐ | **宁可丢弃，不做不确定的自动修复** | 防止错误扩散 |
| **7** | **优先生成稳定断言** | 测试用例 Skill 的核心规则 |

**⭐⭐ 一条可直接用的原则**：
> **"全流程无人干预，比单点智能更重要；整条链路的容错能力，比每一步的最优答案更重要。"**
