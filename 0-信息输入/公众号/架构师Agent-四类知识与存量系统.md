# AI 创新实践｜「架构师 Agent」系统化落地

> **一句话结论**：**复杂系统真正重要的知识，并不完整地存在于代码中。**
> **"存量复杂系统"的困难，在于知识彼此断裂。**

---

## ⭐⭐ 一、核心现象：白纸 vs 旧城

> **"在 AI 的加持下，一名研发工程师可以用一周写出类似 Salesforce 的系统，实现大部分基础功能。
> 但如果让他在已有的 Salesforce 系统上做一个中等规模的 AI Coding 迭代，可能反而一周搞不定。"**

**⭐ 关键差别**：
| | 新系统 | 存量系统 |
|---|-------|---------|
| **AI 面对** | **一张干净的白纸** | **运行多年的城市** |
| **边界** | 可以新建 | 被路网、管线、旧建筑共同决定 |
| **历史包袱** | 少 | 一层叠一层 |
| **调整成本** | 可控 | ⚠️ 改一处可能动摇别处 |

**⭐⭐ 一个精准的比喻**：
> **"存量技术系统像一座运行多年的城市。路网、管线、旧建筑、临时改造和居民习惯共同决定了它今天的样子。**
> **你不能只看一条街上的建筑风格，就决定把地下管线挖掉；也不能只看到一个服务里的代码，就断定它拥有某项业务的最终决策权。"** ✅

---

## ⭐⭐⭐ 二、四类知识（**本文最有价值的框架**）

**大型分布式系统至少有四类知识同时影响方案设计**：

| # | 类型 | 内容 | 为什么代码里没有 |
|:--:|------|------|----------------|
| **1** | **业务知识** | 产品说"优化退款体验""增加人群投放" —— **业务对象、状态含义、边界和例外** | **"一个'订单'在不同团队的口语里，可能是交易单、履约单、支付单"** ⚠️ |
| **2** | **架构知识** | 请求经过哪些 BFF/领域服务/RPC/消息/异步任务？**哪些服务拥有数据主责，哪些只是聚合展示？哪里允许最终一致，哪里必须强一致？** | 代码只表达实现，不表达**职责边界** |
| **3** | **服务内部知识** | API 契约、领域对象、状态机、数据库、缓存、消息、定时任务、配置项、测试方式 | **"仅靠临时 grep，AI 可以找到一些相关文件，却未必知道哪个入口才是真的"** |
| **4** | **工程与组织知识** | 超时、重试、限流、灰度、发布、回滚、安全审批、监控规则 | **"这些往往不改变业务代码的表面逻辑，却直接决定方案能否上线"** |

**⭐⭐ 核心判断**：
> **"代码只表达了部分实现事实；文档可能表达了一部分设计意图；
> 配置记录了运行时行为；经验沉淀了大量没有写下来的约束。**
> ### **如果没有一套机制把它们组织起来，AI 就很难从一个 PRD 走到完整的技术方案。"**

---

## ⭐⭐ 三、AI 在存量系统里最典型的错：**局部正确、整体错误**

> **"AI 在复杂存量系统中最容易出现的错误，往往不是代码语法错误，也不是编译器或单测能直接发现的错误，
> 而是「局部正确、整体错误」："**

**表现**：
- 逻辑写在了**不该承担职责的服务里**
- 增加了一个**看似方便的同步调用**，却消耗了核心链路的（稳定性）
- 改了字段语义，但**下游异步消费方没同步**

**⚠️ 最要命的地方**：
> **这类错误单测发现不了、编译器发现不了、Code Review 也可能漏掉** ——
> **因为它"看起来对"** ⚠️

---

## ⭐⭐ 四、为什么"技术方案设计"是最关键的环节

> **"技术方案设计决定了需求应该落在哪些系统、改动应放在哪一层、
> 哪些能力可以复用、哪些约束不能突破，以及改完以后如何证明它仍然安全。"**

**⭐⭐ 一句极重要的话**：
> **"AI Coding 的效率会放大方案正确性，也会（放大方案错误）。"**

**⚠️ 行业现状**：
> **"技术方案设计仍是人工介入最深的环节之一，仍然是需要架构师强力介入的环节。"**

## 五、行业已有的三条路线（调研结论）

| 路线 | 代表 | 做法 |
|------|------|------|
| **① Spec-Driven Development** | GitHub Spec Kit / Kiro | **Spec → Plan → Tasks → Implement**，用结构化产物把需求、计划和任务串起来<br>**对复杂/陌生/高风险需求，建议保留阶段性审阅** |
| **② 长程 Agent 的 Harness** | — | 给 Agent 提供约束与环境 |
| **③ 系统理解** | 本文主张 | **让存量系统成为 AI 可理解、可推理、可验证的工程系统** |

## ⭐⭐ 六、对我们的直接启示（**跟我们工作台高度相关**）

| # | 启示 | 怎么用 |
|:--:|------|-------|
| **1** ⭐⭐⭐ | **四类知识 = 知识库的分类骨架** | 业务知识 / 架构知识 / 服务内部 / 工程组织 —— **比"按文档类型分类"有用得多** |
| **2** ⭐⭐⭐ | **"知识彼此断裂"是最好的问题定义** | 汇报时说"不是 AI 不聪明，是知识散在四个地方、彼此断裂" |
| **3** ⭐⭐ | **最大风险是"局部正确、整体错误"** | 评测要能发现"看起来对但位置错"的输出 |
| **4** ⭐⭐ | **技术方案是最该做 Skill 的环节** | 因为它决定"改哪一层、复用什么、不能突破什么" |
| **5** ⭐ | **AI 放大方案正确性，也放大错误** | 方案评审比代码评审更值钱 |

**⭐⭐ 一条可直接用于汇报的表述**：
> **"我们不是在教 AI 写代码，是在把散在四处的知识（业务/架构/服务内部/工程组织）
> 组织成 AI 能用的上下文 —— 因为存量系统的困难不在于难写，在于知识断裂。"**
