# 架构师 Agent（下）：技术方案设计落地与 Agent Runtime

> **本文是《架构师 Agent-四类知识与存量系统》的续篇/完整版**，重点讲**怎么落地**
> **一句话结论**：**技术方案设计不该是一次性的长提示词生成，
> 而是一套有输入、有检索路径、有验证和停止条件的推理过程。**

---

# ⭐⭐ 一、起点：白纸 vs 旧城（承接上篇）

> **"在 AI 加持下，一名研发工程师可以用一周写出类似 Salesforce 的系统，
> 但如果让他在已有的 Salesforce 上做一个中等规模的迭代，可能反而一周搞不定。"**

**四类知识再次被强调**（业务 / 架构 / 服务内部 / 工程组织），核心判断不变：
> **"存量复杂系统的困难不在于「代码太多」，而在于知识彼此断裂。"**

---

# ⭐⭐ 二、行业三条路线（他们调研后划的线）

| 路线 | 代表 | 做法 |
|------|------|------|
| **Spec-Driven Development** | GitHub Spec Kit / Kiro | **Spec → Plan → Tasks → Implement**，用结构化产物把需求、计划、任务串起来<br>Kiro 对复杂/陌生/高风险需求**建议保留阶段性审阅**，不直接执行 |
| **长程 Agent 的 Harness** | Anthropic | 只给高层目标不够，需要**初始化、任务拆分、结构化交接**，让后续会话知道前面完成了什么、还缺什么<br>→ 解决**长时间执行中的上下文连续性** |
| **Agent-friendly Repository** | OpenAI | ⭐ **"给 Agent 一张地图，而不是一千页说明书"**<br>短的 `AGENTS.md` 负责**路由**，结构化文档承载**事实**，CI 和自动化检查负责发现**知识陈旧、链接失效、结构漂移** |

**⭐ 他们对这三条的评价**：
> **"这些思路都很重要，也和我们的实践高度一致。
> 不过这些实践比较多的还是偏单个微服务系统内部，
> 对于跨复杂多系统的工业实践层面，并没有给出比较理想和细节的设计。"**

---

# ⭐⭐⭐ 三、最反直觉的设计：**为什么不首推 RAG**

> **"讨论知识库时，很多人的第一反应是 RAG：把历史 PRD、技术方案、会议纪要、接口文档、
> 复盘和 Wiki 都放进向量库，需要时检索 Top K 片段交给模型。
> RAG 很有用，但它不应该是复杂系统知识建设的第一选择。"**

## 三个具体问题

| # | 问题 | 说明 |
|:--:|------|------|
| **1** | **颗粒度不一致** | 一篇完整方案、一次会议纪要、一段接口说明、一个事故复盘截图，都可能成为检索单元，**知识密度差异很大**<br>"一个命中的片段看起来相关，并不代表它涵盖了这个问题真正重要的边界" |
| **2** | ⭐ **语义相似 ≠ 工程相关** | 用户说"订单取消"，检索能找到退款、履约、营销、风控里大量相似描述，<br>**却不一定找到"状态机不可跳转""某个 Topic 仍有历史消费者""这个接口只有聚合服务可以调用"这类决定方案正确性的约束** |
| **3** | **Top K 的完整性和结构性没有保证** | 返回的文档可能来自不同时间、不同业务范围，**甚至互相矛盾**<br>**"上下文越来越长，注意力却没有更集中，推理效率反而下降"** |

## ⭐⭐⭐ 他们给的第一性原理

> ### **"知识是有结构的，更适合被结构化的索引和理解。
> ### 信息（比如新闻类内容）是结构化松散的，更适合被平行/平铺化检索。"**

**⭐⭐ 这一条对我们的知识库设计是决定性的**：
> **业务规则、架构约束 = 知识 → 要结构化索引**
> **会议纪要、新闻、公众号文章 = 信息 → 可以 RAG 平铺检索**
> **⚠️ 我们之前默认"建个知识库就上 RAG"，这个默认是错的。**

---

# ⭐⭐ 四、蒸馏架构师大脑（具体做法）

**目标**：
> **"把架构师脑子里的隐性知识挖出来 —— 从而摆脱「技术方案必须依赖架构师的隐形知识才能产出」的魔咒。"**

**工具**：他们写了专门的 skill `business-knowledge-distill`
> 从技术方案设计文档、技术稳定性体系梳理串讲文档等**蒸馏成强结构化的 business-knowledge**
> ⭐ 而且会**下载并分析文档里的交互图**，一起转成结构化知识

**知识库目录结构**：
```
business/
├── index.md
├── meta/index.md
├── principle/          # 原则：超时、幂等、一致性、降级、兼容
│   ├── timeout.md  idempotency.md  consistency.md  degradation.md  compatibility.md
├── scenario/           # 场景
├── reference/          # 关联、引用内容
├── practice/           # 实践
└── history/            # 历史（history-YYYYMMDD.md）
```

**⭐⭐ 这个结构值得直接参考** ——
**按「原则 / 场景 / 实践 / 历史」分类，而不是按文档类型分类。**

# ⭐⭐⭐ 五、Agent Context 与 Runtime（**五层结构**）

> **"这些能力并不是彼此孤立存在的，整体分别作用于 Agent Context 和 Agent Runtime 调度 ——
> 也就是 Harness 阶段。"**

| 层 | 名称 | 载体 | 解决什么 |
|:--:|------|------|---------|
| **a** | **业务理解层** | KBase MCP | ⭐ **不是"AI 能否搜到某篇文档"，而是"设计之前 AI 是否已理解业务语义与领域上下文"** |
| **b** | **系统分析与探索层** | AITOM（API 检索、调用关系、链路追踪）| 从需求或业务入口出发，探索真实系统中的服务调用、上下游依赖、关键链路 |
| **c** | **架构推理层** | 技术方案设计 Skill | 定义 Agent 的工作方式：如何分析需求、逐步加载上下文、定位服务、验证方案完整性 |
| **d** | **服务知识层** | 各微服务的 Service Knowledge | 服务职责与能力边界、领域概念、API 与事件契约、数据模型、关键依赖 |
| **e** | **事实验证层** | Git Repository（Code Context）| 最终确认实现事实：代码、配置、API 定义、数据结构 |

**⭐⭐ 这五层可以直接当我们的架构图骨架**：
> **业务知识 → 系统分析 → 推理 Skill → 服务知识 → 代码回源**
> **注意最后一条：所有结论都要能回到代码这个"事实层"验证。**

---

# ⭐⭐ 六、六步推理过程（技术方案怎么生成）

| 步 | 动作 |
|:--:|------|
| **1** | 读取**通过准入的 PRD**，提取可验收目标、范围、**不做项**、风险和待确认信息 |
| **2** | 在业务知识库中解析**关键元语和场景** —— 先确认"需求说的是什么"，再确认"这些概念在哪些系统、接口、数据上实现" |
| **3** | 通过**架构图谱**定位候选服务和完整链路 —— 识别主路径、旁路、同步调用、异步事件、下游依赖、服务等级、**架构红线**（不是只找代码关键词）|
| **4** | 进入候选仓库，按任务类型读相应服务知识（新增 API→优先读契约/兼容策略；改库→优先读表语义/迁移规则/下游依赖），再**回源到当前 Git Commit** |
| **5** ⭐ | **形成 Gap 分析**：已有且语义一致→**复用**；已有但需扩展→明确**改造边界**；都没有→**新建**<br>**"Gap 分析强迫方案回答「为什么这样做」，而不是直接罗列文件改动"** |
| **6** | 生成完整方案：改动点、调用方影响、异常传播、兼容策略、测试矩阵、发布与配置动作、**需求覆盖矩阵**、知识库联动、待确认项 |

# ⭐⭐⭐ 七、渐进式上下文加载（和灵码那篇讲的是同一个概念）

> **"所有的结构化知识并不会在一次任务开始时全部加载到 Agent Context 中。"**
>
> **"如果一次性把所有业务知识、服务知识、代码和工具结果全部注入 Context，
> 不仅会造成大量无关信息干扰，也会增加上下文负担，降低推理质量。"**

**加载路径**：
```
技术方案设计 Skill
  → 需求理解
  → 按需加载业务知识
  → 定位相关业务场景
  → 调用 AITOM 分析系统与调用链
  → 按需加载相关 Service Knowledge
  → 发现信息缺口
  → 回源 Git Repository 验证代码与配置
  → 形成技术方案
  → 关键结论进行证据验证
```

**⭐⭐ 一句定性**：
> **"Agent Runtime 不是一个「预先加载所有知识的大 Prompt」，
> 而是一个能够随着任务推进，持续完成：
> 发现问题 → 判断当前缺少什么 → 定位信息来源 → 按需加载 → 更新上下文 → 继续推理 的动态运行环境。"**
>
> **"它追求的不是让 Agent 知道所有信息，
> 而是让 Agent 能以尽可能短、尽可能准确的路径，获得完成当前决策所必需的上下文和证据。"**

---

# ⭐⭐⭐ 八、方案完备度的六个维度（**可以直接当验收标准**）

> 目标："技术方案完善度达到 95% 以上"
> 前提：需求已准入、关键知识能回源、代码与配置得到核查、人工评审完成

| # | 维度 | 检查什么 |
|:--:|------|---------|
| **1** | **需求覆盖** | PRD 条目是否**逐项**归属为"做 / 不做 / 待确认" |
| **2** | **系统覆盖** | 涉及服务、仓库、配置、上下游、**范围外参与方**是否完整 |
| **3** | ⭐ **证据覆盖** | 关键结论是否能**回源**到业务知识、架构事实、代码、配置或已确认文档 |
| **4** | **风险覆盖** | 兼容、异常、灰度、缓存、消息、状态机、安全约束是否被检查 |
| **5** | **验证覆盖** | 单测、契约、回归、监控、发布、回滚是否清楚 |
| **6** | ⭐⭐ **不确定性治理** | **未知和冲突信息是否被显式登记，而没有被 AI 擅自补全** |

**⭐⭐ 第 6 条最值得学**：
> **"把它们压缩到少量明确的问题，而不是让它们以隐性风险的形式藏在方案里，已经是很大的进步。"**

**实际效果**：
> "体验站三期"需求，在原始需求完整度高 + 知识库完备的前提下，
> **AI Agent 原生设计的技术方案覆盖度可达 95% 以上**。
> 剩余不确定性来自跨团队决策、外部系统行为、数据口径和产品取舍 —— **本来就不该由模型单独决定**。

---

# ⭐⭐ 九、人的角色怎么变（一句到位）

> ### **"人不再是系统知识的唯一检索器，而是知识质量和决策权的最终负责人。"**

> **"当出现业务取舍、跨团队接口承诺、数据口径、合规要求或高风险变更授权时，
> AI 应停止猜测并发起明确的问题。人类介入的位置从「替 AI 收集所有资料」
> 转为「裁决事实缺口和承担关键决策」。"**

---

# ⭐ 十、知识库是全流程复用底座（不只服务写代码）

> **"技术方案设计是从需求向未来推演；线上排查是从现象向过去回溯。
> 两者都需要业务元语理解问题、需要场景映射找入口、需要架构图谱定位链路、需要服务知识检查状态机和降级逻辑。"**
>
> **→ 同一套知识体系，可复用于：研发调研、技术方案、代码修改、线上排查、事故复盘、新人理解系统。**

# ⭐⭐ 十一、对我们的用处

| # | 他们的做法 | 我们能用的 |
|:--:|-----------|-----------|
| **1** ⭐⭐⭐ | **不首推 RAG，知识要结构化** | ⚠️ **不要默认"建知识库=RAG"**；业务规则/架构约束按结构索引，会议纪要/文章才用 RAG |
| **2** ⭐⭐⭐ | **Agent Runtime 五层**（业务→系统分析→推理Skill→服务知识→代码回源）| 直接当架构图骨架；**所有结论都能回到代码验证** |
| **3** ⭐⭐⭐ | **渐进式上下文加载** | 和灵码那篇同一个原则 → demo 界面必须"逐层展开"，不预加载 |
| **4** ⭐⭐ | **完备度六维度** | 可直接改成我们的"PRD 质量验收表" |
| **5** ⭐⭐ | **不确定性治理：不能擅自补全** | demo 里 AI 遇到不确定必须停下提问，而不是自己编 |
| **6** ⭐⭐ | **Gap 分析（复用/改造/新建）** | 方案必须回答"为什么这样做"，不是罗列改动 |
| **7** ⭐ | **business/ 目录结构**（原则/场景/实践/历史）| 知识库分类方式可直接参考 |
| **8** ⭐ | **"人不再是知识的检索器，而是决策的负责人"** | 讲"人的价值在哪"的一句话 |

# 十二、一句话

> **这篇最颠覆认知的一条是"不首推 RAG"**：
> ### **知识是有结构的，应该结构化索引；信息是松散的，才适合平铺检索。**
> **我们如果默认"知识库=RAG"，方向就已经偏了。**
>
> **⭐⭐ 另外两个可直接用的**：
> **① Agent Runtime 五层（业务→系统分析→推理→服务知识→代码回源）**
> **② 完备度六维度，尤其第 6 条「不确定性治理：未知信息不能被 AI 擅自补全」**
