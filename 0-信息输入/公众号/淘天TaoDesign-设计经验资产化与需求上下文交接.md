# 一句话

**淘天做了一个 AI 原生设计工作台，它的价值不在"AI 能生稿"，而在三件事：把设计经验做成可调用资产、把需求上下文做成能交给下游的结构化信息、用双评测集让资产自我进化。一次生稿可用率 85%，但这只是入口。**

---

# 一、为什么值得看：它做的正是我们工作台要做的三件事

| 它做的 | 对应我们的 |
|--------|-----------|
| 设计经验 → 可调用资产（4 层） | 知识库怎么建 |
| 需求上下文 → 图结构 + 批注 → MCP 交付研发 | 工作台怎么把上下文传下去 |
| 双评测集 + 反馈 Loop → 资产自进化 | 怎么验证知识库有用 |

**⭐ 而且它的团队定位和我们一模一样**：
> 「团队致力于通过 AI 技术与工程化实践，解决电商业务在**需求表达、设计、研发和验收**等环节的交付难题。我们结合前沿技术与淘天实际业务场景，探索专业经验的沉淀复用与跨角色协作，**推动需求上下文在各环节准确传递**。」

# 二、起点：一个真问题，不是"用 AI 做设计"

**原文的痛点陈述**（这段可以直接用作我们方案的"必要性"表述参考）：
> 「面对不断出现的相似需求，同类页面需要反复制作，许多专业判断也得在不同项目里重新来过。」

**它定义的完整协作链**：
- **产品经理**：明确业务目标、用户任务、规则和边界
- **设计师**：落到 UI、多状态、交互流转和动效
- **技术**：评估能不能实现，处理多端一致、兼容性和工程约束

**⭐ 它抓的缺口**（这句话是全文的题眼）：
> 「**设计过程中形成的需求上下文经常在交接时产生损失或者歧义**，例如为什么会有这个状态、用户点完去哪、异常情况怎么处理，哪些约束已经确认过。」

**→ 所以工作台的定位是"把这些信息留下来，跟着设计稿一起交给研发"**，而不是"帮设计师画得更快"。

# 三、技术路线的两次选择（含失败复盘，比结论值钱）

## 第一次：MasterGo 插件路线 —— 效果卡在"跨表示层转换"

**做法**：模型生成受约束的 HTML + CSS → 工程化映射为画布节点

**两个映射难题及取舍**：

| 难题 | 试过的方案 | 结果 |
|------|-----------|------|
| **节点树映射** | ① 工具调用流（暴露创建/连接节点 API + Skill 引导）| ❌ 需注入大量工具声明和引导 Skill，**调用准确性差、推理耗时高、模型过度思考、复杂层级结构错乱** |
| | ② **中间结构转换**（HTML → Parser → 类 VDOM → 遍历转节点）| ✅ **采用**（生成效率 + 结构稳定性）|
| **样式映射** | ① 纯 CSS | ❌ 画布只支持 CSS 子集，**要写大量约束提示词，反而导致更多指令遵循失败** |
| | ② **Tailwind 原子类** | ✅ **采用**（约束天然内化、样式收敛在有限原子集合、可追溯性好）|

**⭐ 特殊节点**：引入类似 Web Components 的自定义标签 `<x-component props="foo">`，解析阶段还原为设计组件 + Variant 映射

**实际效果**：B 端 C 端一次生成可用率约 **85%**

## 第二次：自建浏览器画板 —— 因为"效果瓶颈正来自这层转换"

**它承认的根本矛盾**（这句话非常重要）：
> 「本质上，MasterGo 画布的表达能力与 Web 标准只是**一个交集**……这种**天然的双向不对等**，导致原本在浏览器里预览正常的 HTML 页面，置入画布后可能出现布局错乱（Grid 得降级用 Flex 模拟、background-repeat 在画布 API 里找不到对应项）。」

> 「模型输出规范与工程转换规则必须**双向迁就**，系统提示词过大导致生成时长、成本和**注意力漂移**——这些叠加的约束最终**拉低了模型生成的创意上限**。」

**转折点**：受 Claude Design 启发 —— 既然模型已经生成了符合 Web 标准的前端代码，**为什么不直接用浏览器引擎承载画板，让 HTML/JSX 直接成为可渲染的设计产物**？

**⭐ 一个关键的判断依据**（我们做工作台可以照抄这个逻辑）：
> 「设计师的**核心竞争力体现在审美把控和对业务需求的理解上，并不绑定在某一款具体的画图软件上**，大家对新工具形态的接受度比预想中更高。」

# 五、⭐ 最值得抄的设计：确定性优先 + Agent 兜底（双流水线）

**画布上的一切操作最终都要落实到源码。它用两条并行流水线**：

## ① 确定性源码处理（优先，不调用大模型）

```
画布操作 → 待应用修改队列
       → 按操作顺序和目标文件分组归并
       → 基于最新源码做「规则精准定位 + 冲突检测」
          （检查 HTML/JSX 节点结构与文本状态是否变了）
       → 可靠且无冲突 → 生成确定性 Diff Patch → 合成新文件
       → 完全工程逻辑执行，秒级生效
```

## ② Design Agent（模型兜底）

```
复杂结构调整 / 定位失败 / 修改冲突
→ 无缝分流给 Design Agent
→ 结合当前源码 + 用户修改意图，重新规划 UI 结构
```

**⭐⭐ 这个设计对我们直接可用**：
**凡是有确定规则能做的，不要交给大模型；只有规则解决不了的才给 Agent。**
省 Token、省时间、结果还更稳。

**另一个可直接抄的**：**异步快照 + 安全回滚**
- 每轮会话流结束时，后台 Worker **异步**触发 Checkpoint，持久化不可变文件 + Manifest
- **与客户端完全解耦，主链路零阻塞，用户无感**
- 回滚时：校验幂等 Key + 基线版本 → 沙箱租约与互斥锁**阻断并发写** → **回滚前先自动建一个安全 Checkpoint**（防误操作）→ 按 Manifest 还原 → 清缓存 → 推前端刷新

# 六、⭐⭐⭐ 资产化：设计经验怎么变成 Agent 能用的东西

## 6.1 为什么必须自建（这段可以直接引到我们方案里）

> 「**企业内部的业务场景，外部世界是无法感知的。** 比如同样是做一张千牛（淘宝商家后台）的大促报名或信息展示页面，**只靠外部公开的大模型，根本不可能知道背后隐含的业务背景、特定设计规约和组件用法等私有信息**；哪怕同样是做商品页面，信息层级怎么排、价格怎么表达、视觉密度定多高，也都要结合具体业务线来判断。**公开模型能写出页面代码，但并不清楚某条业务线为什么要这样设计。**」

## 6.2 ⭐ 资产四层抽象（结构与我们的知识库高度对应）

| 层 | 内容 | 对应我们的 |
|:--:|------|-----------|
| **视觉规范** | Design Token + 基础规范（色彩、字号、间距、圆角）| 术语表 / 字段规范 |
| **复用结构** | 业务组件、典型布局、页面模板 | PRD 模板 / 场景规则 |
| **静态资源** | 业务专属图片、图标、字体 | 原始文档附件 |
| **业务知识** | **特定业务场景的交互规则、文案口径、边界约束** | **业务域 + 智能推理域** |

**⭐ 它的方法论点**：
> 「要让设计经验既能被系统管理，又能被 Agent 稳定调用，**第一步必须先建立统一的技术抽象**——让后续的**录入后台与前台消费链路都建立在同一套数据结构之上**。」

**→ 这和领导说的「第一期就整一块地方，把文档都丢进去，分好目录分好类」是一致的：**
**先有结构和分类，再谈检索。**

## 6.3 风格录入：人工兜底 + AI 蒸馏（两步走）

**第一步：人工录入 + 管理后台**（规则录入、版本管理、权限控制、前台消费全链路）

**第二步：AI 风格蒸馏**（这个设计的巧思值得学）
> 「纯靠人工从零编写规范成本很高，而且**很多专业判断已经融入日常创作，设计师一眼能看出方案合不合适，却未必能把背后的适用条件完整写出来**，不同人写出的规范在粒度和完整性上也差异很大。」

**做法**：
```
设计师提供：成品设计稿 + 已上线页面 + 既有规范 + 业务知识
      ↓
Agent 分析整理设计规律 → 生成结构化候选风格初稿
      ↓
设计师确认和澄清边界  ← ★ 关键在这里
      ↓
正式发布写入版本库
```

**⭐ 它需要设计师澄清的边界长什么样**（这个例子极好）：
> 「**某种颜色究竟是业务常驻强调色，还是单次活动的主题色；某种紧凑布局适用于哪些页面。**」

**→ 对我们的启发**：
**AI 能从材料里归纳出规则，但"这条规则在什么条件下适用"必须由人补。**
这正是我们知识库里那 60 项「待验证」和 5 处「口径冲突」要解决的事。

## 6.4 ⭐ RAG 踩过的坑（我们一期就会遇到）

**原文**：
> 「最初设计规范和组件是以 **Reference 文件的形式散落在 Skill 的目录树里**，虽然这样解决了**渐进式披露**的问题，但是会**让 Agent 沿目录逐层查找，很容易漏看其他分支文件夹的内容，甚至误以为规范不存在**。」

**→ 结论**：把检索**收敛到统一的知识工具**，Skill 只负责指导生成逻辑，知识工具专门承接召回。

**⭐⭐ 而且它明确指出设计规范类知识和普通问答不一样**：
> 「不同于普通问答场景只做切片和相似度匹配，设计规范包含**大量默认值、使用前提、状态联动与页面模板约束**，一旦在召回或压缩时**丢失条件**，生成的页面就会变形。」

**→ 这条直接对应我们领导说的「RAG 一期不一定合适」** —— 条款式、带条件的业务规则，切片+相似度会丢条件。

## 6.5 ⭐⭐⭐ 四个迭代方向 + 每一轮的真实数据

这是全文对我们最有价值的部分：**它把 RAG 优化拆成了四步，每步都有数据，包括失败**。

### 迭代 ①：统一入口与批量召回

**做法**：Agent 把当前任务的多个知识需求**合并成一次批量请求**，工具内部并发召回；页面模板结合真实目录 + 用户需求自动匹配，按 pageId 去重

**数据**：
| 指标 | 优化前 | 优化后 |
|------|-------|-------|
| 知识工具累计调用 | 40+ 次 | **10+ 次** |
| 直接返回字符数 | 60+ 万 | **< 10 万** |
| 紧接模型回合累计 Token | — | **减 3 成** |

**⚠️⭐ 但它诚实报告了失败**：
> 「**设计师盲评均分基本持平，且有几个样本出现降分** —— 说明**单纯把返回内容压小，并不能保证关键约束被有效保留**。」

### 迭代 ②：结构化提取 + 代码组装

**复盘降分样本发现**：
> 「直接让模型对多份文档做**自由摘要**，很容易在压缩过程中把**组件默认值、适用边界和状态联动**一起抹掉，导致'**摘要读起来没错，页面却做错了**'。」

**改法**（关键：不让模型自由改写）：
```
按文档来源和 Markdown 结构分段，最多 6 路并发提取
→ 明确保留：默认值 / 适用范围 / 例外情况 / 状态联动
→ 结合当前任务筛选适用条目
→ 单独标出「模板默认行为」与「用户需求」的冲突
→ 最终由【确定性代码】组装成实现说明
```

**数据**：设计师盲评均分 **3.xx → 4.xx（5 分制）**，主 Agent Token 再减一成以上，平均总耗时大幅下降

**⭐⭐ 我的判断**：
**"自由摘要会抹掉条件" 这件事，和我们在 PRD 上遇到的问题完全同构。**
所以我们的知识库检索也不能用"总结一下这几页"，而要用**结构化的条款提取 + 标记适用范围**。

### 迭代 ③：离线提取 + 在线选择（**这条最值得抄**）

**动机**：
> 「每次任务都重新对稳定文档做分块提取，不仅把**理解成本拖进了用户的在线等待路径**，也无法消除分散在组件说明与页面规范中的**重复规则**。」

**分工**：
| 阶段 | 做什么 |
|------|--------|
| **离线**（文档发布/更新时） | 完整提取规则、数值、条件、例外和来源 → 存为**带版本与内容指纹的知识单元**<br>按风格/类型/约束强度**分桶**<br>用 Embedding 发现**跨文档重复规则** → 模型提合并方案 → **独立审核**后入库 |
| **在线**（任务执行时） | 只做四件事：**召回候选 → 筛选适用条目 → 复核遗漏 → 隔离冲突**<br>遇到版本变化或知识缺口才补读原文 |

**⭐ 重复规则合并效果**：手淘资料中共合并生效 **60% 左右的组数**

**⭐⭐ 数据（这个提升幅度很大）**：

| 生成模型 | 每任务知识工具总耗时 | 平均整页生成耗时 | 设计师评分（5分制） |
|---------|-------------------|----------------|-------------------|
| 某 SOTA **Pro** 模型 | **约 2 分钟 → 20 秒** | 下降 **约 8pt** | 原 4+ 分基础上 **+5pt** |
| 某 SOTA **Flash** 模型 | **1.5 分钟 → 20 秒** | 下降 **约 15pt** | 原 4+ 分基础上 **+4pt** |

**质量提升主要集中在规则更复杂的 C 端场景，B 端整体保持稳定。**

### 迭代 ④：引入专用决策模型（Decision Models）

**问题**：在线阶段的核心动作变成了"从有限候选中筛选适用知识、复核遗漏并判断冲突"——**继续用通用文本生成模型做这类高频结构化判断，延迟和成本依然偏高**

**做法**：用**专用决策模型**承接在线知识选择

**数据**（10+ 页面 / 20+ 批知识 / 30+ 历史版本，每组 307 次请求）：
- 单次调用中位耗时：**4.xx 秒 → 2.xx 秒**
- 关键检查点覆盖率：**+2pt**
- 知识包达标任务数：**+3 成**

**配套两条工程约束**：
1. **强制校验至少读取过一个对应业务风格**
2. **HTML 渲染完成后，基于 DOM 与视觉上下文的偏差自检**

**⭐⭐ 我的判断（对我们最有用的三条）**：
1. **离线做理解，在线只做选择** —— 这是把"读文档"的成本从用户等待路径里挪走
2. **不让模型自由摘要** —— 结构化提取 + 确定性代码组装
3. **专用小模型干高频结构化判断** —— 不必每次都上大模型

# 七、⭐⭐⭐ 评测体系（我们最缺的一块）

## 7.1 两个评测集

| 类型 | 来源 | 用途 |
|------|------|------|
| **标准评测集** | 设计师**录入**，覆盖不同业务线典型场景 | 观察整体生成效果 + **版本更新后的回退情况** |
| **TC 评测集** | 来自**真实使用过程中暴露的问题样本** | 复现和修复具体 Bad Case |

**⭐ 注意这个双层结构**：一个管"别退步"，一个管"修具体病"。
**我们做知识库评测，也应该这么分。**

## 7.2 离线评测流水线

```
自动化流水线批量生成产物
  → LLM-as-Judge 机器打分
  → 设计师人工评审和标注
  → 设计师判断既用来定位问题，也用来【反向校准机器评测的打分规则】
```

## 7.3 ⭐⭐⭐ 全文最狠的一条：高机评分 ≠ 业务可用

**原文**：
> 「在实际运行中，机器打分和设计师的判断**并不总是对齐**。比如在之前的 B 端评测里，有些稿件**机器打分不错、第一眼观感也过得去，但设计师细看就会发现里面的业务设计组件被模型擅自改写了**，在真实业务里根本没法直接用，最终被判定为**不可用**。」

> 「这也说明**高机评分不等于业务可用**，评测必须**重点检查模型有没有如实保留业务要求的组件和细节**。」

**⭐⭐ 这直接对应腾讯那句「失败不可见」**：
- 腾讯：覆盖率看板把「采集失败」和「没有数据」显示成同一个 0%
- 淘天：机器评分把「擅自改写」显示成「看起来不错」

**→ 同一个病：评测只测了"看起来对不对"，没测"是不是按我要求做的"。**

## 7.4 ⭐ 问题归因分两条路（这个分流逻辑太实用了）

拿到评测样本后，结合「原始需求 + 生成产物 + Agent 执行记录 + 设计师标注」做归因：

| 归因 | 判定 | 修复方向 |
|------|------|---------|
| **工程与调用问题** | **规范本身已经写得很清楚**，但 Agent 没有正确召回、漏读或执行偏了 | 回到**召回工具与生成校验**环节修复 |
| **资产本身的问题** | **规范缺失或表述含糊** | 进**资产修订流程**：AI 辅助归纳问题 + 提候选方案 → 设计师确认适用范围和修改内容 → **重新跑一轮回归评测** |

**⭐⭐ 我的判断**：
**"是查不到，还是知识库里本来就没有"——必须先分清。**
不分清就会犯两种错：
- 该补知识库的时候去调 prompt
- 该调检索的时候去改知识库

## 7.5 在线反馈提取（两条线索源）

| 线索源 | 做法 |
|--------|------|
| **用户主动反馈** | 点踩后后台**直接关联当次任务的 Session Trace** 录入评测集；定时任务巡检捞出异常任务 |
| **Agent 批量分析线上会话** | 利用用户输入里的**情绪信号**捕捉潜在问题，经聚合去重后再**人工核对** |

**⭐ 它自建的 Trace 能力**（我们工作台应该同步规划）：
> 「自建的 Agent 执行采样和基于 **OpenTelemetry** 的 Trace 格式已经完整记录了 **LLM 调用、Tool 执行、Reasoning、子 Agent 派发、用户输入**等完整调用链，能帮我们把反馈**精准还原到当时的需求、产物和生成步骤上**。」

## 7.6 ⭐⭐⭐ 为什么情绪信号必须人工核对（这段判断很成熟）

> 「之所以必须人工核对，是因为**情绪信号只能提供线索**，同样是一句带有不满情绪的修改要求，可能是**生成质量确实不行**，但也可能是**用户临时改了需求、个人审美偏好不同，或者是底层工具执行超时失败**，必须结合完整上下文才能分清。」

**沉淀后分两个方向**：
1. **提炼出的共性设计问题** → 整理成**候选风格优化建议** → 设计师拍板是否纳入正式资产
   ⚠️ **「避免把单次会话里的个人偏好直接当成通用规范写进资产库」**
2. **确认有代表性的真实失败场景** → 补充进评测集，固定下来供后续版本反复回归

**⭐ Loop 里的三方分工**（这个分工和我们「三方分工」的判断完全一致）：
| 角色 | 负责 |
|------|------|
| **AI** | 辅助分析样本、归纳共性问题、起草修改建议 |
| **设计师** | 判断规则合不合理、能不能推广 |
| **评测流水线** | 检验修改前后的实际效果 |

# 八、⭐⭐⭐ 需求上下文交接（工作台的核心价值）

## 8.1 传统交接丢了什么（这段几乎是我们方案的现成论据）

**案例**：营销商家端「价格力弹窗」需要增加淘金币策略调整入口，点击后弹二次确认；**商品是否设置了优惠，对应不同的弹窗形态和交互流程**。

**缺口**：
> 「研发**只看静态页面，很难直接推导出背后的业务触发条件**，比如两种弹窗各自在什么前置状态下出现、用户点确认或取消后去往哪里、空态或接口报错时怎么处理。过去这些信息要么**靠口头沟通**，要么**散落在 PRD 各处**，一旦交接时漏掉，下游就得反复找人澄清，**甚至写完代码提测了才发现漏了状态，只能返工重来**。」

## 8.2 解法一：图结构组织多页面状态、多流程分支

- 同一业务页面的不同状态 → **关联分支**
- 补充状态时，Agent 针对新增状态**装配对应的业务语境**，同时**锁定修改范围之外的已有元素**
- 页面与页面、状态与状态之间的流转关系 → 底层用**点（Node）和边（Edge）构成的图结构**描述
- 画布和全景视图解析后自动计算布局与连线

**⭐ 多态协议**：`{ name, pageId, polymorphs: [{ description, nodeXPath, scope, variants: [{ condition, uiDescription, pageId, nodeXPath }] }] }`
→ **一个模块，按条件切不同形态，每个形态都带 condition + 描述 + 精确节点位置**

## 8.3 解法二：批注与源码分离，基于 XPath 挂载

```
XPath 定位页面中的具体 DOM 节点
→ 把说明单独存为 JSON（不写进源码）
→ 渲染时前端借 DOMRect 获取元素实时位置，计算悬浮框坐标
→ 批注能跟着响应式布局自动对齐
```

## 8.4 解法三：通过 MCP 向研发下游交付

> 「下游的编码 Agent 可以通过 **MCP 或 OpenAPI 按需读取目标设计产物、节点批注和页面关系图**，再结合业务仓库、接口与数据约束完成实现。**TaoDesign 负责把设计表达和交互上下文交接清楚，具体的技术方案、代码编写、测试与部署，依然交由既有的业务研发平台承接。**」

**⭐ 边界划得很清楚**（这一点我们要学）：
> **它只做"交接清楚"，不接管研发**

**当前状态**：研发平台已通过 MCP 跑通**取包、产物合并、静态托管与知识库归档**，并支持**将上下文关联进 PRD 供后续澄清与生码使用**

## 8.5 ⭐ 设计验收：直接拿确认结果当共同依据

**查四项**：
1. 视觉有没有还原
2. **状态分支能不能按条件触发**
3. 流转路径对不对
4. 异常处理有没有生效

**两条走查路径**：
- **人工走查闭环**：人工对比预发页与设计稿，在线圈选差异，提交 PASS/NOPASS + 原因，未通过直接退回
- **自动化走查接入**：高频标准场景用静态截图比对 + DOM Diff + 动态数据模拟

## 8.6 ⭐⭐⭐ 验收不一致先分来源（这条最值得学）

> 「如果验收发现不一致，会**先区分问题来源**：
> - 属于**实现偏差**的，带上具体状态、复现条件和期望表现**退回研发修复**；
> - 属于**前期需求有歧义**的，**先退回工作台把设计说明澄清清楚**，再同步更新代码实现与验收基准，**避免出现口头改了代码、设计上下文却没更新的脱节情况**。」

**⭐⭐ 这个分流的价值**：
**它防止了"口头改了代码、上下文没更新"这种最隐蔽的技术债。**

# 九、⭐ 它自己承认的三条边界（诚实，可引用）

> 「在实际探索中，我们也看清了当前方案的几处明确边界：」

| # | 边界 | 原文 |
|:--:|------|------|
| **1** | **专业画板的往返转换仍有损耗** | 跨格式导入导出很难完全无损，复杂异形图层、动态交互转静态矢量图层，仍需取舍或人工二次修复 |
| **2** | **资产修订离不开人工判断与回归验证** | 「无论是从作品中蒸馏规则，还是根据线上反馈修补资产，**AI 目前承担的主要是归纳和起草工作**；一条规则到底通不通用、会不会影响其他场景的体验，**依然依赖设计师的专业判断与回归评测**」 |
| **3** | **动态场景的自动化走查还在持续磨合** | 静态页面样式比对相对容易，但强依赖动态接口数据和复杂前置状态的真实电商页面，端到端自动交互走查还需更深入工程联调 |

**⭐ 结论句**：
> 「因此，**复杂体验的把控、业务意图的决策以及关键质量节点的确认，依然需要专业人员留在回路中。**」

# 十二、⭐⭐⭐ 对我们工作台的 7 条直接可用判断

## ① 我们的"必要性"表述可以直接借用它的框架

**不要说"AI 提效"，要说**：
> 需求上下文在交接时产生损失或歧义 —— 为什么有这个状态、用户点完去哪、异常怎么处理、哪些约束确认过。
> 工作台的作用是**把这些留下来，跟着产物一起交给下游**。

## ② 资产四层可以直接映射到我们的知识库

视觉规范（术语/字段）→ 复用结构（模板/场景规则）→ 静态资源（原始文档）→ **业务知识（交互规则+文案口径+边界约束）**

**这套分类比我们现在"00-总览/01-业务域/02-智能推理…"更贴业务消费视角。**
现在我们是"按知识来源分"，它是"**按被消费的方式分**"。

## ③ 我们一期就会踩它的 RAG 坑 —— 而且已经被证实

> **「规范散落在 Skill 目录树里 → Agent 沿目录逐层查找，很容易漏看其他分支，甚至误以为规范不存在」**

**→ 所以知识库必须有 index 汇总 + 统一检索入口，不能只靠目录树。**

## ④ ⭐ 最关键的一条：不要让模型自由摘要业务规则

> **「自由摘要很容易在压缩过程中把组件默认值、适用边界和状态联动一起抹掉，导致'摘要读起来没错，页面却做错了'」**

**→ 我们的知识库消费方式应该是：**
**结构化提取（保默认值/适用范围/例外/联动）→ 确定性代码组装 → 不让模型二次改写**

**这条直接支持领导「RAG 一期不一定合适」的判断。**

## ⑤ 离线做理解、在线只做选择

**2 分钟 → 20 秒，评分还涨了 4-5pt。**
**→ 知识库的"读懂"应该在文档入库时完成，任务执行时只做召回+筛选+复核+隔离冲突。**

## ⑥ 评测必须分"标准集"和"TC 集"

- 标准集：**防退步**
- TC 集：**修具体病**

**而且必须检查"有没有如实保留业务要求"，不只是"看起来对不对"。**
**→ 高机评分 ≠ 业务可用。**

## ⑦ 验收不一致要先分来源

- **实现偏差** → 退回研发
- **前期需求有歧义** → **先退回工作台澄清，再改代码**

**→ 不分清就会出现"口头改了代码、上下文没更新"的技术债。**

# 十三、它还给了我们一个"要不要做画板"的答案

**它两次选择画板路线的判断逻辑，可以直接用在我们"要不要自建界面"这个问题上**：

| 它的判断 | 对应我们的 |
|---------|-----------|
| 插件路线：复用了专业编辑能力，但**引入跨表示层转换损耗，效果瓶颈正来自这层转换** | 如果在现有系统上做插件，会受现有数据模型限制 |
| 自建路线依据：**"设计师的核心竞争力不绑定在某一款画图软件上"** | **"产品经理的核心竞争力不绑定在某个现有系统上"** |
| 自建画板的功能取舍：**"常规设计不出端、单次生成高还原度"** —— 只支持高频微调，复杂重排交给 AI，极端场景导出兜底 | **工作台的功能边界也应该这么定：常见路径不出工作台，复杂情况退回原工具** |

# 十四、一句话记住它

> **TaoDesign 真正的贡献不是"AI 能生稿 85% 可用"，而是它证明了：**
> **① 企业私有知识必须自建，外部模型不知道为什么这么做**
> **② 知识消费不能让模型自由摘要，会丢条件**
> **③ 上下文要结构化到能交给下游（图结构 + XPath 批注 + MCP）**
> **④ 评测要能区分"查不到"和"本来就没有"**
> **⑤ 人的位置在判断，不在执行**
