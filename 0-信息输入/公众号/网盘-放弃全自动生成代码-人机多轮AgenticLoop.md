# 我们放弃了"全自动生成代码"

> **一句话结论**：
> ### **"全自动最大的风险，不是它会犯错，而是它错了还在自信地往前跑。"**
>
> 网盘团队把 Coding Agent 接进真实研发链路后，从**一次性全自动流水线**
> 转向 **Agentic Engineering Loop（人机多轮反馈循环）**。

---

# ⭐⭐⭐ 一、最核心的判断（全篇最值钱）

> ### **"全自动流水线把「不确定」当成「确定」一路往下传，
> ### 而错误偏偏会在最贵、最靠后、最难定位的地方才冒出来。"**

**他们的原始五阶段流程**：
```
需求规格 → 技术设计 → 任务拆分 → 代码生成 → 质量检查
（每阶段自动接上一阶段产物，中间没有确认关键假设的节点）
```

**问题**：
> **"只要上游产物里混进了没验证的判断，这种一路传递就会把偏差带到后面。"**

**真实表现**：
- 需求做到一半，被还没就绪的服务接口卡住
- **任务走完了所有阶段，代码却建在一份没人确认过的需求理解上**
- 等到验收才发现对不上，只能回头返工
- **过程记录一旦不全，连偏差最早在哪一步跑偏的都说不清**

**⭐ 他们想明白的一句话**：
> **"能不能生成代码，其实不是最难的；
> 难的是让它在真实、复杂、一直在变的研发环境里，靠可靠的上下文把活干对。"**

---

# ⭐⭐⭐ 二、真实迭代暴露的七类问题

## A 类：执行过程 —— 看不见、难追溯

| # | 问题 | 具体表现 |
|:--:|------|---------|
| **1** | **上下文堆起来，关键事实难保持一致** | 字段引用错、接口判断失准、**把早期的推断当成确定事实继续用**<br>**"光是把上下文喂得更多并不解决问题，还得把事实、约束和待确认项分清楚"** |
| **2** | **偏差出现时缺少定位抓手** | 运行记录只留各阶段结果，排查的人无法还原"当时用了哪些输入、做了哪些判断"<br>→ 只能扩大排查范围，或干脆重跑一遍 |
| **3** | **执行状态没有统一视图** | 任务进度、卡在哪、质检结果、模型资源消耗分散在各处<br>→ 研发难判断该不该介入，团队复盘没有共同依据 |

## B 类：任务输入 —— 信息和依赖不到位

| # | 问题 | 具体表现 |
|:--:|------|---------|
| **4** ⭐ | **需求描述有歧义** | 一句话需求 / 不完整产品文档，既没写清业务口径，也没覆盖异常分支和验收标准<br>⚠️ **"要是 Agent 自己把空白补上，而后面的设计和测试又都沿用这同一套理解，就会出现实现和测试彼此自洽、却整体偏离业务目标的情况"** |
| **5** | **存量经验还没显式化** | 历史代码为什么这么设计、有哪些兼容要求、团队约定 —— 部分还装在研发脑子里<br>→ **"写出来的实现可能局部逻辑没错，却漏掉了系统长期演进中沉淀下来的约束"** |
| **6** ⭐ | **知识图谱覆盖不全** | 自动检索受制于覆盖面、更新及时性、关联完整性<br>⚠️ **"没检索到相关约束，不等于约束不存在。"** |
| **7** | **外部依赖会直接把执行卡住** | 部分接口没就绪或状态不稳定，流程没法做真正验证<br>**原来的实现缺少足够的暂停、恢复和替代验证手段**，一处阻塞拖累整条链路 |

**⭐ 第 4 条和第 6 条最值得记** —— 它们解释了"为什么 AI 生成的东西看起来都对，但整体是错的"。

# ⭐⭐⭐ 三、重新划分三方分工

| 谁 | 管什么 | 边界提醒 |
|:--:|-------|---------|
| **脚本 + 质量门禁** | **路径、分支、编译、校验、日志上报** —— 有明确规则可查的事 | ⚠️ **"这些检查结果也受规则本身是否正确、测试覆盖够不够、执行环境稳不稳定的影响，不能拿来当完整的业务验收"** |
| **Agent** | **组织分析和执行**；把证据理清楚、把候选方案摆出来 | 在有分歧的地方不自己拍板 |
| **人（研发 + 业务责任人）** | **需求口径、方案取舍、历史兼容、体验好坏** —— 要结合业务背景拿主意的事 | **"人只在重要决策节点上介入，范围清楚的常规执行还是自动往前推"** |

**⭐⭐ 这个三分法比"人机协同"四个字有用得多** ——
**它明确了：能被检查的交给门禁，需要判断的交给责任人，中间的交给 Agent。**

# ⭐⭐⭐ 四、Agentic Engineering Loop 具体怎么转

**保留了 Spec-Driven Development 的核心**：先把目标、约束和验收标准定清楚，再组织实现和验证。

**一轮循环**：
```
观察 → 决策 → 修改 → 验证 → 复盘
```
> "看当前的代码和反馈，定下这一轮要达成什么，在边界内动手改，
> 跑对应的检查，再根据结果决定下一轮。
> **等满足验收条件，交给研发人员反馈确认，这才算交付完成。**"

## ⭐⭐ 但他们很清醒地补了一句（这点很难得）

> **"这里变的是工作的组织方式，并不是说「循环天生就比流水线好」。
> 一条完善的流水线一样可以有反馈、有可观测；
> 反过来，换成主 Agent 来协调，也不会自动把长上下文的问题解决掉 ——
> 事实来源、任务边界、每一轮需要哪些信息，这些照样得管。"**

**→ 关键不是"循环 vs 流水线"，是"要不要把不确定性显式处理"。**

# ⭐⭐⭐ 五、执行前的需求调研（**这套做法最值得抄**）

> **"多轮反馈要真起作用，得先有一个能讨论、能验证的起点。
> 输入里的关键歧义要是没澄清，循环也可能围着一个错误前提反复打转。"**

## 调研产出四件东西

```
业务描述 → 目标 / 工程约束 / 改动范围 / 验收标准
```

## ⭐ 调研不只是梳理文字，还要"对真实实现"

| 动作 | 说明 |
|------|------|
| 找相关**文件和调用关系** | — |
| **顺着提交历史理解当初为什么这么设计** | ⭐ 这是知识库很难自动补的部分 |
| 核对可能的原因 | — |
| **划清哪些范围要改、哪些行为必须保持不变** | 不变项比改动项更重要 |
| **拆成一个个能独立验收的单元** | — |

## 三个细节机制

1. **需求、验收标准和改动计划各自编号** —— 方便在实现和验证时一一对上
2. ⭐⭐ **"暂时确认不了的信息，先挂成待确认项，而不是直接当成实现前提写进去"**
3. **研发负责把业务目标和现有系统约束对齐；Agent 在划好的边界里继续分析和执行**

**⭐⭐ 第 2 条是关键** ——
**这跟腾讯 OK 平台的「待确认问题收口区」、阿里架构师 Agent 的「不确定性治理」是同一件事：
不确定的东西必须显式登记，不能让 AI 自己补。**
**三个独立团队得出同一个结论，说明这是硬规律。**

# ⭐⭐ 六、可观测：让执行过程看得见、可回溯

**机制**：本地执行通过上报机制，把每一轮的事件、指标和迭代记录汇到远端平台。

**结构化记录四类**：**运行 / 任务 / 事件 / 产物**

**看板展示**：任务阶段、执行耗时、**token 消耗与成本**、**质量门禁结果**、**上下文占用**

## 三个层面的价值

| 层面 | 价值 |
|------|------|
| **执行过程** | 落进日志和看板，复盘时每一步都能回看 |
| **交付结果** | 沉淀成产物和报告，出了问题能追回源头 |
| **记录攒下来** | 形成趋势，慢慢就成了团队的经验资产 |

## ⚠️ 一个非常关键的提醒

> ### **"把执行完成、检查通过、业务验收通过这三件事分开看，
> ### 别拿其中一个状态当成交付结论。"**

**⭐⭐ 这直接对应腾讯那句"覆盖率看板把采集失败和没有数据显示成同一个 0%"** ——
**都是「状态被混淆」的问题。**

# ⭐ 七、现状（他们自己承认的边界）

## 已经跑起来

- 需求进循环之前，先做一遍**证据化的成熟度打磨**
- 把一次性全自动，改成了**人机多轮、随时能停下来纠偏**的循环
- 执行过程能上报到平台、看得见，也能回头复盘

## 还没解决

- 需求相关**知识图谱覆盖还不全**，Agent 检索能力被这个卡着
- 一部分依赖的**服务接口后置**，仍是瓶颈
- **把存量经验沉淀成可复用的能力（Skills），还在慢慢攒**
- **"自动化程度"和"可控性"之间的平衡点，还在不断调**

**⚠️ 而且他们主动声明**：
> "这里讲的是能力建设的进展，**不等于已经量化验证过的效率收益**。"

---

# ⭐⭐ 八、结语里最该记的一段

> **"这次调整，把我们的关注点从「生成一次代码」拉到了整个交付过程上。
> 需求理解得准不准、改动有没有越界、验证能不能撑住结论、出了问题能不能回溯 ——
> 这些才是自动化能不能真正发挥价值的前提。"**

> **"需求确认、分轮验证、过程记录这些确实会多花一些功夫，
> 值不值得，得放到完整的交付周期里看。"**

**三方分工的最终表述**：
> **Agent 负责组织分析和执行，工程工具落实那些能被检查的规则，
> 研发和业务责任人确认关键的取舍与验收结果。**

# ⭐⭐⭐ 九、对「研发工作台」设计的直接帮助

| # | 他们的结论 | 对工作台的设计含义 |
|:--:|-----------|-------------------|
| **1** ⭐⭐⭐ | **"不确定项必须挂账，不能当实现前提"** | demo 里必须有「待确认项」这一块，而且**要阻止流程继续往下走** |
| **2** ⭐⭐⭐ | **"实现和测试彼此自洽，却整体偏离业务目标"** | demo 要展示：AI 的每一轮产出**都要回对业务目标**，不是自证正确 |
| **3** ⭐⭐⭐ | **三方分工（门禁/Agent/责任人）** | 工作台的角色定义可以直接用这三类，比"人机协同"具体 |
| **4** ⭐⭐ | **"没检索到 ≠ 不存在"** | 知识库要显示**覆盖率**，而不是默认"没查到就是没有" |
| **5** ⭐⭐ | **"执行完成 / 检查通过 / 业务验收通过"三态分开** | demo 里的状态机至少要有这三个状态，不能一个"完成"了事 |
| **6** ⭐⭐ | **"暂停、恢复、替代验证手段"** | 对应百炼的 Session 可中断/续跑 —— **外部依赖没就绪时能挂起而不是失败** |
| **7** ⭐ | **"顺着提交历史理解当初为什么这么设计"** | 知识库里"为什么"比"是什么"更难补，也更有价值 |
| **8** ⭐ | **"循环不比流水线好，关键是有没有显式处理不确定性"** | 讲方案时别说"我们用了多轮循环"，要说"我们怎么处理不确定" |

# ⭐ 十、一句话

> **这是目前看到的对"AI 原生研发"最清醒的一份复盘** ——
> **它没有吹全自动，而是承认了"全自动会把不确定当确定一路传下去"。**
>
> **⭐⭐ 三个可以直接用的**：
> **① "不确定项挂账"（三个团队独立得出同一结论：腾讯、阿里、网盘）**
> **② 三方分工：能被检查的给门禁，需要判断的给责任人，中间的给 Agent**
> **③ 执行完成 / 检查通过 / 业务验收通过 —— 三个状态必须分开**
>
> **⭐⭐⭐ 而最该记住的一句**：
> **"全自动最大的风险，不是它会犯错，而是它错了还在自信地往前跑。"**
