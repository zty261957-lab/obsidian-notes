# 二、开场那个估算（全文的问题起点）

> 「一个需求上线大约**二十个工作日**，**写代码占其中两天**。假设写代码快十倍，两天变成零点二天，整个周期从 20 天变成 18.2 天——**省了 1.8 天，剩下 18 天还在等需求确认、等 Spec 对齐、等测试、等 Review、等联调、等发布窗口。**」

**→ 所以它把其余环节也交给了 Agent：15 个角色，Leader 调度，从需求推到可验证的交付。**

**⭐ 这个估算和快手阿姆达尔定律是同一件事的另一种算法**：
| 说法 | 出处 |
|------|------|
| 编码占 20%，即使快 10 倍，整体只提升约 22% | 阿姆达尔定律 |
| 20 天里编码占 2 天，快十倍只省 1.8 天 | 本文粗估 |

# 三、⭐⭐⭐ 核心判断：验收对象从"产物"变成了"产物 + 过程"

## 一个 diff 背后经过六道手

| 角色 | 干什么 |
|------|--------|
| **Research** | 查清相关模块与历史变更 |
| **Explorer** | 找同构实现，形成候选方案 |
| **Spec** | 定目标和验收条件 |
| **Code Worker** | 实现 |
| **Test / Harness** | 编译、测试、端到端验证 |
| **Judge / Verify** | 独立挑方案、语义验收、**对抗式审查** |

**之后还有 Deploy 负责环境与发布验证。**

## ⭐ 原文那句应该被当作设计原则直接抄的话

> 「最终的交付物**除了代码和 PR，还包括测试报告、审查证据、进度、阻塞信息和完整的运行 trace**。」

**→ 作者的点睛**：
> **「验收对象从'产物'扩展成了'产物＋过程'。」**

## ⭐⭐⭐ 为什么这是最要命的一条

> 「单 Agent 的时候，你审的是 diff。多 Agent 之后，同一个 diff 背后有**六道手**，每一道都可能添加、也可能丢掉信息。如果中间某一道的证据没留下来，你就无法回答一个最基本的问题：**这个 diff 是'实现符合 Spec'，还是'实现恰好跑通了那个测试'？** 这两件事在结果上长得完全一样。」

**⭐⭐ 我的判断**：
**这跟腾讯「失败不可见」、淘天「高机评分 ≠ 业务可用」是同一个病根：**
**我们只看结果，所以分不清"做对了"和"看起来做对了"。**

**三家说法对照**：
| 来源 | 说法 |
|------|------|
| 腾讯 PUBG | 覆盖率看板把「采集失败」和「没有数据」显示成同一个 0% |
| 淘天 TaoDesign | 机器打分不错、观感过得去，但业务组件被模型擅自改写了 |
| **本文** | **无法区分"实现符合 Spec"和"实现恰好过了测试"** |

# 四、四个持久问题（原文列的，作者逐个翻成测试动作）

## 问题 ①：架构约束不在需求文本里

**原文例子**：
> 想扩展现有 API 的能力，Agent 却选择**新加一个 API** —— 单看当前任务更简单，放到系统里**不符合设计要求**。

**性质**：约束不在需求文本里，而在**代码结构、文档和人的经验**里。

**传统做法**：人工 review 时提一句 —— 但 **review 也会漏**。

**⭐⭐ 可执行解法：把约束写成断言**
```
"新增的对外接口数必须为 0"
"改动的模块必须限定在给定目录内"
→ 这两条都可以用一个【脚本】在 diff 上跑
```

> **「约束一旦能写成断言，它就不再依赖谁记得提。」**

**⭐⭐⭐ 而且它给了一个极关键的警告**：
> 「反过来，**只写进 prompt 的约束会在上下文压缩时被截掉，而你事后无法证明它当时在不在。**」

**→ 这条直接打在我们 Skill 上**：
**我们 prd-writer 里 16 条约束，如果只写在 SKILL.md 里靠模型"记得住"，上下文一压缩就没了，而且无法证明它当时在不在。**

## 问题 ②：输入边界不是设计出来的，是撞出来的

**原文例子**（很妙）：
> 在外卖应用里问「**怎么写 Python 程序**」—— 这已经超出了原本的业务边界。

**性质**：**输入域边界需要持续发现，不是一次性设计出来的。**
> 「你设计输入域时能想到的是'用户会问订单、会问退款'，**你想不到的是'用户会问怎么学编程'**。」

**解法**（原文没给，作者补的）：做成一个**常驻的观察位** —— 把线上超出业务边界的输入收集起来，**定期送进评测集**。

**⚠️ 作者的现实提醒**：
> 「这不是新方法，但它的**执行成本主要不在技术，在于谁负责看这个队列**。多数团队建了这个队列，然后没人看。」

## 问题 ③：同一个坑反复掉

**原文**：同一个问题反复出现，经验和没积累一样。

**⭐⭐ Agent 场景的特殊性**：
> 「在 Agent 流水线里，**复发比人更隐蔽** —— 因为**每一轮上下文的开头是一样的，上一轮学到的修复方法不一定被带进来**。」

**原文的实践经验第一条**：**跨轮次保留必要的上下文**

**解法**：给每个已修复的缺陷配一条用例，**且这条用例必须和它对应的缺陷编号绑在一起**
> 「当同类缺陷再次出现时，你能立刻知道是'**新问题**'还是'**老问题回来了**'。」

**⭐⭐ 作者的点睛**：
> 「这件事看起来只是**台账习惯**，但它决定了你能否回答一个关键问题：**这套流水线有没有在学习。**」

## 问题 ④：改一处，别处回归

**原文**：改一个 Skill，当前用例过了，另一条可能坏。

**原文自己点明要**：「相对稳定的 **Benchmark** 和**回归检查**」

**⭐ 作者认为这句可以直接搬进任何团队的 Agent 上线流程**：
> 「**任何一次 Skill、Tool 或协作流的调整，都必须跑同一套固定题集。**」

# 五、⭐⭐⭐ 评测集怎么构造（含陷阱）

## 构造方法

```
从代码库挑 20 个人类专家的高质量提交
        ↓
从这些代码【反推】出对应的需求
        ↓
组成 Benchmark
        ↓
让 Agent 团队去做这些任务，结果与专家实现【并排比较】
```

## ⭐ 巧妙处

> **需求由代码反推，"需求—实现"天然对齐，题是可解的。**

## ⚠️⚠️⚠️ 陷阱也在这

> 「Agent 拿到的需求**比真实需求干净得多**，所以它**适合做回归题集，不适合用来估'能不能替代人做需求'**。」

**⭐⭐ 这条对我们极其重要**：
**我们的知识库也是从原始文档"反推"出来的（raw → wiki 归纳页）。**
**→ 归纳页可能和"代码反推的需求"一样，比真实业务干净太多。**
**→ 用它测出来的效果，会系统性高估。**

# 六、⭐⭐⭐⭐⭐ 全文最锋利的一节：实现与验证为什么必须是两个 Agent

## 原文给的原则

> 「**实现和验证由不同的 Agent 承担，让验证有独立视角。**」

## ⭐ 作者指出的含义变化（这是全文最有价值的一句）

> 「这一条在测试行业里是**老原则**——**四眼原则、开发不测自己的代码**。但放进 Agent 协作里，**它的含义变了：不是"人"不能自己验，是"上下文"不能自己验。**」

## 为什么

> 「原因很直接：**同一个 Agent 的实现和验证共享同一个上下文。** 验证的时候，它**已经知道自己是按什么思路写的**。于是它写出的断言会**自然贴合自己的实现——包括实现里的错误假设**。」

**→ 原文第四个问题描述的现象正是这个**：改一个 Skill，当前用例通过了，另一个用例却回归了。

## ❌ 作者否掉的两种做法

| 做法 | 问题 |
|------|------|
| 喊口号"必须两个 Agent" | 组织调整要开会，落不了地 |
| 什么都不改 | 独立性已经被削弱 |

## ✅ 他给的改编版：不改架构，改字段裁剪

**检查方法（在 trace 里定位两个 Session）**：
```
问题 1：写代码 和 跑验证 是不是同一个 Session？
问题 2：验证阶段的输入里，是否包含了实现的【完整推理过程】？
```

**判定**：
> 「如果第 2 个问题的答案是'**包含**'，**验证的独立性就已经被削弱了**。这时**不需要改架构**——可以让它在同一个 Agent 里做，但**验证阶段的输入应该被裁到只有 Spec 和产物，不含实现思路**。」

## ⭐⭐⭐ 那句可以直接当方法论记的话

> **「这一条我认为比'必须两个 Agent'更可落地，因为它把组织问题变成了一个字段裁剪问题。字段裁剪可以写进代码，组织调整要开会。」**

# 七、⭐⭐ 人工闸：是有进闸条件的状态，不是兜底

## 原文：Leader 要决定三件事

| 情况 | 处理 |
|------|------|
| 测试不过怎么办 | 回到原来的 Code Session 继续修 |
| 方向错了怎么办 | 带着**失败证据**重做 Research 和 Explore |
| **反复不收敛怎么办** | **触发 Human Gate 请人判断** |

## ⭐ 作者的区别（这个区分极重要）

> 「第三个最值得单独说，因为它是一个**有明确进入条件的机制**。多数团队把它做成了'**出错就找人**'——这两者差别很大：
> - 做成**兜底**，人工闸会变成**日常**，**人成为整条流水线上最慢的一环**；
> - 做成**有条件的闸**，它只在**特定状态下**开。」

## 触发条件怎么翻译成可判定的

**原文**：「反复尝试仍不收敛」

**翻译**：
```
同一任务在同一类失败上重试次数 > N
  或
连续两轮验收结论均为【不通过】
   → 升级
```

**⭐ 但要让这个判定跑起来，需要两样东西**：
| 需要什么 | 为什么 |
|---------|--------|
| **失败要能被分类** | 不然"同一类失败"无从判断 |
| **每轮验收结论要留档** | 不然"连续两轮"无法计算 |

> **「两样东西都属于前面那张证据清单的一部分。」**

**⭐⭐ 我的判断**：
**这条把"人工介入"从"没办法了找人"升级成了"状态机的状态转移"。**
**区别在于：前者不可度量，后者可以统计"人工闸触发率"——而这个指标本身就能反映流水线健康度。**

# 八、那组成绩单 + 三个限定

## 成绩

- 抽 **19 道题**验证
- 约 **10 道**产出的实现与专家方案**大致相当**
- 另有 **5 道**接近**专家水平**
- 在「限定且约束明确」的场景里，交付周期从**约一个月缩到一周以内**

## ⚠️⚠️⚠️ 三个限定（缺一个就会读错）

| # | 限定 | 影响 |
|:--:|------|------|
| **1** | **题是从已有代码反推的** | 需求描述与实现天然对齐，**Agent 拿到的需求比真实需求干净得多** |
| **2** | **"大致相当"是作者团队自己的判定** | 口径是"思路有没有漂、代码有没有问题、验证够不够、分工对不对"，**没有第三方盲评** |
| **3** | **19 道题是小样本**，且来自**两个已上线的受限场景** | 不能外推 |

## ⭐⭐ 正确读法（这句话是全文的收口）

> 「在**需求清楚、验收条件可写**的场景里，多角色协作已经能接近专家；**一旦需求模糊，这个成绩不能外推**。」
>
> 「它也恰好划出了'**什么场景能交给 Agent、什么场景必须人来定验收**'。」

# 九、三个可以直接写进验收单的检查项

**作者挑的三件"成本最低、收益最直接"的事**：

## ① 交付物清单里加 trace，且「缺了不算交付」

> 「**不是'建议留存'。** 理由前面说过：没有 trace，你**无法区分'实现符合 Spec'和'实现恰好过了那个测试'**。」

## ② 验证阶段的输入做裁剪

> 「把实现的推理过程从验证上下文里摘掉，**只给 Spec 和产物**。**不改架构，改的是喂进去的字段。**」

## ③ 固定题集先行

> 「在接入任何 Agent 改动之前，**先把 10 到 20 条覆盖主要路径的题固化下来**。原文用的是专家提交反推的题，**你可以用自己仓库里最近一年被 review 打回过的高质量提交反推。**」

**⭐ 成本与收益**：
> 「三件事加起来大概**一两天工作量**，能挡住的是同一类问题：**不知道该相信哪一个 Agent 的结论。**」

# 十、⭐ 最后那句反方的话（作者自己留的）

> 「这套 15 角色流水线的**适用前提是'需求清楚且场景受限'**。如果你的业务本身处在**需求天天变的阶段**，强行上多角色流水线，**最大的产出可能是更多需要人来判断的交接点**——而**人的判断力是这条链上最稀缺的资源**。」
>
> 「这也是为什么我把它理解为'**给成熟链路加速**'，而不是'**给早期项目提效**'。」

**⭐⭐ 这句话对我们特别有用**：
**因为我们的项目现在正是"需求天天变"的阶段**（领导一天一个口径，产品重心从产研侧转到项目储备+交付）。
**→ 所以不该急着上多 Agent 流水线，该先把"需求清楚化"这件事做扎实。**

# 十一、⭐⭐⭐ 对我们工作台 / Skill 体系的 8 条直接可用判断

## ① ⚠️ 最重要的一条：我们的「自检」环节独立性不足

**我们 prd-writer 的 Step 4「自检可追溯性」是同一个 Agent 做的。**
按本文标准：
> **"同一个 Agent 的实现和验证共享同一个上下文，它写出的断言会自然贴合自己的实现——包括实现里的错误假设。"**

**→ 不用改成两个 Agent，改字段就行**：
**自检时的输入应该只有「原始文档 + 知识库 A 级条目 + 产出的 PRD」，不含我生成时的思路。**

**⭐ 而且这条能顺手解决我们一个老问题**：为什么同一份 PRD，我自己查不出问题，别人一眼看出？

## ② 我们的 16 条约束，有几条能写成断言？

**现在的形式**：写在 SKILL.md 里，靠模型读到并记住。
**本文警告**：
> 「**只写进 prompt 的约束会在上下文压缩时被截掉，而你事后无法证明它当时在不在。**」

**→ 该做的是**：挑出能脚本化的约束，做成**文档出稿后的自动检查脚本**。
**可脚本化的例子**：
- 交付说明三节是否齐全（grep 关键词）
- 正文有无 `[[页面名]]` 泄漏（grep）
- 【待产品确认】条目是否都在第 11 章出现过（集合比对）
- **标题是否手写了编号**（正则）
- 第 11 章阻断型是否置顶（顺序检查）

**→ 这几条都能写进一个 `verify_prd.py`，出稿后自动跑。**

## ③ 交付物该加 trace，且「缺了不算交付」

**我们现在的交付说明只有三节**：事实源与产出范围 / 知识库引用清单 / 格式说明。

**→ 按本文标准，应该加第四项**：**本次执行轨迹**（读了哪几页、用了哪些 A 级条目、跳过了什么、为什么跳过、哪些地方停下问过）。

**⚠️ 但注意**：约束 13 说"交付说明只留三节"，这是用户定的。
**→ 所以不是加进交付说明，而是作为附件/日志留存。**

## ④ 我们的知识库是"反推"出来的，要警惕过于干净

**本文陷阱**：
> 「Agent 拿到的需求比真实需求干净得多，适合做回归题集，**不适合用来估'能不能替代人做需求'**。」

**→ 我们的 wiki 归纳页相比 raw 原始文档，也是"干净版"。**
**→ 用它测 PRD 质量，会系统性高估。**

**⭐ 所以知识库必须能随时下钻到 raw —— 这也是我们 A/B/C 分级存在的真正理由。**

## ⑤ 人工闸要有进闸条件

**我们现在的 Step 6 审核闸门是"每次必停"** —— 那是**交付闸**，必须有。

**但另有一类更需要按本文改造的**：**什么情况下该停下来问不确定项**。
**现在的挂账闸门是按"类型"判（阻断型/可后置型）—— 这已经是"有条件"了，符合本文标准。✅**

**→ 可再补一条**：**同一类问题问过两次还没定 → 升级**（不要第三次还问同一个问题）。

## ⑥ 固定题集先行 —— 我们最缺的一块

**我们现在没有任何 PRD 质量的固定题集。**
**→ 按本文建议**：**用最近一年被评审打回/退回修改的需求文档反推 10-20 道固定题。**

**我们的条件比阿里还好一点**：我们有**真实的评审打回意见**（领导的批评、甲方的退回），**这就是现成的"专家标注"**。

## ⑦ 失败要能被分类

**本文要求**：失败分类 + 每轮验收结论留档，否则"反复不收敛"无法判定。

**→ 我们该做的最小动作**：
**把历次 PRD 被打回的原因分类归档**（缺事实源 / 格式不对 / 编造了内容 / 没写交付说明 / 编号错乱……）
**这个分类一旦有了，"第几次因为同类原因被打回"就能统计。**

## ⑧ 「给成熟链路加速，不是给早期项目提效」

**这条是对我们项目节奏的提醒**：
**我们现在是需求天天变的阶段（产品重心一个月内从产研侧调到项目储备+交付）。**
**→ 这个阶段上多 Agent 流水线，产出的是更多交接点，不是更多成果。**
**→ 该做的是先把「需求说清楚」这件事做扎实。**

# 十二、一句话记住它

> **多 Agent 之后，你审的不再是一个 diff，而是六道手留下的证据链。**
>
> **⭐⭐ 所以：交付物里必须有 trace，缺了不算交付 —— 因为否则你分不清"做对了"和"看起来做对了"。**
>
> **⭐⭐⭐ 而全文最锋利的一句是：**
> **「实现与验证必须分离」在 Agent 时代的含义，从"人不能自己验"变成了"上下文不能自己验"。**
> **落地不必改架构 —— 把实现的推理过程从验证的输入里裁掉就行。**
> **「字段裁剪可以写进代码，组织调整要开会。」**
