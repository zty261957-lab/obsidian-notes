> **原文**：《智能体设计模式 — 构建智能系统实战指南》

## 📌 一句话概括

> **这本书把"怎么造一个能干活的 AI"拆成了 21 个可组合的设计模式** ——
> 从最基础的**提示词链**，到**路由、并行、反思、工具、规划、多智能体、记忆**，
> 再到工程化的 **MCP、A2A、护栏、评估、资源优化**。
> **核心主张**：**AI 智能体应该被当作"复杂软件"来造** —— 用几十年验证过的工程实践（容错、状态管理、健壮测试）去构建它。

# 一、★ 21 个模式速查表（**全书骨架**）

| # | 模式 | 一句话 | 关键机制 |
|---|------|--------|---------|
| **1** | **提示词链** | 把复杂任务拆成一串小步骤 | 每步的输出 = 下一步的输入（也叫"管道模式"） |
| **2** | **路由** | 按条件决定下一步走哪 | LLM 判断 / 规则 / 嵌入相似度 |
| **3** | **并行化** | 独立任务同时跑 | 降延迟；但增加设计/调试/日志复杂度 |
| **4** | **反思** | 自己检查自己再改 | **生产者-评审者模型**（独立角色评估，更客观） |
| **5** | **工具使用** | 让 AI 能用外部系统 | 函数调用；**LLM 决定何时用、生成结构化调用** |
| **6** | **规划** | 把大目标拆成有序步骤 | 多步任务、工作流自动化、复杂环境导航 |
| **7** | **多智能体协作** | 多个 AI 分工合作 | 顺序交接 / 并行 / 辩论 / 层级 |
| **8** | **记忆管理** | 短记忆 + 长记忆 | 短期=上下文窗口；长期=向量库检索 |
| **9** | **学习和适应** | 从经验里改自己行为 | 自我改进编码智能体（SICA） |
| **10** | **MCP** | LLM 与外部系统的**标准化接口** | 客户端-服务器架构；公开资源/提示/工具 |
| **11** | **目标设定与监控** | 给 AI 目标和进度跟踪 | **目标要 SMART**；监控→反馈→修订 |
| **12** | **异常处理和恢复** | 出错了怎么办 | 检测（校验/错误码/超时）→ 处理（重试/回退/降级）→ 恢复 |
| **13** | **人机协同（HITL）** | 关键节点人介入 | 人类监督/干预/反馈；**缺点：扩展性不足** |
| **14** | **知识检索（RAG）** | 给 AI 补外部知识 | 检索+增强；**GraphRAG / Agentic RAG** |
| **15** | **智能体间通信（A2A）** | 不同框架的 AI 互相通信 | 开放 HTTP 标准；**AgentCard** 标识能力 |
| **16** | **资源感知优化** | 动态管算力/时间/钱 | **按复杂度选模型**（简单用 Flash、复杂用 Pro）|
| **17** | **推理技术** | 让"思考过程"显式化 | **CoT / ToT / ReAct / 自纠正** |
| **18** | **护栏/安全模式** | 防有害/偏见/跑题 | 输入验证 + 输出过滤 + 工具限制 + 外部审核 |
| **19** | **评估和监控** | 持续量它的表现 | 准确率 + 延迟 + token；**看"轨迹"不只是结果** |
| **20** | **优先级排序** | 按紧急/重要/依赖排任务 | 动态重排；战略层 + 战术层 |
| **21** | **探索和发现** | 主动找新信息和可能 | 自主生成假设、设计实验（如 Google 协同科学家）|

**附录**：A 高级提示技术｜B AI 智能体交互（GUI→真实世界）｜C Agentic 框架概览（LangChain/ADK/CrewAI）｜D AgentSpace｜E 命令行中的 AI Agent

# 二、逐章要点（**每章"关键要点"原文精炼**）

## 第 1 章 提示词链
- **把复杂任务分解为一系列较小的、聚焦的步骤**（也叫**管道模式**）
- 每步涉及 LLM 调用或处理逻辑，**用前一步的输出作为输入**
- 提高与语言模型复杂交互的**可靠性和可管理性**
- LangChain/LangGraph、Google ADK 提供定义与执行多步序列的工具

## 第 2 章 路由
- 让智能体**根据条件动态决定下一步**
- 使其能处理多样输入、**超越线性执行**
- 路由逻辑可用 **LLM / 基于规则 / 嵌入相似性** 实现

## 第 3 章 并行化
- 通过**并发执行独立任务**提高效率，**对等待外部资源（如 API）的任务特别有效**
- ⚠️ **代价**：引入显著的复杂性和成本，影响**设计、调试、日志**
- LCEL 的 `RunnableParallel`；ADK 通过 LLM 驱动的委托实现

## 第 4 章 反思
- **最大优势：迭代地自我纠正和优化输出** → 显著提高质量、准确性、对复杂指令的遵循度
- **生产者-评审者模型**：独立智能体（或提示角色）评估初稿 —— **关注点分离增强客观性**
- ⚠️ **代价**：增加延迟和计算成本；有超出上下文窗口的风险

## 第 5 章 工具使用
- 让智能体**与外部系统交互、访问动态信息**
- 关键：**定义有清晰描述和参数的工具**（LLM 能理解）
- **LLM 决定何时用工具，并生成结构化调用**；框架执行调用并回传结果
- ADK 预置工具：Google 搜索、代码执行、Vertex AI 搜索

## 第 6 章 规划
- 把**复杂目标分解为可操作的顺序步骤**
- 对多步任务、工作流自动化、复杂环境导航**至关重要**
- 明确提示或设计任务要求规划步骤，会**鼓励这种行为**
- 例：**Google Deep Research**（反思 + 规划 + 执行）

## 第 7 章 多智能体协作
- 多个智能体**协同实现共同目标**，利用**专业角色、分布式任务、智能体间通信**
- 形式：**顺序交接 / 并行处理 / 辩论 / 层次结构**
- **非常适合需要多样化专业知识或多阶段的复杂问题**

## 第 8 章 记忆管理
- 记忆对**处理事务、学习、个性化交互**都至关重要
- **短期记忆**：即时信息，临时性，受上下文窗口限制
- **长期记忆**：持久信息，用**向量数据库**跨会话保存，**通过搜索访问**
- ADK 三件套：`Session`（聊天线程）、`State`（临时数据）、`MemoryService`（可搜索长期知识）
- ⚠️ 应通过 `EventActions.state_delta` 或 `output_key` 更新状态，**不要直接改字典**

## 第 9 章 学习和适应
- **学习** = 智能体通过经验改进自身行为；
- **适应** = 学习导致的**行为或知识的可见变化**
- **SICA**（自我改进编码智能体）：基于过去表现修改自己的代码

## 第 10 章 模型上下文协议（MCP）
- **MCP 是开放标准，促进 LLM 与外部应用、数据源、工具之间的标准化通信**
- 采用**客户端-服务器架构**，定义公开和使用**资源、提示、工具**的方法
- ADK 既支持用现有 MCP 服务器，也能通过 MCP 服务器公开 ADK 工具
- **FastMCP 简化了 MCP 服务器开发**

## 第 11 章 目标设定与监控
- 为智能体配备**目的感和跟踪进度的机制**
- **目标应该是 SMART**：具体的、可衡量的、可实现的、相关的、有时限的
- 监控涉及**观察智能体的行动、环境状态、工具输出**
- **反馈循环**让智能体能适应、修订计划或升级问题

## 第 12 章 异常处理和恢复
- 对构建**强大可靠的智能体非常重要**
- **检测**：验证工具输出、检查 API 错误码、使用超时
- **处理**：日志记录、重试、回退、**优雅降级**、通知
- **恢复**：通过诊断、自我纠正或升级恢复稳定运行

## 第 13 章 人机协同（HITL）
- 把**人类智能和判断整合进 AI 工作流**
- 在**复杂或高风险场景**中对安全性、道德、有效性至关重要
- 关键：**人类监督、干预、学习反馈、决策增强**
- ⚠️ **主要缺点：固有的可扩展性不足** —— 在准确性和数量之间造成权衡

## 第 14 章 知识检索（RAG）
- 让 LLM 能访问**外部的、最新的、特定的信息**
- 过程：**检索**（搜索相关片段）+ **增强**（把片段放进提示）
- 作用：**克服过时训练数据、减少幻觉、集成领域知识、让答案可归因**
- **GraphRAG**：用知识图谱理解信息间关系 → 回答需综合多源的问题
- **Agentic RAG**：用智能体**主动推理、验证、精炼**外部知识

## 第 15 章 智能体间通信（A2A）
- **Google A2A 协议**：开放、基于 HTTP 的标准，**让不同框架构建的智能体互相通信协作**
- **AgentCard**：智能体的数字标识符，让他者**发现并理解其能力**
- 支持**同步请求-响应** + **流式更新**
- 支持**多轮对话**（如 `input-required` 状态，允许智能体请求补充信息）
- ⭐ **A2A vs MCP**：**A2A 管"智能体之间"的协作；MCP 管"LLM 与外部资源"的接口**

## 第 16 章 资源感知优化
- 智能体可**动态管理计算、时间、财务资源**，按实时约束做模型选择和执行路径决策
- **动态、LLM 驱动的路由**：路由器按**查询复杂性和预算**选模型（简单→Flash，复杂→Pro）→ **优化成本与性能**
- **批评智能体**：为自我纠正、性能监控、改进路由提供反馈
- 其他技术：自适应工具选择、**上下文修剪与摘要**、主动资源预测、成本敏感探索、节能部署、优雅降级

## 第 17 章 推理技术
- **标准化解决方案**为智能体提供结构化推理框架
- **CoT（思维链）/ ToT（思维树）** 指导 LLM 分解问题、探索多路径
- **自纠正**允许答案迭代改进
- **ReAct** 把**推理与行动集成**，使智能体能调用工具、与环境交互、调整计划
- ⭐ **推理扩展定律**：智能体性能**不只关乎模型大小，还关乎分配的"思考时间"**
- **适用**：问题对"一次通过"太复杂，需要分解、多步逻辑、外部数据交互或战略规划时

## 第 18 章 护栏/安全模式
- 防止**有害、有偏见、离题**的响应，构建负责任、合规、安全的智能体
- 实施阶段：**输入验证、输出过滤、行为提示词、工具使用限制、外部审核**
- **不同技术组合提供最强保护**
- 需要**持续监控、评估和改进**
- ⭐ **有效方法：把智能体当"复杂软件"** —— 用传统系统几十年验证过的工程实践（容错、状态管理、健壮测试）

## 第 19 章 评估和监控
- **超越传统测试**：在真实环境中**持续测量有效性、效率、对要求的遵守**
- 应用：性能跟踪、A/B 测试改进、合规审计、**检测行为漂移或异常**
- 基本评估看**响应准确性**；真实场景还需**延迟监控 + token 使用跟踪**
- ⭐ **智能体轨迹（它采取的步骤序列）对评估至关重要** —— 把实际操作与理想路径对比，识别错误和低效率
- ⭐⭐ **关键结论**：**"为了使 AI 在复杂的、高风险的任务中可靠，我们必须从简单的提示词转向精确、定义可验证可交付成果和范围的正式'合约'。"**

## 第 20 章 优先级排序
- 让智能体在**复杂多方面环境**中有效运作
- 按**紧急性、重要性、依赖关系**评估和排序任务
- **动态重新优先级排序**：按实时变化调整焦点
- 发生在多个层面：**总体战略目标 + 即时战术决策**

## 第 21 章 探索和发现
- 让智能体**主动追求新信息和可能性**，对复杂演变环境至关重要
- 例：**Google 协同科学家**（自主生成假设、设计实验，补充人类科研）
- 多智能体框架（如 Agent Laboratory）自动做文献综述、实验、报告撰写

# 三、★ 这本书对我们最有用的 5 点

## ① 「提示词 → 合约」—— **回答"为什么会有 Skill"的最有力一句** ⭐⭐⭐

> **书里原话（第 19 章）**：
> **"为了使 AI 在复杂的、高风险的任务中可靠，我们必须从简单的提示词转向精确、定义可验证可交付成果和范围的正式'合约'。"**

**→ 这就是"为什么需要 Skill"的另一种权威表述** ✅
- **提示词**：说一次，松散的
- **合约**：写下来，**定义"可验证的交付成果和范围"** —— **这正是 Skill 在做的事** ✅

**★ 汇报时可以直接引用**（书 + 官方文档双重依据）✅

## ② 「不用时零成本」—— 书里印证了"按需加载"的价值

> **第 16 章**：资源感知优化提到"**上下文修剪和摘要**""**按查询复杂度选模型**"

**→ 和 Skill 的"三级加载"是同一个思路**（**用不到的就不加载**）✅

## ③ 「RAG 管事实，Skill 管方法」—— **书里把两者分得很清** ⭐⭐

| 书里 | 管什么 |
|------|--------|
| **第 14 章 RAG** | **外部知识/事实**（"是什么"）|
| **第 1/4/6/17 章**（链/反思/规划/推理） | **做事的方法与思考过程**（"怎么做"）|

**→ 正好印证我给你写的"Skill 边界"那篇**：
> **"会不会做"→ 模型本体；"是什么"→ 知识库/RAG；"怎么做"→ Skill；"能不能连"→ MCP** ✅

## ④ 「把智能体当复杂软件」—— 书的核心主张，也是"为什么人要读 Skill" ⭐

> **第 18 章**："**有效方法是将它们视为复杂软件，应用与传统系统相同的工程最佳实践——容错、状态管理、健壮测试。**"

**→ 领导说的"你写 skill 和写代码是一回事，复杂工程里不能全让它改"—— 和这本书的主张完全一致** ✅

## ⑤ 「轨迹比结果更重要」—— 评估思路 ⭐

> **第 19 章**："**智能体轨迹（采取的步骤序列）对评估至关重要，将实际操作与理想路径对比，以识别错误和低效率。**"

**→ 对我们做 Skill 培训的启发**：
- **评估一个 Skill 写得好不好，不只看它出没出结果**
- **要看它走的步骤对不对**（**比如"有没有认错数据块""有没有跳过校验"**）✅
