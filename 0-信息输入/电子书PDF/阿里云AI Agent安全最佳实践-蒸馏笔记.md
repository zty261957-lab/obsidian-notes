# §1 一句话概括

> **阿里云提出「Agent 原生安全」** —— 把 **Agent 本身**确立为**第一安全主体**，
> 系统化解决 **三大核心矛盾：资产不可见 · 身份不可管 · 行为不可控**，
> 构建覆盖 **开发态（Buildtime）+ 运行态（Runtime）** 的纵深防御体系。

**核心判断**：
> **"安全不再是可选的附加项，而是业务成功的必要条件。"**
> **安全要从「人防」走向「智防」，从依附于模型的"附加项"变成内生于 Agent 的"原生基因"。**

# §2 ⭐ 为什么要重新理解 Agent 安全（风险机制变了）

## 2.1 传统云安全 vs Agent 安全（根本差别）

| | 传统云安全 | **Agent 场景** |
|---|-----------|--------------|
| 模型参与什么 | 只生成内容 | **参与任务规划、工具选择、上下文理解、操作执行** |
| 攻击者怎么做 | 利用漏洞、窃取凭证、绕过访问控制 | ⭐ **不需要突破系统漏洞** —— 只要**操纵 Agent 的输入、上下文或工具链**，诱导它**以合法身份**完成非预期操作 |
| 攻击路径 | 利用系统缺陷 | ⭐ **影响智能体决策** |
| 风险结果 | 输出不可信内容 | ⭐ **调用真实系统能力** |

## 2.2 ⭐ Agent 攻击链（五步，记这条）

```
不可信输入进入上下文
  → Agent 目标或判断被影响
    → 工具/插件/API 被选择或误用
      → Agent 继承系统身份执行操作
        → 数据、资源或业务流程受到影响
```

**⭐ 关键洞察**：
> **攻击者可能只需把恶意指令嵌入「网页、邮件、PDF、文档、工单、知识库或第三方数据源」** ——
> **当 Agent 读取这些内容时，就可能把攻击者意图混进任务上下文。** ⚠️

# §3 为什么传统防御失效（三个"不匹配"）

| # | 问题 | 数据/说明 |
|---|------|----------|
| **① 规模鸿沟** | 企业指数级部署 Agent，传统安全工具难以监控海量 Agent | **CyberArk：Agent 数量已高达人类的 82 倍** |
| **② 工具链脱节** | 现有工具**缺乏对 Agent 自主行为（如工具组合调用）的深度理解**，难以防御**看似合法的越权操作** | — |
| **③ 运营模式滞后** | 传统 SOC 平均响应时间 **28.7 小时**，无法应对 AI 驱动的**分钟级自动化攻击** | Palo Alto Networks |

**三个具体挑战**：
| # | 挑战 | 数据 |
|---|------|------|
| **① 资产治理全面失控** | 静态资产清单和基于人类身份（IAM）的治理体系**已彻底崩塌** | 60% 的企业仍在用未纳管的 AI 应用 |
| **② 决策风险** | Agent 自主决策带来不可预测的"危险操作" | **MIT/Harvard/Stanford：超 70% 的 Agent 产品缺乏有效的自我反思和错误恢复机制**<br>**麦肯锡：80% 企业已遭遇此类问题** |
| **③ 合规困境** | 中国生成式 AI 管理办法 + 全球差异化合规要求 | **Gartner：40% 以上的 Agentic AI 项目因合规风险将在 2027 年前被取消** |

# §4 ⭐ Agent 的 5 类典型风险（做交付必须逐条对照）

| # | 风险 | 具体表现 |
|---|------|---------|
| **①** | ⭐ **间接提示词注入** | 攻击者把恶意指令**隐藏在外部网页、PDF、邮件、知识库文档或工单内容**中<br>Agent 在检索、总结或处理时，**可能误将其中的指令当作任务要求**，进而泄露上下文、查询敏感数据或调用不该调用的工具 |
| **②** | ⭐ **工具与插件误用** | Agent 通过 **Skills、插件、MCP Server 或内部工具**访问外部能力<br>若**工具描述不清晰、权限边界过宽、第三方工具链被篡改**，Agent 可能在看似正常的流程里调用高风险能力（读数据、发外部请求、执行脚本、改系统配置）|
| **③** | ⭐ **过度 Agent 权限** | Agent 一旦绑定云账号/服务角色/临时凭证/应用身份，**就具备真实操作系统的能力**<br>权限过大时，攻击者**无需拿到凭证**，只要操纵任务目标，**就能间接触发删除、修改、导出、发布、扩缩容** |
| **④** | ⭐ **上下文与记忆污染** | Agent 依赖**长期记忆、历史任务、向量数据库、业务知识库**做判断<br>一旦被污染，**风险具有持续性** —— 后续任务会**反复产生错误判断** |
| **⑤** | **数据汇聚导致泄露面扩大** | Agent 常同时连接对象存储、数据库、日志平台、代码仓库、工单、消息系统<br>**单个系统里原本低敏的数据，经 Agent 汇总、推理、组合后，可能形成更高敏感度的信息资产** ⚠️ |

**⭐ 一句话总结这个视角**：
> **Agent 不应仅被视为一个应用组件，而应被视为一种具备行动能力的「非人身份」和「自动化执行主体」。**
> ⭐ **它的风险不只取决于模型是否安全，还取决于：**
> **① 连接了哪些数据源　② 持有哪些权限　③ 能调用哪些工具　④ 是否有外联能力　⑤ 行为是否可审计回溯**
>
> **→ 治理重点应从「单点防护」转向「依赖关系治理」** ——
> **高危风险往往并非源于模型本身漏洞，而是源于 Agent 与身份、工具、数据、API、运行环境之间的关系失控。** ⭐

**参照的框架**：**OWASP Top 10 for LLM / Agentic Applications**（提示词注入、过度自主性、工具误用、供应链风险、上下文污染、敏感信息泄露）+ **NIST AI RMF 1.0**（治理/识别/度量/管理）
**→ 共同结论**：**Agent 安全不能只在模型层解决，必须覆盖「模型、身份、工具、数据、权限、运行环境」之间的完整关系。**

# §5 ⭐ 三层防御体系（框架可以直接借用）

| 层 | 名称 | 核心主张 |
|---|------|---------|
| **第一层** | **资产与供应链层** | ⭐ **"看不见就无法保护"** —— 提供对智能体资产、依赖关系及供应链风险的**全面可见性**，消除"影子 Agent"盲区 |
| **第二层** | **身份与访问层** | ⭐ **机器身份管理有别于人类** —— 为**每个智能体绑定唯一的数字身份** |
| **第三层** | **行为检测与防护层** | ⭐ 基于 **AI 原生的意图与上下文理解**，对行为实时监控管控，实现端到端可管可控 |

**→ 三层联动**：把安全**内嵌于 Agent 从开发到运行的全生命周期**，实现**从被动防御 → 主动免疫**的跨越。

## 覆盖两个态（Buildtime / Runtime）

| 态 | 做什么 |
|---|--------|
| **开发态** | 资产发现与 **Agent-BOM 生成**、供应链风险评估、**部署前漏洞扫描**、安全态势基线配置（**从源头筑牢防线**）|
| **运行态** | **实时行为监控**、动态访问控制、威胁检测与响应、**持续合规审计** |

**机制**：**「持续检测」+「实时响应」** —— 从资产构建到业务运行无缝衔接。

# §6 六个安全实践（含痛点 → 解法 → 效果）

## 实践 1｜资产全量识别 + 血缘关联

| 项 | 内容 |
|---|------|
| **痛点** | 传统 IP 资产管理覆盖低，**Agent 影子资产达 60%**；每年万级 Agent 增长；供应链漏洞影响面评估**以天计** |
| **解法** | **"自动化探测 + 主动注册"双轨** —— 秒级识别 200+ 种 AI 工具组件、150+ AI 服务、180+ 核心组件<br>纳管 **6 类资产**（模型/Tool/API/数据集/Agent/基础设施）<br>构建"AI应用、大模型、工具"**全链路调用拓扑 → AI-BOM 供应链血缘图谱** |
| **效果** | 供应链漏洞影响面评估 **天级 → 分钟级**；内置 **2500+ 专项漏洞规则库**、**17 种 Agent 配置风险检测模型**，覆盖 **30+ 类细分风险** |

## 实践 2｜模型输入输出防护（提示词攻击 + 行为/意图审计）

| 项 | 内容 |
|---|------|
| **痛点** | **88% 的组织在过去 12 个月内确认或遭遇过 Agent 安全事件**（Gravitee 2026）<br>⚠️ **传统 Guardrail 面向单节点、短窗口，无法关联跨轮次上下文** → 攻击者在前序轮次注入恶意指令，后续才触发高危操作，**意图链被截断 → 高危风险漏过** |
| **解法** | ⭐ **从"单节点内容检测"升级为"全链路纵深防御"** —— 覆盖**模型输入输出、工具调用、知识库访问、文件操作**等**全部 Trace 节点**<br>核心是 **"意图-行为一致性"检测**：判断当前操作**是源自用户合法指令，还是前序攻击注入的延迟触发** ⭐ |
| **效果** | 覆盖 **MCP 投毒、RAG 投毒、目标劫持、路径遍历**等 30+ 攻击手法<br>**高危拦截准确率、召回率超 90%**；端到端平均响应 **<120ms**（长上下文 P95 <300ms）|

## 实践 3｜机器身份安全（打通权限和数据）

| 项 | 内容 |
|---|------|
| **痛点** | **外部 Agent**：越权访问（第三方通过 API 拿敏感数据）、**责任难界定**<br>**内部自建 Agent**：权限分配随意、**员工与 Agent 权限混淆**（普通员工通过报销 Agent 访问财务数据）、缺乏统一纳管 |
| **解法** | ⭐ **为每个 Agent 分配全局唯一的 Agent ID（类似员工工号）** —— 身份可识别、可追溯、可审计<br>**企业身份源集成**：钉钉/企业微信/飞书/LDAP/Azure AD，SSO 登录，基于 **OIDC/OAuth 2.0** 做令牌传递与校验 ⭐<br>**动态凭据管理**：集中托管敏感凭证，**Agent 代码无法访问长期有效原始凭据**，运行时只拿**短期、受限的临时凭证** ⭐ |
| **效果** | 支持 10+ 类企业身份、100+ 企业应用 SSO |

## 实践 4｜网络流量检测与管控

| 项 | 内容 |
|---|------|
| **痛点** | 大量风险**隐藏在 Agent 通信的流量里**；Agent 行为更灵活、边界更模糊 |
| **解法** | **Agent 防火墙**：端网融合一体化引流，覆盖 Agent 所在 workload 或网络关键出口<br>**Agent 自身零改造、零感知** |
| **核心能力** | · **流量覆盖**：正向代理一键引流；TLS 加密流量也处理<br>· **资产识别**：从流量自动发现**未注册的 Shadow Agent**；解析通信流量提取 **System Prompt**，**精确提取 Agent 完整的 skill/tool 资产清单** ⭐<br>· **行为管控**（这块最值得抄）：<br>　- **按 Agent 身份**管控能访问哪些应用（例：**代码 Agent 可访问 GitHub，拒绝社交媒体和游戏；客服 Agent 不可访问 GitHub**）⭐<br>　- **按 Agent 身份限速** LLM API 调用，解析响应统计 **Token 用量**<br>　- **LLM 服务准入**：域名黑名单 + **URL 路径级控制**（如**允许 `/v1/chat` 但拒绝 `/v1/files`**）⭐<br>· **异常检测**：Skill/Tool 黑白名单；对**加载的 skill.md 原始文件送检云端沙箱**并生成安全检测报告 ⭐<br>· **数据泄露**：内置 **10+ 凭据格式 + 40+ 个人信息**特征库；**敏感数据实时阻断/脱敏转发**<br>· **审计**：记录每次 LLM 交互的 Prompt、响应、Token 消耗 |

## 实践 5｜办公场景收敛风险

| 项 | 内容 |
|---|------|
| **痛点** | 员工私装第三方 Agent 导致敏感数据外泄；**SaaS 类 Agent 资产发现率仅约 35%** |
| **解法** | **终端探针 + 网络侧 DNS/HTTPS 流量分析**：建立 **500+ AI 服务域名动态指纹库**，无感发现<br>新发现的 Agent **自动触发云端沙箱评估** → 按风险分级管控（**审批放行 / 观察 / 实时封禁**）|
| **效果** | 办公网 Agent 资产纳管率 **35% → 95%+**；**数据外泄事件同比下降 78%**；审计日志完整率 99.9% |

## 实践 6｜用 Agent 重塑安全运营（Agentic Native）

> **从「人防」向「技防 + 智防」转变，用 Agent 对抗 Agent。**

| 产品 | 能力 | 效果 |
|------|------|------|
| **Agentic SOC** | **5 类专业 Agent + 1 个编排 Leader**（日志标准化/威胁检测/事件调查/事件处置/安全报告），基于 **ReAct 框架**自主决策 | **响应时间 37 小时 → 47 分钟**；自动化处置率 +22.2%<br>某汽车企业日均百万告警自动化处置率 **89%** |
| **Agentic NDR** | 5 个专业化 Agent 各司其职、自动协作 | 数小时人工溯源 → **分钟级** |
| **Agentic 代码安全** | 大模型静态代码扫描 | 检出率 80%（+30%）、准确率 90%（+35%） |
| **Agentic API 安全** | 大模型语义理解 | 比传统规则方案提升 **50%+** |
| **安全运维 Agent** | **一句话把安全需求转成可执行任务** | — |

**⭐ 值得注意的方法**：
> **Agentic SOC 采用「分层 Multi-Agent 协同架构」** ——
> **研判模式从「人工逐条分析」升级为「Agent 自主推理 + 人工审核确认」** ⭐
> **（这个"AI 干、人审"的分工，和你做 Agent 的设计原则一致）**

# §8 ⭐ 对我们最有用的话（企业交付安全底线）

> **做企业 Agent 交付时，这 8 条可以直接当检查清单：**

| # | 底线 | 为什么 |
|---|------|-------|
| **1** | ⭐ **Agent 拿到的权限必须是"最小必要"** | 权限过大时，**攻击者不需要拿到凭证**，只要操纵任务目标就能间接触发删除/导出/发布 ⚠️ |
| **2** | ⭐ **长凭证绝不进代码**，运行时只取短期临时凭证 | 「Agent 代码无法访问长期有效原始凭据」是硬要求 ⚠️ |
| **3** | ⭐ **每个 Agent 要有唯一身份（ID）+ 行为可审计** | 没身份就没法追溯；"责任难界定"是真实痛点 |
| **4** | ⭐ **高风险动作必须人工确认**（发布/付款/删除/覆盖/对外发送）| 这与破局手册的"权限三原则"完全一致 ✅ |
| **5** | ⭐ **把"AI 的输入"当成不可信内容** | 网页/PDF/邮件/知识库文档里**可能藏指令** —— 这是 Agent 独有的攻击面 ⚠️ |
| **6** | ⭐ **知识库和记忆要防污染**（污染会持续影响后续任务）| 不是一次性问题 |
| **7** | ⭐ **工具描述要写清、权限要给窄** | 「工具描述不清晰、权限边界过宽」是工具误用的直接原因 |
| **8** | **开发态就要做**（不是上线后补）| 官方明确：安全要在开发态 + 运行态都覆盖 |

**⭐ 一句可以直接引用的话**：
> **"Agent 不应仅被视为应用组件，而应被视为一种具备行动能力的「非人身份」和「自动化执行主体」。"**
