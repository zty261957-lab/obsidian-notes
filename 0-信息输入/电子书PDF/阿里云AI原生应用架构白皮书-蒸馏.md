## 1. 先看结论：这本白皮书最重要的 10 个判断

1. **云原生解决“如何高效运行”，AI 原生进一步解决“如何智能运行”。** LLM 从一个嵌入式功能升级为系统认知底座，业务路径不再完全由工程师预编码，而会由模型在运行时判断、生成和调整。（PDF pp.26-30）
2. **AI 原生应用的核心不是模型本身，而是模型、数据和场景的闭环。** 模型负责通用认知，私域数据决定业务差异化，场景与评估决定价值是否成立。（PDF p.10、pp.37-38）
3. **架构工作本质上是在管理非确定性。** 模型输出、工具选择、执行路径和多 Agent 协作都具有概率性，因此可观测、评估、安全与人工确认必须从外围补丁变成内生能力。（PDF pp.60-65、216-224、246-265）
4. **提示词工程只是“单次沟通优化”，上下文工程才是“系统认知环境建设”。** 生产级系统要动态组织外部知识、历史记忆、工具描述、任务状态与执行环境。（PDF pp.104-108）
5. **RAG 的上限首先由数据解析和索引质量决定。** 分块破坏语义、文档噪声、意图模糊、只做单路向量召回，都会让后续更强的模型也无从补救。（PDF pp.109-118）
6. **MCP 解决“如何标准化连接”，不自动解决“如何安全、可靠、低成本地使用”。** 生产落地仍需要身份、授权、审计、限流、协议治理、工具检索与效果评估。（PDF pp.126-149）
7. **AI 网关是统一控制面。** 它把多模型路由、故障切换、身份认证、Token 配额、内容安全、语义缓存、MCP 治理和可观测集中起来。（PDF pp.157-169）
8. **Agent 运行时的核心单位从“请求”变成“会话”。** 长任务、记忆、文件系统、浏览器和代码执行要求有状态、强隔离、可冻结/恢复、按忙闲动态计费的运行环境。（PDF pp.195-214）
9. **评估不是上线前的一次测试，而是贯穿设计、开发、灰度、上线和运营的持续系统。** 评估的最终产物不是分数，而是可执行的改进决策。（PDF pp.246-265）
10. **安全边界必须覆盖应用、模型、数据、身份、系统与网络。** 尤其要把用户提供的网页、PDF、工具返回等视为不可信数据，防止其通过提示注入劫持 Agent 工作流。（PDF pp.267-287）

## 2. 全书的架构主线

```text
业务目标与真实场景
        ↓
模型（认知、推理、生成）
        ↓
上下文工程（Prompt + RAG + Memory + State）
        ↓
Agent / Workflow / Multi-Agent（规划与编排）
        ↓
Tools / MCP / A2A（连接知识、系统与其他 Agent）
        ↓
AI Gateway（统一接入、路由、鉴权、限流、安全、审计）
        ↓
AI Runtime / Sandbox（有状态执行、隔离、弹性、异构算力）
        ↓
Observability + Evaluation（解释发生了什么、为什么、效果怎样）
        ↓
Security + Human Confirmation（约束风险与高影响动作）
        ↓
线上反馈与 Bad Case 回流，形成数据飞轮
```

**蒸馏后的理解**：

- 模型给系统“脑”；
- 数据、上下文和记忆给它“认知环境”；
- 工具给它“手”；
- Agent/工作流给它“行动结构”；
- 网关给它“统一交通规则”；
- 运行时给它“安全工作间”；
- 可观测和评估给它“反馈神经”；
- 安全和人工确认给它“行为边界”。

如果缺少最后四层，得到的通常只是能演示的 Agent，而不是可持续运营的 AI 原生应用。

## 3. AI 原生应用的定义与成熟度

### 3.1 定义

白皮书将 AI 原生应用定义为：**以大模型为认知基础，以 Agent 为编排和执行单元，以数据作为决策和个性化基础，通过工具感知和执行的智能应用。**（PDF pp.28-30）

它与传统应用的关键差异是：

| 维度 | 传统应用 | AI 原生应用 |
|---|---|---|
| 逻辑来源 | 工程师预先编码 | 代码约束 + 模型运行时推理 |
| 输入输出 | 结构化、边界明确 | 自然语言、多模态、开放式 |
| 执行路径 | 相对固定、可复现 | 动态生成、具有概率性 |
| 外部连接 | API 由程序显式调用 | 模型选择工具，程序负责执行 |
| 数据作用 | 记录业务事实 | 同时构成上下文、记忆、评估集与优化反馈 |
| 质量保障 | 确定性测试 | 离线评估 + 在线评估 + 可观测 + 人在回路 |
| 安全重点 | 代码、接口、网络边界 | 还需覆盖 Prompt、模型行为、工具权限与 NHI |

### 3.2 四级成熟度

| 等级           | 状态       | 判断标准                            | 典型误区             |
| ------------ | -------- | ------------------------------- | ---------------- |
| **M1 概念验证级** | 单点功能辅助   | 验证技术可行性；AI 尚未进入核心流程             | 把 Demo 当成业务价值    |
| **M2 早期试用级** | 场景化初步闭环  | 在有限范围形成“感知-决策-反馈”闭环             | 只有功能闭环，没有评估与治理闭环 |
| **M3 成熟应用级** | 核心业务深度集成 | 多模态、复杂推理、实时决策；有企业级平台、持续部署与体系化治理 | 只追求自动化率，忽略异常与责任  |
| **M4 完全成熟级** | 企业级自适应迭代 | AI 成为业务创新引擎，可持续学习、跨域迁移并主动驱动增长   | 将愿景误当作当前普遍能力     |

成熟度要同时观察五个能力轴：**自然语言交互、多模态理解与生成、动态推理与自主决策、持续学习与迭代、安全可信**。（PDF pp.31-35）

> [!important] 实用判断
> 是否“AI 原生”不应看用了多少模型或 Agent，而应看：AI 是否进入真实业务闭环、是否产生可度量价值、是否能持续迭代，以及是否具备安全可信的运行与治理体系。

## 4. 11 个关键要素：各自解决什么问题

| 要素 | 解决的问题 | 生产级检查 |
|---|---|---|
| **模型** | 理解、推理、生成 | 是否按任务复杂度选择模型，而非所有任务都用最强模型？ |
| **开发框架** | Agent、Workflow、多 Agent 的编排 | 自主性与可预测性是否平衡？是否可调试、可替换？ |
| **提示词** | 单次任务的目标、角色、约束和格式 | 是否版本化？是否有示例、结构化输出和失败处理？ |
| **RAG** | 注入实时知识和企业私域知识 | 解析、分块、召回、重排、拒答、证据引用是否分别评估？ |
| **记忆** | 跨轮次、跨会话的连续性与个性化 | 什么可记、何时写入、何时过期、用户能否删除？ |
| **工具** | 让模型读写外部世界 | 参数校验、幂等、超时、权限、审计、回滚是否完备？ |
| **AI 网关** | 统一模型与工具接入和治理 | 路由、容灾、鉴权、限流、成本、安全是否统一？ |
| **运行时** | 承载动态、长时、有状态执行 | 是否有会话隔离、沙箱、弹性、异构算力和成本控制？ |
| **可观测** | 解释“发生了什么、为什么” | 能否从用户请求追到模型、RAG、工具、网关和推理引擎？ |
| **评估** | 把不确定性变成可度量反馈 | 是否有业务黄金指标、回归集、Bad Case 和在线评估？ |
| **安全** | 约束自主系统的风险敞口 | 是否覆盖应用、模型、数据、身份、系统、网络全栈？ |

## 5. 模型与 Agent：不要把自主性当作默认答案

### 5.1 模型选择

白皮书给出的务实策略是：**先用能力最强的模型验证业务逻辑，再逐步把简单、高频、非核心任务替换为更快、更便宜的小模型。** 生产系统往往是通用大模型与垂直/小模型协同，而不是一个模型包打天下。（PDF pp.37-38）

因此模型选型顺序应是：

1. 先定义业务任务与验收指标；
2. 用强模型建立效果上限；
3. 建立评估集和基线；
4. 按任务拆分，逐步替换为低成本模型；
5. 用网关做路由、灰度、回退与成本治理。

### 5.2 单 Agent、Workflow、多 Agent 怎么选

| 形态 | 适合 | 优势 | 主要风险 |
|---|---|---|---|
| **单 Agent** | 工具有限、目标集中、模型能力足够 | 架构简单，模型自主性高 | 工具过多时选择退化；长任务容易失控 |
| **Workflow** | 步骤明确、稳定性要求高、可拆解 | 可控、可调试、可审计 | 分支增多后编排和维护成本上升 |
| **多 Agent** | 角色专业化、需协作或动态分工 | 可分解复杂任务，独立上下文 | 通信成本、冲突、循环、责任不清、评估更难 |

白皮书区分了四种主流范式：简单 LLM 应用、单 Agent、Workflow、多 Agent；并指出当前模型能力仍有限，因此工作流和多 Agent 常被用来以工程结构弥补模型不足。（PDF pp.67-76）

**选择原则**：

- 能用确定性代码解决的，不交给模型猜；
- 能用单 Agent 完成的，不先上多 Agent；
- 对流程固定、风险高的任务，优先 Workflow；
- 只有当角色隔离、上下文隔离或并行协作带来明确收益时，才使用多 Agent；
- 从双 Agent 小系统开始，先定义职责、通信协议、冲突处理和退出条件，再逐步扩展。（PDF p.76）

## 6. 上下文工程：从“写提示词”升级为“配置认知环境”

### 6.1 提示词工程的边界

优秀提示词的基本要素是：明确角色与目标、提供完整上下文、用范例引导、定义结构化输出。（PDF pp.104-105）

但提示词无法独立解决：

- 动态长流程任务；
- 模型无状态与跨会话记忆；
- 训练截止后的新知识与企业私域知识；
- 长上下文中的“中间遗忘”。（PDF pp.105-106）

### 6.2 上下文工程的四个组成

1. **外部知识动态供给**：用 RAG 接入私域和实时知识；
2. **短期与长期记忆**：维持当前任务状态，并跨会话沉淀偏好、事实和经验；
3. **工具与能力描述**：让模型知道有哪些可执行动作；
4. **运行时上下文管理**：压缩、摘要、重排、选择和隔离信息。（PDF pp.107-108）

### 6.3 RAG 的生产链路

```text
原始文档
→ 解析与结构保留
→ 语义分块
→ Embedding 与索引
→ Query 改写/分解
→ 向量 + 关键词混合召回
→ RRF 融合
→ Rerank
→ 父子块合并/上下文重组
→ 有证据约束的生成
→ 评估与 Bad Case 回流
```

基础 RAG 是“索引 → 检索 → 生成”三阶段；生产级难点在于语义完整性、用户意图理解、语义召回与精确匹配的平衡、上下文噪声和多跳推理。（PDF pp.109-111）

白皮书推荐的优化组合包括：

- 查询改写、子问题分解和 HyDE；
- 向量检索 + BM25 关键词检索；
- RRF 多路融合；
- 交叉编码器 Rerank；
- 父子块层级索引与自动合并。（PDF pp.112-118）

未来三条演进路线是：

- **Agentic RAG**：Agent 自主判断何时检索、如何改写和是否继续检索；
- **多模态 RAG**：统一处理文本、图像、表格、音频和视频；
- **Graph RAG**：结合知识图谱，增强关系推理、证据溯源和解释性。（PDF pp.119-121）

### 6.4 记忆不是“保存全部历史”

上下文窗口有限、昂贵且有中间遗忘问题，因此运行时应使用四类策略：

- **Write**：把信息写入外部记忆；
- **Select**：只拉入当前任务相关信息；
- **Compress**：摘要、修剪，减少 Token；
- **Isolate**：用子 Agent 或结构化状态对象隔离上下文。（PDF pp.122-123）

短期记忆负责当前任务的对话、计划、工具结果和中间结论；长期记忆保存跨会话偏好、项目摘要和持久事实，并需具备提取、检索、版本与删除机制。（PDF pp.123-124）

## 7. 工具与 MCP：连接标准不等于生产可用

工具让模型从“会说”走向“能做”。模型只负责决定使用哪个工具和生成参数，真正执行仍应由外部程序完成，这种分离是安全、扩展和治理的基础。（PDF pp.52-53、126-127）

### 7.1 MCP 的价值

- 把模型与工具之间的 N×N 定制适配转为标准协议；
- 支持工具、资源和提示模板的统一暴露；
- 支持本地与远程服务，便于发现、共享与复用；
- 可用适配层把存量 OpenAPI/数据库能力转为 MCP Server。（PDF pp.129-145）

### 7.2 MCP 仍需补齐的生产能力

| 风险/缺口 | 需要的工程措施 |
|---|---|
| 工具描述或返回结果中藏有恶意指令 | 内容与指令隔离、Prompt Injection 检测、结果过滤 |
| 远程 MCP 缺少统一身份 | OAuth/机器身份、短期凭证、最小权限 |
| 工具列表过长、Token 消耗高 | 工具检索、Query 改写、Rerank，只注入 Top-N |
| 参数错误和调用顺序错误 | Schema 校验、重试边界、幂等、执行前确认 |
| 服务不稳定 | 超时、熔断、回退、SLA、健康检查 |
| 无法归责 | 调用日志、用户/Agent 身份、参数、结果与成本审计 |

白皮书的结论很准确：**以 MCP 为协议底座，叠加工具接入最佳实践与企业级安全治理，才能把“可接入”变成“可规模、可移植、可审计”。**（PDF pp.129-135）

从 0 到 1 应选择一个“小而确定”的用例，先打通业务闭环，再补安全、性能和治理，最后扩展到复杂流程。（PDF p.149）

## 8. AI 网关：把分散能力收束成统一控制面

AI 网关位于应用与模型、应用与工具、模型与模型之间，处理以 Token 为中心、高延迟、流式传输的 AI 流量。（PDF pp.55-57、157-160）

### 8.1 十项核心能力

1. 多模型代理与动态路由；
2. 多模型回退/容灾；
3. 消费者认证与权限；
4. 输入输出内容安全；
5. Token 级限流与预算；
6. 语义缓存；
7. 统一可观测；
8. MCP 代理、协议转换与治理；
9. 工具动态组装；
10. 工具智能路由。（PDF pp.161-163）

### 8.2 为什么应集中到网关

- 模型厂商和协议持续变化，需要解耦上层应用；
- 所有调用经过统一切面，才可能做成本归集、审计和全链路追踪；
- 安全、限流、缓存、灰度、回退属于跨应用公共能力，不应在每个 Agent 内重复实现；
- 多模型和多工具系统需要一致的身份、配额与策略。（PDF pp.164-169）

> [!warning] 边界
> 网关只能治理“经过它的流量”。Agent 在本地沙箱、浏览器或内网直接执行的动作，仍需运行时安全、网络隔离和业务权限系统共同约束。

## 9. 运行时：从无状态请求转向有状态会话

白皮书把 AI 负载概括为：**会话式、工具增强、事件驱动、异构算力、需要极致弹性与精益成本。**（PDF pp.195-198）

### 9.1 三类运行时

| 运行时           | 主要职责                  | 关键能力                            |
| ------------- | --------------------- | ------------------------------- |
| **模型运行时**     | 承载推理                  | 异构算力、GPU 切分、负载调度、快速冷启动、模型灰度     |
| **Agent 运行时** | 承载长任务与会话              | 会话亲和、状态持久化、冻结/恢复、Active-Idle 调度 |
| **工具/沙箱运行时**  | 执行代码、浏览器、Computer Use | MicroVM 级隔离、文件系统与凭证隔离、可观测、超时与销毁 |

### 9.2 关键转变

传统 Serverless 以“瞬时请求”为原子单位；Agent 运行时需要把包含代码、内存、文件系统和上下文的完整会话，作为可冻结、恢复和迁移的原子单位。（PDF pp.202-210）

复杂工具运行时必须同时满足：

- 强隔离：模型生成代码默认不可信；
- 有状态：浏览器、代码解释器和桌面操作需要持续会话；
- 弹性：突发任务能快速扩展；
- 经济：空闲时不为完整计算资源持续付费；
- 可观测：能还原 Agent 实际做了什么。（PDF pp.206-210）

### 9.3 成本模型

运行时计费的演进可概括为：

1. 按单次请求执行时间计费；
2. 按实例活跃区间计费；
3. 按实际资源消耗区分忙/闲，在长连接与低负载保活时减免 CPU 费用。（PDF pp.211-214）

**架构含义**：成本治理不能只看模型 Token，还要看会话保活、工具运行、GPU 利用率、网络与存储。

## 10. 可观测：从“报警”走向“解释”

监控回答“发生了什么”，可观测需要回答“为什么发生”。一个错误答案可能来自 Prompt、RAG 召回、模型路由、工具参数、外部 API 或推理引擎，必须用统一 Trace 串起来。（PDF pp.216-223）

### 10.1 三层观测

| 层 | 重点 |
|---|---|
| **应用层** | Agent 计划、工具选择、循环调用、上下文、RAG、最终答案 |
| **网关层** | QPS、RT、TTFT、Token、模型路由、限流、缓存、安全事件、消费者成本 |
| **推理引擎层** | 队列、吞吐、GPU/显存、KV Cache、TTFT、TPOT、端到端延迟 |

### 10.2 最小可观测数据契约

每次任务至少应记录：

- task/session/user/agent/model/tool 标识；
- 原始目标与约束；
- Prompt 版本、上下文来源和检索证据；
- 计划步骤与工具调用参数/结果；
- 模型路由与回退；
- 延迟、TTFT、TPOT、Token 和金额；
- 最终结果、人工确认、评估分数和失败原因；
- TraceID/SpanID，便于从结果反查整条链路。

白皮书推荐以 OpenTelemetry 统一语义与跨组件透传，并通过无侵入埋点覆盖主流框架。（PDF pp.218-224）

## 11. 评估：AI 工程里真正的质量系统

### 11.1 为什么评估是核心

传统软件对固定输入通常有明确预期；AI 应用是概率系统，同一输入也可能产生不同输出。因此评估必须从发布前测试，升级为贯穿全生命周期的持续工程。（PDF pp.246-247）

评估的基础二分法：

- **内在 vs. 外在**：语言质量/事实性，还是实际业务任务效果；
- **自动化 vs. 人工**：规模与一致性，还是专家判断与语境理解；
- **静态 vs. 动态**：固定基准，还是变化输入、模拟环境和对抗测试。（PDF pp.248-250）

最佳实践不是二选一，而是自动化筛选 + 人工复核 + 动态红队的组合。

### 11.2 LLM-as-a-Judge 的价值与陷阱

LLM 裁判把自然语言评分规则转成可扩展的评估函数，适合数据标注、回归评估、实时护栏和模型优化反馈。（PDF pp.252-253）

但必须防范：

- 位置偏见；
- 冗长偏见；
- 自我模型偏好；
- 情绪/语气偏见；
- 评分粒度过细导致随机性；
- 裁判能力上限与裁判幻觉。（PDF pp.254-255）

缓解方法包括：明确评分 Rubric、提供黄金答案和示例、交换回答顺序、多裁判投票、约束输出格式、人工抽样与红队演练。（PDF pp.255-256）

### 11.3 评估系统应交付什么

评估不应停留在“模型 A 比模型 B 高 3 分”，而要回答：

1. 哪类任务失败？
2. 失败来自模型、检索、Prompt、工具还是流程？
3. 哪些用户/场景/版本受影响？
4. 该修改什么？
5. 修改后是否通过历史 Bad Case 回归？

生产级评估链路应包含：Trace 采集 → 数据清洗/关联 → 评估模板 → 自动评分 → 聚类与根因分析 → 版本对比 → Bad Case 回流。（PDF pp.257-265）

推荐至少覆盖：

- 端到端任务成功；
- RAG 召回相关性与答案忠实度；
- Agent 规划与执行路径；
- 工具选择、参数和调用效率；
- 幻觉、毒性、PII 与内容合规；
- 延迟、成本与用户满意度；
- 关键风险动作的人工确认率与误放行率。

## 12. 安全：把外部内容当数据，不当指令

白皮书把 AI 风险划分为六层：**应用、模型、数据、身份、系统、网络**。（PDF pp.267-268）

### 12.1 Agent 带来的新增风险

- Agent 可访问网页、数据库、代码执行器和企业系统，受操纵后会成为攻击“代理人”；
- 恶意网页、表格、PDF 或工具返回中可隐藏指令，劫持工作流；
- SSRF、SQL 注入、XSS 等传统攻击会借 Agent 合法调用路径进入内网；
- Denial of Wallet 可诱导模型生成巨量 Token 或频繁调用昂贵 API；
- RAG 可能被逐步爬取，工具参数可能被劫持，NHI 凭据可能泄露。（PDF pp.269-272、281-284）

### 12.2 最小纵深防御

1. 所有外部文本、文件、网页与工具结果均标记为不可信数据；
2. 系统指令与用户数据进行上下文隔离；
3. 工具执行采用最小权限、短期凭证和明确 Allowlist；
4. 高风险动作执行前进行人类确认；
5. 限制 Token、调用次数、金额、执行时长和递归深度；
6. 代码、浏览器与文件操作在强隔离沙箱中执行；
7. 输入、推理、输出各层设置安全检测与敏感信息脱敏；
8. 记录身份、调用、参数、结果与审批，支持审计追溯；
9. 数据覆盖采集、传输、存储、访问、使用、删除全生命周期；
10. 持续扫描镜像、依赖、暴露面与横向移动风险。（PDF pp.270-287）

> [!danger] 高影响动作原则
> 只要动作会产生外部发送、写库、转账、删除、发布、审批、签约或影响真实用户，就不应仅凭模型判断自动执行；必须引入确定性规则、权限校验、幂等/回滚和人工确认。

## 14. 对实际 AI 研发最有用的落地清单

### 14.1 立项：先证明业务，不先证明模型

- [ ] 写清真实业务任务、用户、触发条件和期望结果；
- [ ] 定义成功指标、失败边界和不可接受风险；
- [ ] 用真实样本建立人工基线；
- [ ] 明确哪些环节必须人工确认；
- [ ] 评估模型调用、工具执行、运行时和人工复核的总成本。

### 14.2 原型：建立效果上限

- [ ] 先用强模型验证端到端逻辑；
- [ ] 从单 Agent 或确定性 Workflow 起步；
- [ ] 工具先做小而确定的闭环；
- [ ] 建立 Prompt、知识库、工具 Schema 的版本；
- [ ] 从第一天就保留 Trace 和 Bad Case。

### 14.3 生产化：补齐控制面与执行面

- [ ] AI 网关统一模型、工具、身份、限流、缓存与审计；
- [ ] 会话、记忆、文件系统和凭据明确生命周期；
- [ ] 高风险执行放入隔离沙箱并设置超时、配额和网络边界；
- [ ] 配置模型与工具回退，但回退不得突破原安全策略；
- [ ] 端到端 Trace 能关联用户目标、模型、RAG、工具、成本和结果。

### 14.4 验收：同时看六类指标

| 类别 | 代表指标 |
|---|---|
| 业务效果 | 任务成功率、人工节省、转化/质量提升 |
| 模型质量 | 准确、忠实、相关、格式与鲁棒性 |
| Agent 行为 | 规划正确、工具正确、路径简洁、无死循环 |
| 系统性能 | 延迟、TTFT、吞吐、可用性、恢复时间 |
| 成本 | 单任务 Token、工具/API、运行时、人工复核成本 |
| 风险治理 | 越权、泄露、误执行、拦截与人工确认指标 |

### 14.5 运营：形成数据飞轮

```text
真实请求
→ Trace 与反馈
→ 失败案例聚类
→ 判断根因（数据/Prompt/模型/工具/流程）
→ 修复
→ 历史回归
→ 灰度上线
→ 在线评估
```

这比单纯“继续调 Prompt”更接近白皮书所描述的 AI 原生工程方法。

| 观点 | 置信度 | 说明 |
|---|---|---|
| AI 原生需要模型、数据、工具、运行时、评估和安全协同 | **高：作者主张 + 工程共识** | 全书多章互相支撑，逻辑完整 |
| 生产级 AI 的核心是治理非确定性 | **高：合理归纳** | 原文分散讨论，本笔记做了跨章整合 |
| Serverless 是模型、Agent 和沙箱运行时的“最优/终极”载体 | **中：厂商主张** | 有实践案例，但替代方案与适用边界讨论不足 |
| AI 网关是所有公共能力的最佳载体 | **中高：工程上合理，但实现可多样** | 控制面可集中，执行面和业务权限仍不能只靠网关 |
| 多 Agent 是智能体发展的必然形态 | **中：趋势判断** | 多 Agent 也会增加通信、成本、评估和治理复杂度 |
| 通往 AGI/ASI 的时间与路径 | **低：前瞻判断** | 第 11 章属于愿景，不是已经验证的工程事实 |
| 文中阿里云产品实践数据 | **中：原文事实陈述** | 多为厂商案例，缺少第三方复验与完整实验条件 |

**阅读时最应避免的误用**：把厂商产品名当成架构原则。真正可迁移的是控制面/执行面分层、上下文管理、会话隔离、持续评估、纵深安全等设计思想。
