# §1 FDE 是什么（认知篇）

## 1.1 一句话定义

> **FDE = 把工程师派到客户现场，用 AI 把「通用模型能力」接进企业的「数据、流程、权限、业务结果」里，并对结果负责的人。**

**两个关键词**：**组织内部 + 业务结果**（不是在办公室做产品，是要进到企业里出结果）

**起源**：不是 AI 新造词 —— **Palantir 近 20 年前的交付模式**（内部代号 Delta）：
- **Echo 团队**（embedded analysts，懂领域的业务专家）：找痛点 + 管客户关系
- **Delta 团队**（部署工程师）：快速写原型，**质量糙但能准时交付**
- 总部把现场踩出的「**碎石路**」观察出共性 → 铺成服务后 5-10 个客户的「**柏油路**」（标准产品）

## 1.2 ⭐ 判断真假 FDE 的三个硬标准

| # | 标准 | 说明 |
|---|------|------|
| **①** | **这家公司有自有产品或平台吗？** | 没产品 = 纯人力 |
| **②** | **现场经验能沉淀成可复用能力吗？** | 不能沉淀 = 每次从零 |
| **③** | **是按业务成果定价，还是按人头/工时收费？** | 按人头 = 外包 |

> **三条都「否」= 外包。** ✅

**最大误区**：**FDE ≠ 驻场外包 / 咨询顾问**

**官方类比**（咨询 vs FDE）：
- **咨询** = 设计师出效果图，交付图纸收钱走人，落不落地是你的事
- **FDE** = 顶级装修师傅**搬来你家住**，观察你的生活习惯再边住边改，**还把经验带回公司改进标准方案、教你的家人日常维护** —— 嵌入式的、**双向价值创造**

## 1.3 FDE 五大能力模型

| # | 能力 | 关键点 |
|---|------|-------|
| **①** | **问题重构** | **客户说的不一定是想要的** —— 多问三层「为什么」，把「知识库问答」翻译成「经验传承」 |
| **②** | **快速构建** | **不是从零写代码，是选对工具+拼接+快速验证** —— 关键判断力在「**不做什么**」 |
| **③** | **组织推动** | **做完不算完，用起来才算** —— 搞定内部 champion、小步快跑、**量化价值** |
| **④** | **三重身份** | **业务专家**（策略层/SOP层）+ **AI 专家**（提示词/RAG/语义层/消幻觉）+ **产品经理**（判断能否标准化）|
| **⑤** | **结果责任** | 对「人+流程+模型+数据+治理」的闭环负责 |

**⚠️ 关键**：**工程能力排不进前三** —— 核心是**懂业务、懂组织、懂人、会驾驭 AI 做结果**

**量化价值的说法**：
> ❌ 空谈「提效」
> ✅ 「**询价从 2 天缩到 10 分钟，月省 200 小时**」

## 1.4 为什么现在火

| 原因 | 说明 |
|------|------|
| **大模型的「最后一公里」** | 现成 LLM 是通用的，企业要接进自己的数据/权限/流程/合规 —— **远程交付做不到** |
| **Agent 时代 = FDE 的 PMF 范式** | 上一代 SaaS 有标准化产品（PMF 在总部搞定）；**AI Agent 没有现成产品，PMF 必须在客户现场探索** |

**关键区别**：
> **SaaS**：有了标准化产品找客户
> **FDE 模式**：**先进客户现场找真问题，再把解决方案沉淀成产品** ✅

**中国路径判断**：
- **更可能走「产品型 FDE」**：少量前线人员进高价值场景，把经验沉淀为**评估集、行业模板、产品组件、标准工作流**
- **判断标准**：**同类项目第二次为什么更快？**
- ⚠️ **如果客户越多 FDE 必须同比例增加，那仍是人力生意**

**CIO 调研数据**：**73.3% 接受厂商提供 FDE 服务**（33.3% 非常认可、40% 愿试点）
**客户要的是**：行业型 FDE + 同行案例 + 小周期 + 阶段验收 + **帮客户沉淀内部能力**

**选根据地三标准**：
1. **你最懂的行业**（有认知壁垒）
2. **客户最愿意为 AI 付费的场景**（有明确 ROI）
3. **同行业客户密度高**（做完一家能复制到下一家）

# §2 企业 AI 落地方法论

## 2.1 ⭐ 进场三阶段（非标企业实操）

### 第一阶段：流程梳理 + AI 机会识别

**做法**：把流程从一级拆到二级、三级，每个流程看**输入输出节点**，核心看：**这个节点到底在干什么？能不能交给 AI？**

**⭐ 流程节点分三类**：

| 类型 | 是什么 | 怎么处理 |
|------|--------|---------|
| **A. 执行节点** | 人或机器去执行的工作（线下调查、生产、写报告/PPT/标书）| **最适合 AI 介入** |
| **B. 审核节点** | ⭐ **关键判断在这里** | **凡是基于明确的数据、公式或逻辑判断的审核 → 交给 AI**（更标准、更稳定）<br>**需要人的经验判断的（合规风险、违约/保密条款完整性、条款是否有利）→ 留给人工** |
| **C. 审批节点** | 涉及人的主观决策和战略考量 | **仍留人工** |

**⚠️ 最重要的一句**：
> **流程改造的关键不是把原有环节原样保留，而是逐个审视 —— 把能用数据和规则自动判定的部分变成 AI 的规则，真正需要人拍板的才留人工。**
> ⚠️ **那些「为了审而审」、或者层层加审来兜底责任的节点，可以直接删掉。**

### 第二阶段：技术验证
向客户收集**最小样本集** → 组织项目组用**敏捷方式快速做出 Demo** → 让客户有直观感受

### 第三阶段：ROI 评估 + AI 员工上线
与客户**一起算投入产出比** → 共识出「AI 员工落地规划 + 后续开发计划及范围」→ 开发上线
**上线不是结束**：建**评估系统**，随业务变化和模型升级持续保持稳定准确

## 2.2 ⭐ AI To B 落地五步法

```
① 从老板 KPI 出发，访谈业务痛点
   → 生成 6–10 个候选场景
② 四维评分排序 → 输出 Top 3 + 1 个快速验证场景
   → 产出：AI 落地场景诊断报告
③ 针对快速验证场景做两周可运行原型
   → 产出：可演示的 AI 原型 + 验证数据
④ （部署交付）
⑤ 持续监控效果、维护数据、迭代模型
   → 产出：运营仪表盘 + 持续优化机制
```

# §3 找客户与判断客户

## 3.1 ⭐⭐ 客户三层分类（决定做法、难度、报价空间）

| 层 | 特征 | 难度 | 报价空间 |
|---|------|------|---------|
| **第一层：未信息化** ⭐ **最好做，没有之一** | 流程全靠纸质单据、Excel 传来传去、微信群吼 | **最低** | 单笔小但**复购惊人** |
| **第二层：信息化** | 有系统，明确要把 AI 引入现有系统 | **骨头最难啃** | **单子肥** |
| **第三层：数字化** | 数据互通已完成，AI 核心只做**决策** | **不是一个人能接的** | 需要**团队级作战体系** |

### ⭐ 第一层为什么最好做（三条）

1. **没有历史包袱** —— 没有系统/数据/流程，**你交付的就是他们的第一个系统**；不存在对接、兼容、「我们原来的流程不能动」
2. **需求极度具体** —— 报销录票、合同归档、考勤统计，**客户一句话说清，需求冰山浮在水面**
3. **一把手拍板，链路极短** —— **老板点头=需求确认，老板满意=验收通过**，没有层层审批

### ⚠️ 第二层为什么难（三条）

1. **难在「结合点」的挖掘** —— 「我要把 AI 引入系统」**等于什么都没说**；必须做需求深挖，把业务流程一条条拆开
2. **难在「存量对接」** —— 每个系统都是雷区（技术栈？有接口吗？供应商还管吗？）；**光打通接口就可能耗掉大半工期，而报价时极易低估**
3. **难在「组织惯性」** —— 你改的每个流程背后都有一群习惯旧流程的人；**推行、培训、抵触情绪都是隐性工作量**

**⭐ 第二层的解法（管用）**：
> **私下跟老板通个气（⚠️ 绝不能写进合同），让他指定一个「不会被裁的核心骨干」来对接你，先在这位骨干的流程上跑通、站稳，再谈推广。**
> **至于客户内部怎么调整人员 —— 那是老板的事，你不参与。**

**第二层接单姿势（三条）**：
1. **先深挖，再报价** —— 坚决不能聊完第一轮就报价
2. **把「提效」量化成客户听得懂的话** —— 「原来三个人干的审核活，以后一个人复核 AI 的结果就行」
3. **边界写进合同** —— 存量系统对接范围/改造范围/不包含范围，一条条写清
   ⚠️ **信息化企业需求漂移风险最高**（每个部门都能提一嘴「能不能顺便也……」）

### 第三层
**数据互通已有人做完，AI 只做决策**：在保证准确/稳定/安全/快速前提下，把数据统计分析、个性化决策建议、预测做出来
**散活**（自动填写、流程审核、OCR、智能办公小模块）**只是配菜，主菜永远是决策**

**⚠️ 判断**：个人 FDE 或刚起步小团队 —— **这层是你努力的方向，不是现在的饭碗**

## 3.2 ⭐ 判断一家企业的 AI 化水平（看老板用什么工具）

> **不要先看他的 PPT，先看老板每天打开什么工具 —— 工具站往往就是认知水位。**

| 老板用什么 | 阶段 | 你该怎么聊 |
|-----------|------|-----------|
| **① 只用豆包** | **认知层**（刚接触） | **别谈复杂部署**，先帮他找一个小场景，快速做出看得见的结果 |
| **② 用 WorkBuddy 或豆包工作伙伴** | **部署意愿层**（已理解智能体）| 把他的意愿**变成业务流程、工具组合和交付路径** |
| **③ 用适配企业的 agent + data + FDE** | **实战部署层**（高段位） | 聊**场景优先级、系统边界和结果指标** |

## 3.3 获客与信任链

**⚠️ 不要把 FDE 获客理解成找流量** —— FDE 更接近**专业服务**，客户看到你会用几个 AI 工具，不足以把业务流程交给你。

**客户真正判断的是**：你理解他的行业到什么程度、能不能听懂他的流程、遇到问题能不能拆清楚、最后能不能交付出来

**⭐ 一个关键能力：现场学习能力**
> 你不可能提前把客户行业研究透 —— **要能一边听，一边抓重点，一边把零散信息组织成可以继续讨论的问题**

**第一轮聊完后的动作**（⚠️ 不能只停在「我回去研究一下」）：
**借助 AI 在很短时间内把听到的信息消化掉，再带着更具体的问题回来细聊**：哪个环节最高频、哪里最耗人、数据在哪、谁负责、最后怎么验收

**信任链（从小单到大单）**：
```
客户愿意找你聊 → 别停在「他要的功能」上，继续往下问
（现在流程怎么跑？最卡在哪？数据在哪？谁用？怎么验收？做成了业务上什么变化？）
→ 拆出一个「高频、清楚、能验收」的小场景做第一版试点
→ 交付后帮客户复盘（解决了什么/哪里跑通/下一步扩展哪里）
→ 后面才更愿意把更多流程交给你
```

**⚠️ 员工抵触怎么破**：
> 很多基层员工听到「提效、降本增效」，第一反应是**担心被替代** —— 心里有这担心，他就很难真的配合你梳理流程、提供资料。
> **FDE 不能只站在老板视角讲效率，也要理解员工感受**：让他们知道 AI 是先从**重复、低效、消耗人的工作**里解放他们，**让他们的经验和判断被放到更重要的位置**。

# §4 ⭐⭐ 需求（最重要的一章）

> **核心结论**：**AI 落地大多数项目失败，不是技术不行，而是需求从一开始就理解错了。**

## 4.1 为什么不能只听老板讲需求

**要追问三个问题**：
1. （为什么不是「我想要什么工具」）
2. **现在这个问题卡在哪个流程？**
3. （还有一个）

**⭐ 还要去现场看一线员工怎么做，核对数据到底发生了什么。**

**⭐【问题观察员】到一线先观察、再访谈**：
> **访谈不是找问题的唯一方式，甚至不是最好的方式。**

| # | 做法 |
|---|------|
| **①** | **先观察，不先访谈** —— 客户说的往往是「应该怎样」，**群聊记录、工作流、真实协作痕迹才是「实际怎样」** |
| **②** | 先看真实数据，再带着问题去访谈，效率和准确度都更高 |
| **③** | ⭐ **群聊是组织痛点的上下文收集器** —— 群聊里**反复出现的问题、反复@的人、反复等待的环节**，就是最真实的痛点地图 |

**问题观察员的输出标准**：
**分「问题候选」和「经验候选」两类，每类不超过 5 项**
每项包括：**名称、事实证据、重复情况、业务影响或正向结果、待确认信息、置信度**
**关键原则**：**先找证据，不急着提完整方案**；只读已授权范围；不评价个人；不替负责人决策

## 4.2 初步需求抓取（4 点，用于报价）

**⚠️ 对客户不要问「你想要什么功能」，要问「咱现在系统是怎么做的？目前卡在哪一步？」**

**初步需求抓取的 4 点**：
1. （**顺着「需求冰山」往下打** —— 客户开场说的永远是冰山尖「我要一个环境监测网站」）
2. **客户说得平静的地方是现状；音量变大、语速变快、反复强调的地方才是痛点** —— ⭐ **他说三遍的，一定是真正要的需求**
3. **复述确认**：
   > 「我理解您的意思是 —— 现在 XXX 流程全靠人工，每次要 X 天，出错还要返工，您想要一个能把审批周期压到 X 小时、并且可追溯的方案。是这个意思吗？」
   **一箭三雕**：确认理解 + 展示听懂了 + 把散乱诉求收拢成结构化需求
4. （每问一层，往冰山深处走一步，**千万不要在第一层就停下**）

## 4.3 ⭐⭐ 需求深挖五个动作（核心方法论）

| # | 动作 | 怎么挖 | 挖到底的判断 |
|---|------|--------|------------|
| **①** | **挖动机（为什么）** | 从客户最表面的诉求问起，**他答一层你再往下问一层「为什么」，一般三到五轮见分晓** | **能和业务目标对上号**，能一句话讲清「这功能为什么非存在不可」 |
| **②** | **挖场景** | **4 个要素逐个问清：角色、触发时机、要完成的任务、使用频率** | 场景具体可复述 |
| **③** | **挖边界** | ⭐ **正向问验收标准，反向问排除项** | **产出：验收标准 + 边界清单** |
| **④** | **挖异常**（核心需求都过一遍）| 见下方五问 | 异常清单 |
| **⑤** | **挖约束** | 规矩、合规、国产化、涉密 | 约束清单 |

**⭐ 异常必问五连（照问就行）**：
```
① 空数据：没数据怎么显示？
② 数据超量：涨 10 倍扛得住吗？扛不住怎么办？
③ 依赖中断：上游接口/数据源断了怎么办？
④ 操作出错：用户填错/操作错怎么办？能撤回吗？
⑤ 安全合规：数据涉密等级怎么定？要不要过国产化？展示脱不脱敏？数据留多久能删？
```

**⭐ 一句话收口公式**：
> **这条需求，就是让【某角色】在【某场景】下办成【某个目标】，做到【什么边界】，出事了【怎么兜】，同时受【哪些规矩】管着。**

**问「来龙去脉」的话术**：
> 「这个需求的来龙去脉是怎样的？**线下有没有对应的单据或者流程？**」

## 4.4 真需求 vs 伪需求（3 个判断标准）

| # | 标准 | 做法 |
|---|------|------|
| **①** | ⭐ **看行动不看说法** | 客户说「这个很重要」，**但他有没有为此花钱/花时间/派人？没有行动的需求都是伪需求**<br>例：说「客服效率低很重要」，**但连一个专门客服负责人都没有、也没花过钱优化** → 大概率伪需求 |
| **②** | ⭐ **追到底层动机** | 客户说「我想要 X」，**连续问 3 个「为什么」** —— 追到**第 3 层还站得住的，才是真需求**；**追到第 2 层就说不清楚，说明客户自己也没想明白** |
| **③** | （结合场景验证）| — |

**⭐ 伪需求的典型表现（听到就要继续追问，不要记下来就当需求）**：
- 「AI 听起来不错」
- 「同行都在做」
- 「老板让我了解一下」
- 「提升效率」（**说不出具体数字**）

## 4.5 访谈：4 项必做准备 + 5 种追问

### ⭐ 访谈前 4 项必做准备

| # | 准备 | 关键 |
|---|------|------|
| **①** | （材料准备）| — |
| **②** | **准备问题清单** | 按「**行业→KPI→痛点**」框架，**提前写好 10-15 个问题 + 每个问题的追问方向**<br>⚠️ **清单是底线，不是限制** —— 可灵活调整，**但不能没有清单就上场** |
| **③** | **确认参会人** | 必须确认访谈对象是谁（老板/业务负责人/IT/一线员工）—— **不同角色问不同问题**<br>⭐ **理想情况：老板 + 一个一线员工都在场**（既听到战略 KPI，也听到执行层面真实痛点）|
| **④** | **设定访谈目标** | 这次结束**必须拿到什么**？（如「3 个 KPI 的现状和目标」「2 个痛点的强度评分」）<br>⚠️ **结束前 5 分钟对照目标检查，没拿到赶紧补问** |

### ⭐ 信息采集：KPI 三问（诊断的地基）

```
① 是什么：老板今年最在意的 1–3 个指标是什么？（毛利率/人效/客户续约率/合规事故数/获客成本）
② 现状与目标：现在是多少？目标是多少？（例：人效现在每人每月 120 billable hour，目标 150）
③ 差距原因：差距主要由什么造成？（人手不够/流程太慢/出错太多）← 这步直接指向后续 AI 场景
```

**⭐ 话术（客户说不出 KPI 时）**：
> **「老板最近在会上反复提什么？」「什么事让老板睡不着觉？」**
> **—— KPI 往往藏在老板的焦虑里。**

**痛点强度打分**：
> 「这个痛点如果 1–5 分打分，您觉得是几分？**为什么？**」
> ⚠️ **然后用标准校准客户的回答** —— 客户说 4 分但实际只是偶尔困扰，**要追问校准**

### ⭐ 访谈 5 种追问技巧

| # | 类型 | 话术 |
|---|------|------|
| **①** | **为什么追问** | 「**为什么**这个问题这么重要？」→ 找底层动机 |
| **②** | **具体追问** | 「**能举个最近的例子吗？具体是怎么发生的？**」→ 从抽象到具体 |
| **③** | （澄清追问）| — |
| **④** | **对比追问** | 「**和去年/和同行比**，这个问题有什么变化？」→ 找趋势和差距 |
| **⑤** | **假设追问** | 「**如果这个问题明天就解决了，你第一件事会做什么？**」→ 找真正的价值锚点 |

**⭐ 关键原则**：
> **客户说「我想要 X」，不要记 X**，要追问「**为什么想要 X**」「**X 解决了什么问题**」。
> **X 是解决方案，问题才是需求。**

## 4.6 ⚠️ 访谈 5 个最容易踩的坑

| # | 坑 | 说明 |
|---|-----|------|
| **①** | **引导性提问** | ❌「你是不是觉得客服效率很低？」→ 客户会顺着你说<br>✅ 问「客服这块**现在情况怎么样**？」让客户自己描述 |
| **②** | （只听需求不核对数据）| — |
| **③** | ⭐ **只听老板不听一线** | **老板说的是「应该怎样」，一线员工说的才是「实际怎样」**<br>⚠️ **必须访谈至少 1 个一线执行者**，否则拿到的都是理想化需求 |
| **④** | **过早给方案** | 客户一说问题你就说「AI 可以解决」→ 打断真实表达、错过真正的问题<br>**访谈阶段只听不说方案，方案是诊断完的事** |
| **⑤** | **忽略政治因素** | 客户说「这个部门效率低」，可能是**部门负责人之间的权力斗争**<br>⚠️ **AI 解决不了组织政治问题，但政治因素直接影响项目成败**<br>**要留意「谁支持、谁反对、谁的利益会受损」** |

## 4.7 ⭐ 销售 Agent 案例：FDE 与需求方沟通的 10 个关键问题

> **关键**：不能马上问「想用哪个模型、要不要私有化知识库、有多少文档」—— **先别急**，因为「销售 Agent」可能是整理会后纪要、可能自动跟进线索出报价、甚至代替人推进商机，**这几件事根本不是同一件事**。
> **建议按优先级从高到低问**：

| # | 问题 | 关键提示 |
|---|------|---------|
| **①** | **上线后这个 Agent/流程必须改变什么？业务结果怎么量化？** | ⚠️ **别回答「提升效率、体验更智能」等车轱辘话**<br>✅ 要说「**把报价等待从两天缩到半天**」「**让标准咨询 5 分钟内办完**」<br>⚠️ **没有量化指标和当前基线，做完也没人知道值不值得继续** |
| **②** | **现在这件事有多高频？** | 是销售每天花两小时翻资料，还是一个月才碰到一回？<br>**把人工时间、漏单、返工、投诉的账和发生频率摆出来**，才知道该不该排进第一批 |
| **③** | **真实流程是什么？** | ⚠️ **不要只听流程图，也别只听负责人讲理想流程** |
| **④** | **关键确认实际发生在哪里？** | ⚠️ **审批写在系统里，不代表事情真在系统里办完** —— **很多关键确认其实发生在微信、钉钉聊天里** |
| **⑤** | **正常流程之外，最常见的例外是什么？哪一步只能靠人判断？** | ⭐ **第一版最怕什么都想做**<br>**能写成规则的才有机会交给 AI；靠关系判断和权责拍板的节点，先不要假装能自动化** |
| **⑥** | **AI 的权限边界到哪？** | ⚠️ **AI 生成一份草稿报价单 vs 直接给客户发报价单，风险不是一个级别**<br>要定清：AI 能查资料/给建议/生成待审核内容，**哪一步可以写回正式系统、发出正式消息？低置信度交给谁？** |
| **⑦** | **样本集在哪？** | ⭐ **如果需求方不愿意拿出样本，这个项目建议转头就走**<br>**没真实数据，做出来的大概率只是一个好看的 Demo** |
| **⑧** | ⭐ **提需求的人是不是承担结果的人？** | **提需求的人经常不是最后承担结果的人** |
| **⑨** | **一线员工本来在哪工作？** | 在 CRM、邮箱还是微信群？<br>⚠️ **如果新方案逼着大家多开一个入口、多登一次账号，采用成本也要算进项目** |
| **⑩** | **下一步的具体安排是什么？** | 第一次会不必问完所有细节，**但不能只留一份空泛纪要**<br>✅ 约定下周走一次真实流程：**谁提供 50 个脱敏案例？谁确认接口和数据边界？哪天让 IT 负责人进来？** |

**⭐ 为什么 FDE 必须在现场（重要洞察）**：
> **通过调研问答，大部分得到的是理论化、标准的「完美流程」，但实际工作中有很多例外。**
> **如果不跟老员工在现场一起跑一次流程，你得到的只是标准的理想画面，也不知道哪些是表里不一的情况。**
> ⭐ **更重要的是：你在现场一起做事，对方才可能把你当伙伴**（因为一起经历过一个流程）。
> **如果你只是单纯去调研，对方会把你当成指手画脚的老师，没有义务告诉你过程中的例外和坑。**

# §5 场景挖掘与诊断报告

## 5.1 ⭐ AI 最适合解决什么问题（5 个判断标准）

| # | 标准 | 说明 |
|---|------|------|
| **①** | （高频重复）| — |
| **②** | **规则相对明确** | 有标准流程或判断依据，**不是纯靠灵感创造力**（如质检、合规检查、格式转换）<br>**规则越明确，AI 准确率越高** |
| **③** | （有数据基础）| **核心业务数据已在线化**（至少有 Excel/系统记录），不是全靠人脑和纸质单据 |
| **④** | ⭐ **容错率较高** | 出错有人复核，**不是零容错的生死决策**（如辅助诊断、风险标注、初稿生成）<br>**AI 第一版往往是辅助人，不是替代人** |
| **⑤** | （可闭环验证）| — |

> **判断标准**：**同时满足 3 条以上，就值得做；一条都不满足，别浪费时间。** ✅

**⚠️ 反面清单（五个常见陷阱）**：
- ❌ **用技术反推场景**（「我们有大模型，能干点啥？」→ **必然落到玩具**）；**必须从 KPI 和痛点出发**
- ❌ **忽略数据与权限**（原型做出来却拿不到数据，**交付即翻车**；涉密、无权限、数据散落都是硬约束）
- ❌ **评分拍脑袋**（每个维度的分数必须有访谈依据；**Data=4 就要说清有什么数据、在哪、质量如何**）
- ❌ （不挖需求就报价）
- ❌ （范围不写边界）

## 5.2 ⭐ 场景改写四步法（从通用场景到客户真实流程）

```
① 还原客户真实流程：让客户描述这个任务现在怎么做
   （谁来做、用什么工具、花多少时间、输入是什么、输出是什么、中间有哪些环节）
② 定位 AI 能介入的环节
   （在真实流程中找「重复、规则明确、耗时多」的环节）
③ （判断哪些必须留给人）
   例：写标题和卖点描述是重复劳动 → AI 批量生成
       ┃ 但确定产品核心卖点需要人的判断 → AI 只能辅助
④ （改写原则）⭐ 一个好的场景描述必须包含三个要素：
   ── 输入是什么、AI 做什么、输出给谁用
```

**⭐ 一个精彩例子（AI 发现不了「人才能感知」的点）**：
> 除皱产品的卖点，最终沟通核心不是「除皱」本身，而是：
> **「当一个姑娘决定在所有的场合都能放肆大笑、放肆哭、放肆地表现自我时，它给了姑娘们在这一刻可以放肆做自己、不用担心皱纹的底气。」**
> **即使 AI 发现了这个点，也需要人来判断 —— 只有人对场景才是足够敏感的。**

## 5.3 ⭐⭐ 四维评分（场景优先级怎么打分）

**每个场景按四维打分，每项 1–5 分。⚠️ 评分必须有依据，不能拍脑袋。**

| 维度 | 权重 | 判断依据 |
|------|------|---------|
| **痛点（Pain）** | ⭐ **0.35** | 看这个场景**直接关联的 KPI 有多重要** + 痛点强度<br>**5 分**=直接影响核心 KPI、老板级痛点、不解决会出大事<br>**1 分**=锦上添花、边缘流程、做不做都行<br>**依据来自一线洞察 + 访谈**（客户说的 KPI 现状、目标差距、痛点强度打分）|
| **ROI（杠杆）** | ⭐ **0.25** | 第二重要 |
| **Data（数据就绪）** | **0.20** | 三问：**有没有数据？数据质量怎么样？有没有权限？** |
| **Feasibility（可行性）** | **0.20** | **4–5 分**=标准 LLM + agent 可解，集成简单，无需部署模型<br>**3 分**=需接入复杂业务系统但有 API<br>**1–2 分**=需部署模型/强实时推理/系统无接口只能爬虫 |

**⭐ 一条硬规则**：
> **Feasibility ≥ 4 意味着「用标准 LLM + Agent 就能解决」**（不需部署模型或复杂集成）
> **—— 这样才能保证两周内跑出原型。** ✅

**评分产出的三档**：
| 档 | 含义 |
|---|------|
| **Tier A** | 快速验证场景（0–2 周）|
| **Tier B** | 有价值但**现在做不了**（需前置条件）→ 写成 **Roadmap** |
| **（低分）** | 暂不做 |

**⭐ Roadmap（路线图）设计**：
- **定义**：Tier B 场景的分阶段实施计划 —— **回答「这些有价值但现在做不了的场景，什么时候、在什么条件下可以做」**
- **按时间线排**：快速验证场景（0–2 周）→ 第二个 Tier A 场景（1–3 月）→ Tier B 按前置条件满足顺序（3–12 月）
- **⭐ 找飞轮**：例「客服质检积累的话术库，可以喂给销售陪练场景」
- 示例：第一个月客服质检与话术陪练（Tier A）→ 第二个月选品与评论洞察的飞轮（Tier B，需先完成评论数据归集）

## 5.4 ⭐ 诊断报告（FDE 进场调研后的第一份正式交付物）

**三个作用**：① 把零散调研发现**结构化**，让客户看到「你真的懂我们的业务」② **用数据和排名说话**，避免「我觉得哪个场景好」的主观争论 ③ 给出明确下一步，**推动客户从「聊聊」走向「动手做」**

**四段结构**：
| # | 段落 | 要点 |
|---|------|------|
| **①** | **背景摘要**（半页纸）| **行业和业务模式**：一句话定位客户是做什么的<br>**关键 KPI**：客户最在乎的 1-3 个指标，写清现状和目标（如「客服响应时长：现状 48 小时 → 目标 2 小时」）<br>**痛点强度**：用具体数字或案例（如「每月因合同审核延迟导致的订单流失约 200 万」）|
| **②** | ⭐ **场景排名表**（核心，用数据说话）| — |
| **③** | ⭐ **推荐快速验证场景** | 写清：**场景名称、一句话商业逻辑、可量化的成功指标、两周原型交付计划**<br>**这部分是推动客户买单的关键** —— 「我们建议先做这个，两周就能看到效果」 |
| **④** | **风险与数据缺口** | **坦诚说明不确定性** |

**⭐ 写法要求**：
- **用客户的语言，不用技术黑话**
- **每个结论都要有数据或案例支撑**
- **报告控制在 5-8 页**（太长没人看）
- ⚠️ **结尾一定要有明确的「下一步建议」**，不能让客户看完不知道该干嘛

**⭐ 诊断成功的标志**：
> **客户看完报告后能立刻说「先做这个」，并且知道为什么先做这个、做了能得到什么、有什么风险需要提前解决。**
> ⚠️ **如果客户还在犹豫做哪个好，说明诊断不够聚焦，需要回到第一步重新访谈。**

## 5.5 ⭐ 数据/权限缺口（AI 落地的真正杀手）

**发现了怎么处理**：
```
① 列数据需求清单：对每个场景，列出做这个 AI 需要什么数据
   例：合同审查需要（a）标准合同模板库（b）历史合同及审查意见（c）风险条款规则库
② 逐项核对现状：对每项数据问 —— 现在有没有？在哪里？格式是什么？能不能访问？质量怎么样？
③ 估算补齐成本
   例：缺少标准模板库 → 需 1 周整理；合同无权限 → 走 IT 审批预计 3 天；数据质量差 → 人工标注 100 份约 5 人天
```

**⚠️ 关键原则**：
> **数据和权限缺口是 AI 落地的真正杀手，不是模型能力。**
> **很多原型做出来了却拿不到数据，交付即翻车。**
> **所以必须在诊断阶段就把缺口摆到台面上，并评估补齐成本。**
> ⭐ **如果一个 Tier A 场景的数据缺口需要 1 个月才能补齐，那它就不适合做快速验证场景。**

**⭐ 数据的六个认知（为什么数据是 AI 的魔鬼）**：
| # | 认知 |
|---|------|
| ① | （数据决定下限）|
| ② | （先有数据观）|
| ③ | ⭐ **不同时间线的数据权重不同** —— 昨天的报价、上个月的库存、3 年前的客户画像不能同一权重。**数据不是越多越好，关键是知道什么时间的数据更有价值** |
| ④ | （口径要先定）|
| ⑤ | ⭐ **数据缺失、重复、过期和口径不一致** —— **缺一个字段可能断掉整个流程，错一个单位可能让老板做出错误判断** |
| ⑥ | ⭐ **数据权限和数据边界** —— 什么数据可被模型读取、什么只能脱敏、什么必须留在原系统？**这不是后期补丁，而是 AI 一开始就要设计的系统边界** |

**⭐ 一句话**：**先判断数据从哪里来，再判断数据是否可信；先定义口径和权重，再谈模型。**

# §6 商业与报价

## 6.1 ⭐ 老板为什么愿意为 AI 付钱（四类理由 + 三个心理）

### ⭐ 四类付费理由（**判断标准：能不能归到这四类中的某一类**）

| # | 类型 | 判断标准 | 典型场景 |
|---|------|---------|---------|
| **①** | **省钱（减人头/费用）** | **能不能直接减少人头/费用？** | 客服从 10 人减到 3 人、数据录入从外包转 AI、文档审核从法务转 AI 初审 |
| **②** | **增效（同样的人产出更多）** | 同样的人能不能产出更多？ | 销售跟进客户 20→50、研发效率+30%、运营内容 5 条→50 条 |
| **③** | **避损（减少出错/罚款）** | 能不能减少出错率、避免罚款/损失？ | AI 合同审核发现人工漏掉的风险条款、财务异常检测提前发现欺诈、质检减少次品 |
| **④** | **增收（直接带来收入）** | 能不能直接带来更多收入？ | 智能营销、线索挖掘与评分、个性化推荐、定价优化 |

> ⚠️ **一个 AI 场景如果不能明确归到这四类中的某一类，老板大概率不会为它付费。** ✅

### ⭐ 三个底层心理动机（穿透「降本增效」的表层）

| 动机 | 说明 | 排序 |
|------|------|------|
| **① 恐惧** | 不做会死/被淘汰 | 第一 |
| **② 贪婪** | **做了能赚更多** —— 「做得好就能超越同行」的诱惑 | 第二 |
| **③ 从众** | **同行都在做** —— 不做显得我落伍了、不重视技术 | 第三 |

## 6.2 ⭐ 诊断要不要收费

**常见三种顾虑**（很多 FDE 刚入行心里没底）：
① 觉得诊断是售前应该免费，收费客户就跑了 ② 觉得还没做出成果，不好意思收钱 ③ 担心客户说「你们不就是聊聊吗，这也要钱？」

**⭐ 结论**：
> **提炼需求、梳理根因、定义问题边界，是核心价值，应收钱 —— 相当于一次商业诊断。**
> **根据清晰的需求选、建、调工具，相对标准化，溢价有限。**

**为什么该收**：
- **你帮客户避免了一个错误方向，这个价值远大于后面的实施**（⚠️ 大多数项目失败是因为需求从一开始就理解错了）
- **帮客户看准「钉子在哪」是第一位的** —— 因为他们知道 AI 很重要，**但不知道业务流程里哪个环节最值得改造**
- 客户付费了**才会认真配合访谈、提供数据**，诊断质量才有保障
- 诊断阶段就建立了「**我是专业顾问**」的定位，而不是免费干活的
- **筛选掉蹭方案的客户**

**⭐ 诊断怎么收费：5 个实操建议**

| # | 建议 |
|---|------|
| **①** | **收费模式**：用**固定费用的项目制诊断**（需 1–2 周完成）<br>⚠️ **不要按天收费** —— 按天会让客户觉得你在磨洋工 |
| **②** | （先定义交付物）|
| **③** | ⭐ **开口话术**：<br>❌ 不要说「我们要收诊断费」<br>✅ 要说「**我们先做一个 2 周的诊断项目，交付一份场景诊断报告和优先级建议，费用是 X。如果后续合作，这笔费用可以全额抵扣。**」 |
| **④** | **抵扣策略**：诊断费可抵扣后续实施费用 —— **这样客户觉得反正后面要做，诊断等于免费，你也筛选出了真正有诚意的客户** |
| **⑤** | **不付费的客户怎么办**：连诊断费都不愿付的，说明要么没诚意、要么没预算、要么不相信你的价值 —— **这样的客户即使免费诊断了，后面也很难成交** |

**⭐ 一句话**：
> **敢不敢收诊断费，本质上是你相不相信自己的诊断有价值。**
> **当你真的能帮客户看准钉子在哪，收费是理所当然的。**

## 6.3 ⭐⭐ FDE 报价四级（市场很混乱，先判断客户为什么买单）

| 级 | 你做什么 | 卖的是什么 |
|---|---------|-----------|
| **① 诊断收费** | 业务访谈、流程梳理、数据盘点、AI 场景判断 | **卖的是判断，不是代码** |
| **② 方案收费** | 已找到关键问题，能拿出业务方案、产品原型、技术路线、投入产出测算 | **客户买的不是一份 PPT，而是一条少走弯路的路径** |
| **③ 部署收费** | 系统接入、流程打通、权限配置、测试上线、团队培训 | 按人天/阶段/里程碑<br>⚠️ **只会部署的人价格通常最低，因为替代性更强** |
| **④ 结果收费** | 对效率提升、成本下降、转化提高、交付结果负责 | **报价不应只绑工时，要和项目价值/节省成本/新增收益挂钩** |

**⭐ 怎么判断自己属于哪一档**：
> **报价混乱不是因为市场没标准，而是因为很多人把不同层级的服务混在了一起。**
> **一个简单判断方式：能打通全流程 → 按项目收费。**

**⚠️ 最常见的商业错误：还没收费就把方案做完了**
> 客户说「你先帮我看看」→ 一看变成业务访谈 → 再一拆变成流程方案 → **最后一写连 MVP 和报价都出来了** ⚠️

## 6.4 ⭐⭐ 避免被白嫖：三个关键原则

| # | 原则 |
|---|------|
| **①** | ⭐ **免费只做诊断，不做交付** —— 可以帮客户判断卡点、评估价值、确定方向，**但不要免费画完整架构，更不要直接写出能运行的方案** |
| **②** | ⭐ **把工作拆成阶段** —— **诊断是诊断的价格，方案是方案的价格，MVP 和部署是交付的价格**；每一步都有明确的产物、时间和验收标准 |
| **③** | ⭐ **先收启动款，再打开深度权限** —— **真实数据、业务流程、系统接口和现场协同都是交付资源，不是聊天时顺手送出去的资料** |

**⭐ 最关键的一点**：
> **不要按「陪客户聊了多久」报价，要按「帮客户减少了多少成本、试错拿到了什么结果」报价。**
> **FDE 不是廉价外包，也不是免费顾问 —— 你卖的是判断、方案、部署和结果。**

## 6.5 ⭐ 报价的成本评估（4 点注意）

**⚠️ 报价前必须先做成本评估**（不是直接出报价）

**四个注意**：

| # | 注意 |
|---|------|
| **①** | （按功能清单逐项拆）|
| **②** | **报价不是只算写代码、做对接和实施的钱** —— 要**把整个项目从头到尾过一遍**（从设计一路算到运维），**中间有要花钱采购的，特别是 AI 算力，也得一并记进去** |
| **③** | ⭐ **成本评估要覆盖这几块**：<br>**设计**（产品、架构、数据库）· **功能点**（前后端、Skill、Agent 的设计实施、AI 接入、对外接口）· **采购**（中间件、数据库、服务器、授权）· **测试**（功能性、联调、第三方）· **部署**（外网/内网、国产化）· **运维**（出差、驻场）|
| **④** | ⭐⭐ **算力成本不要打包进固定费用里**<br>**服务器、数据库这些是固定成本，可以算进报价；但模型调用的算力消耗是波动的** —— 这个月一千，下个月客户用量上来可能一万<br>⚠️ **打包进去必然后期扯皮**<br>✅ **正确做法：报价里含一部分算力额度，超出部分让客户单独充值、自己承担** |

**⭐ 算账手法「先加后减」**：
> **先按功能清单和需求说明把所有成本加起来，拉一份完整的成本评估；**
> **但在这之前，先用提醒的方式把技术难点、采购成本、运维差旅这些一项一项摆出来跟客户过一遍，确认不要的再减掉。**
> **这样磨出来的成本评估和报价才贴地气。**

**⭐ 单价参考（没标准答案）**：
> ⚠️ **别拿「月收入 ÷ 22 天」硬套** —— 现在 AI 辅助编程普及了，**懂业务又会用 AI 的新手能把价格压得很低，纯拼技术只会越来越不值钱**
> ⭐ **参考：按你每天收入的 1/4 到 1/2 来报**

**⭐ 报价单至少写清六项**：
```
① 本次交付什么
② 客户需要提供什么
③ 预计周期
④ 确认和验收方式
⑤ 试运行支持多久
⑥ 哪些内容不包含
```

**⚠️ 重要**：报价单上的费用 = **成本评估 + 上浮**，**浮出来的就是利润**

## 6.6 ⭐ 企业 AI 应用三层（标准化程度决定 FDE 介入深度）

| 层 | 内容 | FDE 介入 |
|---|------|---------|
| **第一层** | **员工个人用通用工具**（写周报、润色邮件、写文案初稿、写代码）| **不用介入**，员工自己就能做，企业甚至不用额外花钱 |
| **第二层** | **企业统一采购标准产品**（发票识别、会议纪要、智能客服、企业知识库问答、垂直 SaaS 如律所合同初审）| **顶多做培训答疑这类伴随式服务** |
| **第三层** ⭐ | **基于企业自己的数据、独特业务流程、自有系统开发的 AI 应用** | ⭐ **只能靠定制，这才是 FDE 深度介入的地方** |

> **规律**：**工作流程越标准，FDE 参与得越浅；工作流程越非标，越需要 FDE 深度介入。** ✅

**第三层实例**：制造业给非标产品报价（要结合自家图纸和成本逻辑，帮销售尽快给出准确报价）

**⚠️ 重要提醒**：
> **交付结果，不交付过程** ——
> 真正干活的 AI 员工，不是「做了几个 agent、做了什么 skill、用的谁家大模型、怎么跟 IM 交互」。
> **至于这个技能怎么做的、背后用了什么，完全不用给他看，甚至都不用让他知道。**
> **交付结果，不交付过程，反倒能省很多事儿的同时还能多挣钱。**
>
> ⚠️ **如果要给客户长期使用**，在做法稳定后可以尝试更符合使用成本的模型 —— **但不要只比较模型价格，要看完整交付的效果和总成本**。

# §7 交付（从需求到落地）

## 7.1 ⭐ 选型（交付形式）

**核心判断**：
> **不要先问「现在最火的产品是什么」，而要先问「这个需求最适合用什么方式交付」。**
> **交付越轻，通常越快、越便宜；交付越重，通常越能融入业务，但建设和维护也越多。**

**⭐ 当前阶段建议（重要）**：
> **无论个体还是团队，推荐选「轻的、快的」** ——
> **即使这样会让你少赚很多，也务必把交付时间和周期压短。** ✅

**基础知识：几种交付形式**

| 形式 | 是什么 | 适合 |
|------|--------|------|
| **提示词** | 告诉 AI 任务要求、参考资料、做事方法、可用的「手脚」 | 一次性任务 |
| **知识库** | 给 AI 可反复使用的业务资料 | — |
| **Skill** ⭐ | **把一套反复使用的方法、模板和工具说明打包**，让 AI 知道这类工作该怎么做 | **反复出现、方法已验证的任务 → 当前最佳、较轻的交付方式** |
| **Workflow** | 提前把步骤和先后顺序定好，AI 按路线执行 | **步骤固定、变化少、要求高精度和低成本** |
| **Agent** | 给目标 + 可用工具，由它根据现场情况判断下一步 | **过程变化多，需要 AI 自己判断** |

**⭐ 关键认知**：
> **这些交付形式不是从低到高的升级关系，而是可以组合的零件。**
> 真实项目中两者经常一起用：**确定的步骤交给 Workflow，不确定、需要判断的环节交给 Agent**；**Skill 和知识库也常常放进 Workflow 或 Agent 里使用**。

**选型判断树**：
```
步骤固定吗？
├─ 步骤清楚、变化少、要求高精度和低成本 → 优先 Workflow
└─ 情况经常变化 → 考虑 Agent
     └─ 如果还要跨系统找数据、发现异常并追问负责人 → 才可能需要 Agent + 工具
```

**⭐ 其他判断**：
- **自己偶尔处理一份材料** → 现成 Agent 就够
- **多人经常重复同一项操作、希望有固定按钮/表单/展示方式** → 考虑做**小工具**（Chrome 插件 / HTML 页面）
- **用户只有几个** → ⭐ **直接用 Skills 交付是最推荐的**
- ⚠️ **Workflow 在当前场景的必要性下降了**（很多以前的工作用 Agent + Skills 就能完成）—— **但它仍要讲，因为很多 FDE 场景需要「产品化」，即这个工具在组织内使用、需要很多人同时使用；而客户端 Agent 和 Skills 只能作为个人工作终端**

**⭐ FDE 的价值**：
> **不是把所有 AI 能力都堆上去，而是理解真实需求，用合适的产品和合适的交付方式，把问题可靠地解决。**

**⭐ 传统需求分析 vs FDE 深入业务**：**需求是截图，流程是影片**

## 7.2 工具地图（初级 FDE 常用）

| 类别 | 工具 | 用途/选它的原因 |
|------|------|---------------|
| **桌面 Agent** ⭐ | **WorkBuddy**（腾讯）| **目前企业 FDE 常用的交付工具 —— 核心不是它有多好用，而是它合规**<br>把任务要求告诉它，让它读指定文件夹的材料，完成整理/分析/文件生成；**方法稳定后可存成 Skill 复用** |
| **办公生态** ⭐ | **飞书 + CLI** | **让资料、处理结果和团队协作留在同一个工作入口**<br>业务人员沿用熟悉的文档和表格，减少来回导出、复制、维护多份材料 |
| **小工具开发** | **Vibe Coding**（自然语言写代码）| 初级 FDE 从 **Chrome 插件**和 **HTML 网页小工具**开始，这是**项目落地中最常见使用的方案** |
| **工作流平台** | **FastGPT** | 知识库 + 工作流，把资料检索/模型处理/条件判断连接起来<br>⚠️ **初级小白不必深研；只有服务有规模、需协作、需极致降本时才用到 workflow** |

| **笔记** | Obsidian | ⚠️ **本课程不建议初级阶段专门学** —— 学习曲线陡、大部分人会吃灰；**且 Agent 工作场景里文档首先要方便 Agent 读取** |

**⭐ 关于代码托管**：**GitHub** = 存放项目代码、记录修改历史、支持多人协作的平台
- **仓库（Repository）** = 「带版本记录的项目文件夹」
- ⚠️ **文件在电脑里改好还要推送，GitHub 上才会出现修改**

## 7.3 ⭐ 开发（Rules 五原则 —— 写规则的核心）

**为什么需要 Rules**：
> **AI 就像一个能力很强、但完全不了解你项目习惯的「新员工」。如果你不做任何约束，它就会按自己的默认习惯工作。**

**⭐ 核心标准：可验证**
> **任意取一段 AI 生成的代码，你都能明确判断它是否遵守了这条规则。**
> **如果连你自己都无法判断 AI 是否遵守，那 AI 也一定无法遵守 —— 问题不在 AI 的理解能力，而在于规则本身写得模糊。** ⭐

**⭐ 五条原则**：

| # | 原则 | 例子 |
|---|------|------|
| **①** | **具体** | ❌「代码要简洁」（多简洁才算？）<br>✅「**每个函数不超过 30 行**」 |
| **②** | **可验证** | ❌「写好代码」<br>✅「**启用 TypeScript strict 模式**」（打开配置文件就能确认）|
| **③** | **有优先级** | 规则冲突时提前替 AI 决策：「**性能和可读性冲突时，优先保证可读性**」 |
| **④** | **有例外** | ❌一刀切「统一使用箭头函数」<br>✅「统一使用箭头函数，**除非是第三方库的回调**」 |
| **⑤** | （可检查）| 「代码要优雅」等于没说；「**Service 方法必须加事务注解**」才算数 |

**⭐ 一句话**：
> **规则写得越像「检查清单」，AI 的行为就越接近规范的资深工程师；**
> **规则写得越像「口号」，AI 的表现就越像自由发挥的实习生。** ✅

**⭐ 使用建议**：
- 规则文件**不必全堆在一个文件**，**按类型拆成多个 .md** 便于维护
- **写代码之前先让 AI「认识」你的项目**：用 `@Folders src` 让 AI 看目录结构、描述技术栈，**再告诉 AI 后续回答要保持与现有模式一致**
- ⚠️ **上下文管理直接影响生成代码的准确率** —— 即使 1M 上下文，**超过特定阈值大模型的回答照样会飘**

**其他开发要点**：
- **MCP**：大模型需要 MCP 查询数据库拿真实表结构和数据（**而不是凭记忆瞎猜**）；**相当于给大模型装上手和脚**
  ⚠️ **大多数场景不需要自己开发 MCP**（网络现有服务够用）
  ⚠️ **MCP 安全底线两条**：① **开发阶段一律默认只读** ② **交付阶段一旦涉及写入、迁移、发布，必须走专门账号并由人工确认**
- **架构设计**（AI 时代更重要）：
  > **AI 能在 5 分钟给你一个能跑起来的脚手架，但企业工程化要的不是「能跑」，而是「能扛」** —— 扛得住并发、数据一致性、安全审计、三年五载的人员更替和需求变更（**这也是能否产生复购的重要原因**）
  > **架构设计就干两件事：① 提前消化关键的不确定性 ② 替后续全部开发工作立下规矩、划出边界**
- **Skill 开发**：
  > **不需要一个什么都能干的「全栈工程师」式 Skill** —— **一个能包揽所有工作的技能，本质上已经不是 Skill 能承载的了，那是 Agent（甚至 Agent 团队）**
  > **Skill 的定位恰恰相反：把一件「可流程化、职责单一、边界稳定」的事，交给 AI 反复执行，且每次都能输出符合预期的结果**
  > ⭐ **核心就四个词：流程化、职责单一、稳定、可复用**
  > **创建方法**：① 先用 AI 手工改通第一个 → ② 立刻把这次成功经验「固化」（提炼输入 → 标准化处理流程 → 迭代打磨）→ ③ 开新对话窗口，不断用真实场景「喂」它，**直到它能稳定输出相对固定的结果为止**
  > ⭐ **模型选择**：**制作 Skill 需要用好模型（事半功倍）；调用 Skill 执行时可以尝试将模型降级**（降到日常工作环境与成本可接受的程度）

## 7.4 测试

**⭐ 关键判断：要不要搭自动化测试**
| 情况 | 结论 |
|------|------|
| **项目结果明确、主要工作靠外部 AI 工具完成** | ⚠️ **没必要搭自动化测试** —— 可以用 skill 出测试用例，**但不建议直接做自动化测试**（**成本太高、复用率低**）|
| **新建/二开 AI 项目（网站/应用系统/小程序/APP），有固定开发语言和框架** | ⭐ **有必要** —— **做一套测试框架就能应对一类项目的测试问题** |

**⭐ 两条线**：
- **第一条线（项目开始时走一次）**：把项目资料、测试用例、测试代码、CI 配置准备好存进项目里，**以后开发直接复用**
- **第二条线（每次改代码自动走）**：`git add → commit → push` → **服务器（CI）自动跑同一套测试**，保存日志和每条用例结果；**只有测试失败且你授权了，AI 才帮忙分析原因**；**最后合并还是返工，全由人决定**

**⭐ 测试依据（至少要有一样，否则 Skill 必须停下来）**：
**需求说明 / 需求确认单 / 功能清单** —— **三样都没有，就没有可靠测试依据**
⚠️ **其他资料缺了也不能让 AI 猜**（用户角色、验收规则、性能要求、外部系统行为没依据 → **先标记为「需要人工确认」**）

**⭐ 两条行业规定**：
1. **项目原来用什么测试框架就继续用什么**（Jest 就 Jest，Vitest 就 Vitest），**不建议中途换**
2. **测试失败要用 AI 分析时，必须你授权，且只给脱敏后日志**（删掉密码、密钥、客户数据）

**⭐ 编号规范**：每个功能产生固定编号（如 `FEAT-LOGIN`），每条用例也产生编号（如 `TC-LOGIN-001`）—— **定下来就不变**，以后文档/代码/结果都能对上号

**⭐ 分工**：
> **AI 负责生成测试和辅助分析，测试框架负责执行，确定性脚本负责收集证据和生成报告，Git 和 CI/CD 负责触发与留痕，人工负责业务判断和最终放行。**

## 7.5 ⭐⭐ 部署、验收与交付（防扯皮）

### 部署前必确认（⚠️ 合同签订前就要问）
> ⭐ **是否包含国产化/信创改造** —— **这可不是仅仅几个字，随随便便换一个中间件或者数据库就能把开发任务翻一倍，而且 AI 还不一定帮得到你！**

### ⭐ 两个原则（一句话记住）
> **部署方案写的是「别人照着做也能完成的步骤」；**
> **迁移方案写的是「出了问题也能退回去的方案」。**
> ⚠️ **如果某一步依赖客户提供的信息，就标记为「待确认」，不能让 AI 用假设补齐。**

**部署包/方案必备**：
- **数据迁移**：迁移前备份、迁移范围、执行顺序、数据量核对、关键表校验、**失败后的恢复方式**、迁移脚本能否重复执行
- **验证和回滚**：服务健康检查、登录和核心业务流程、接口联调、日志位置、**备份恢复验证**，以及**什么情况下停止发布、怎样回退到迁移前的版本**

**⭐ 部署流程**：
```
① 准备一套「尽量接近客户目标环境」的测试环境
② 从空环境开始执行方案（让 AI 协助安装部署）
③ 用脱敏或模拟数据走一遍迁移流程
④ 执行前确认：操作系统、运行时、网络、账号权限、依赖服务；保存当前版本、配置清单、数据库备份
⑤ 执行前列出：将要执行的步骤、需要的权限、可能影响的文件或数据
⑥ 验证：核心功能和接口能否正常使用？迁移前后数据量和关键数据是否一致？
⑦ 测试环境验证通过后，**再根据实际执行记录更新部署和迁移方案**（补版本差异、缺少的前置条件、失败处理、人工确认点）
⚠️ **方案没有经过一次完整演练，就只能算草稿，不能算交付文档**
```

### ⭐ 验收防扯皮三条

**① 交付前自检**：
先由自己按**合同、需求确认单、功能清单、测试报告**做一次交付前检查 —— **确认交付内容没有超出范围，也没有漏掉合同里明确写出的部署、数据迁移、培训和文档**

**② 交付包至少包括**（提前和客户沟通）：
**部署日志、验证结果、交付清单**

**③ ⭐ 验收时最常见的问题：客户看到成品后产生新想法**
> **这很正常，因为真实页面比文字需求更容易激发讨论。**
> ⚠️ **这时候不要急着全部答应，也不要直接拒绝 —— 先判断它属于「小修正」还是「新需求」。**
> **如果涉及新功能模块、新接口、新表结构、新权限规则，或需要重新设计流程 → 记录下来，放到下一轮迭代。**
> **这样做不是不配合客户，而是保护第一版按时完成 —— 第一版先验收，新增需求再排期，项目才不会越做越散。**

**④ ⭐ 另一个常见坑：延期和变更没有提前沟通**
> 真实项目中，**第三方接口、飞书权限、地图 Key、客户资料、部署环境、浏览器兼容都可能影响进度** —— **如果等到交付当天才告诉客户做不完，客户一定会觉得你不靠谱。**
> ✅ **更稳的做法：在开发过程中就保持阶段性同步**（原型确认一次、静态页面确认一次、表单和数据同步确认一次、智能助手确认一次）

**⭐ 交付清单的作用**：
> **因为客户不知道从哪里看，也不知道哪些内容属于本次范围，验收就很容易变成一边看一边提新需求。**
> ✅ 明确告诉客户：**当前版本已完成 X/Y/Z；A/B/C 暂时不在第一版范围内，后续可作为下一轮迭代。**

**⭐ 交接还要做的事**：
- **带客户走一遍核心流程，或录一段简短操作视频**（重点是让实际使用的人能完成最常见动作）
- ⚠️ **约定试运行和问题反馈时间**，提前写清：**交付范围内的故障由谁处理、小问题怎么反馈、新增功能怎么记录并进入下一轮评估**

# §8 组织与变现

## 8.1 ⭐ AI 原生组织（为什么 AI 提效但利润不涨）

**核心问题**：**为啥 AI 让个人效率涨了 10 倍，但公司利润没涨？**

**⭐ 底层原因**：
> **很多公司的组织架构、考核体系、流程设计，还是为「前 AI 时代的人类」设计的 —— 生产工具已经变了，但生产关系还在原地。**

**⭐ 两类效率（关键区分）**：
| | A 类效率 | B 类效率 |
|---|---------|---------|
| **是什么** | **用更少时间做同样的事**（AI 写代码/做图/写文案）| **用同样时间做更有价值的事**（发现新需求、创造新品类、建立新商业模式）|
| **终点** | ⚠️ **同质化竞争** —— 所有人用同样的 AI 工具，产出同样的中等质量内容，争夺同样的注意力 | ✅ 需要**判断力、创造力、风险承担能力** |

**⭐ 黑洞（组织滞后性）**：
> **KPI 按产出数量考核 → AI 让数量膨胀，质量稀释**
> **薪酬体系没调整 → 员工用 AI 多产出了 3 倍，工资涨 10%**
> ⭐ **当 AI 只改变了「怎么做」，没改变「做什么」和「谁来做」时，它带来的不是利润，是内卷加速度。**

**⭐ 怎么办**：**不是买更多 AI 工具，是重构组织，让 AI 的局部效率能穿透到全局。**

**⭐ AI 融入的两个层次**：
| 层次 | 解决什么 |
|------|---------|
| **AI 融入流程** | **效率** |
| **AI 进入决策** | **质量** |

**⭐ 企业 AI 成熟度三阶段**：
| 阶段 | 特征 |
|------|------|
| **①** | **AI 停留在个人工具**（写邮件、做总结、生成代码）—— **个人变快了，协作仍然是摩擦和转述** |
| **②** | **AI 进入组织运行** —— **任务被拆成可以判断、执行和验收的环节**；会议、客户反馈和规则进入**共享上下文**；agent 可以行动，**权限和最终责任仍有对应具体的负责人** |
| **③** （原生）| **以 AI 为起点重新思考全部的工作** |

**⭐ AI 原生组织的两个关键前提**：**① 人才密度（顶尖人才密度）② 透明度**（⚠️ **你不透明就没有分享，透明变成非常重要的文化指标**）

**⭐ 激励机制怎么改**：
- **旧机制已崩塌**：KPI 按产出数量考核 → 改问「**这些代码解决了什么问题？这些图带来多少转化？这个流程优化省了多少钱？**」→ **按结果价值定价**
- ⭐ **Palantir 的「碎石路到柏油路」是绝佳模型**：
  > **传统激励只奖励「碎石路」（这次项目交付得好），不奖励「柏油路」（把经验沉淀成可复用的组织能力）** → **结果就是每个人都在重复造轮子，组织能力不增长**
- **具体设计**：晋升评价中**认知贡献度**占重要权重（你培养了多少人？你的方法论被多少人复用？）；**设立「导师分成」**；⚠️ **反向惩罚：关键经验只在自己脑子里、不沉淀不分享的，即使个人业绩好，晋升也受限**

**⭐ 人才制度怎么改**：
- **从「学历+经验」到「判断力+学习力+协作力」**
- ⭐ **价值嗅觉**：**能不能判断什么值得做、什么不值得做？** —— **AI 可以做任何事，但做什么需要人来判断**
- **人才培养的核心不再是教技能**（AI 可以随时教），而是：① 建立**组织第二大脑**（把最强个体的思考过程、判断逻辑、经典案例沉淀下来）② **刻意练习判断力** ③ 培养 **「AI 协作素养」**（知道什么该交给 AI、什么必须自己判断、怎么给 AI 设护栏和验收标准）
- ⚠️ **必须正面回答：被 AI 替代的人怎么办？**（能力升级：从「执行者」升级为「判断者」）
- **管理者的核心工作是「匹配」** —— 把最合适的能力单元匹配到最需要的任务上，**而不是「管」人**

**⭐ 一句话**：
> **激励机制和人才制度是组织的「操作系统」。如果操作系统还是旧的，再强的 AI 工具也跑不出新价值。**

## 8.2 ⭐ 落地后怎么变成复购

> **商单变现只是表面 —— 真正积累下来的是一套可复用的交付方法。**

**⭐ 复购的因果链**：
```
需求挖清楚 → 不返工
报价算清楚 → 不亏本
AI 按规则开发 → 质量稳定
测试和部署证据 → 验收不扯皮
→ ⭐ 客户愿意继续付费的原因，不是某一次代码写得多好，
   而是「能够把事情持续稳定地做下去」
```

**⭐ 沉淀清单（每个项目结束都做一次简短复盘）**：
- **客户一开始遇到了什么问题**
- **第一版完成了什么**
- **实际使用后有哪些反馈**
- **哪些需求暂时放到了下一轮**
- ⭐ **同时把这次用过的「需求访谈问题、原型确认方式、报价范围、验收清单、踩坑记录」整理下来**
- **下次遇到相似项目时，在这些材料的基础上继续完善，减少重复摸索**

**⭐ 核心逻辑**：
> **让每一个项目都能反过来验证和完善自己的方法和过程资产，逐步从「靠个人经验接项目」走到「靠一套稳定流程就能标准化交付项目」。**

**⭐ 从内部复用走向产品化的三阶段**：
| 阶段 | 内容 |
|------|------|
| **① 内部复用** | 历史文章参与下一次写作，模板与脚本服务下一批物料 |
| **② 服务内部用户** | 把长期积累的知识与服务经验，通过一个产品入口直接提供帮助 |
| **③ 产品化输出** | 制作标准化工具，直接赋能外部用户或行业，变成产品解决方案<br>⚠️ **这个阶段应独立明确：服务谁、解决哪类问题、使用什么知识、谁负责维护** |

# §9 ⭐ 可复用清单（拿走就用）

## 9.1 需求深挖五问（核心需求都过一遍）

```
① 挖动机：连续问 3-5 层「为什么」，直到能一句话说清「这功能为什么非存在不可」
② 挖场景：角色 / 触发时机 / 要完成的任务 / 使用频率（4 要素）
③ 挖边界：正向问验收标准 + 反向问排除项 → 产出验收标准 + 边界清单
④ 挖异常：空数据 / 数据超量10倍 / 依赖中断 / 操作出错能撤回吗 / 安全合规（涉密等级+国产化+脱敏+留存）
⑤ 挖约束：规矩、合规、其他限制
```

## 9.2 需求收口公式（一句话定需求）

> **这条需求，就是让【某角色】在【某场景】下办成【某个目标】，做到【什么边界】，出事了【怎么兜】，同时受【哪些规矩】管着。**

## 9.3 访谈提纲框架

```
一、KPI 三问
   ① 老板今年最在意的 1-3 个指标？（说不出 → 问「老板最近反复提什么？」「什么事让他睡不着？」）
   ② 现状多少 → 目标多少？
   ③ 差距主要由什么造成？（人手/流程/出错）

二、真实流程
   ① 这件事现在是怎么做的？谁来做？用什么工具？花多少时间？
   ② 输入是什么？输出给谁？
   ③ 卡在哪一步？（⚠️ 说得平静的是现状，音量变大/反复强调的才是痛点）

三、边界与验收
   ① 做成什么样算成功？（可量化）
   ② 哪些明确不做？

四、异常
   复用 9.1 的「异常五连」

五、现场
   要求走一次真实流程，看实际怎么跑（⭐ 不只是听）
```

## 9.4 四维评分权重（记牢）

```
痛点 Pain       0.35   ←  最重要
ROI 杠杆        0.25
数据 Data       0.20
可行性 Feasibility 0.20
⭐ 硬规则：Feasibility ≥ 4 才能保证两周出原型
```

## 9.5 诊断报告模板（5-8 页）

```
① 背景摘要（半页）
   · 行业和业务模式：一句话定位
   · 关键 KPI：现状 → 目标
   · 痛点强度：用数字或案例

② 场景排名表（核心）
   · 场景名称 / 一句话商业逻辑 / 可量化成功指标 / 两周原型交付计划

③ 推荐快速验证场景
   · 我们建议先做这个，两周就能看到效果

④ 风险与数据缺口
   · 坦诚说明不确定性

⭐ 结尾必须有「下一步建议」
```

## 9.6 报价单必备六项

```
① 本次交付什么
② 客户需要提供什么
③ 预计周期
④ 确认和验收方式
⑤ 试运行支持多久
⑥ 哪些内容不包含
```

## 9.7 避免被白嫖三原则

```
① 免费只做诊断，不做交付
② 把工作拆成阶段（诊断/方案/MVP/部署各有各的价）
③ 先收启动款，再打开深度权限
```

## 9.8 交付清单模板

```
□ 部署日志
□ 验证结果
□ 交付清单（本次范围 / 不在范围内的 / 下一轮可迭代的）
□ 使用说明（换一个同事也能照着用）
□ 试运行与反馈机制（谁处理故障 / 小问题怎么反馈 / 新增功能怎么记录）
```

## 9.9 判断「AI 该不该做」五标准（满足 3 条以上才做）

```
① 高频重复
② 规则相对明确（不是纯靠灵感创造力）
③ 有数据基础（核心数据已在线化）
④ 容错率较高（出错有人复核，不是零容错生死决策）
⑤ 可闭环验证
```

| **1** | **客户说的不一定是想要的 —— X 是解决方案，问题才是需求。** | 需求访谈 ⭐ |
| **2** | **没行动的需求都是伪需求**（没花过钱、没派过人、没花过时间）| 判断真假需求 |
| **3** | **「他要三遍的，一定是真正要的需求」** | 抓痛点 |
| **4** | **先观察，再访谈** —— 群聊里反复出现的问题、反复@的人、反复等待的环节，就是最真实的痛点地图 | 找场景 ⭐ |
| **5** | **AI 落地大多数项目失败，不是技术不行，而是需求从一开始就理解错了** | 给自己定规矩 |
| **6** | **数据和权限缺口是 AI 落地的真正杀手，不是模型能力** | 诊断阶段必备 |
| **7** | **不要按「陪聊了多久」报价，要按「帮客户减少了多少成本、拿到了什么结果」报价** | 报价 ⭐ |
| **8** | **还没收费就把方案做完了 —— 这是 FDE 最容易犯的商业错误** | 防白嫖 ⭐ |
| **9** | **交付结果，不交付过程**（怎么做的完全不用给他看）| 交付策略 ⭐ |
| **10** | **客户愿意继续付费，不是因为某次代码写得多好，而是因为「能持续稳定地把事情做下去」** | 复购 ⭐ |
| **11** | **规则写得越像「检查清单」，AI 越像资深工程师；越像「口号」，越像自由发挥的实习生** | 写 Skill / Rules ⭐ |
| **12** | **如果规则连你自己都无法判断 AI 是否遵守，那 AI 也一定无法遵守** | 验收自己的 Skill |
| **13** | **当 AI 只改变了「怎么做」，没改变「做什么」和「谁来做」时，它带来的不是利润，是内卷加速度** | 跟老板讲价值 ⭐ |
| **14** | **交付越轻，通常越快、越便宜** —— 当前阶段推荐选「轻的、快的」，即使少赚很多 | 选型 ⭐ |
| **15** | **你在现场一起做事，对方才可能把你当伙伴；只做调研，对方会把你当指手画脚的老师** | 驻场 ⭐ |
