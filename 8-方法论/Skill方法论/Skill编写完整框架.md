# Skill编写完整框架

## 1. 任务定义

先回答五个问题：

1. 谁在什么场景下使用？
2. 用户会用什么表达触发？
3. 输入是什么，缺少什么就不能继续？
4. 最终输出是什么，保存到哪里？
5. 什么结果算完成，什么情况必须停止？

## 2. 边界设计

- **包含**：Skill负责完成的核心任务。
- **不包含**：相邻但不应该顺手扩展的任务。
- **依赖**：需要的工具、脚本、账号、文件和权限。
- **风险动作**：删除、覆盖、发送、发布、支付、授权等。
- **人工确认点**：涉及责任、外发和不可逆操作时暂停确认。

## 3. 信息架构

推荐采用渐进式披露：

```text
Skill目录/
├── SKILL.md          # 触发条件、核心流程、关键规则
├── references/       # 详细规范、业务规则、字段说明
├── templates/        # 输出模板和表单
├── examples/         # 正例、反例和边界样例
├── scripts/          # 可重复执行的脚本
└── tests/            # 测试样例和验收记录
```

主文件回答“何时使用、怎样执行、何时停止”；细节和大体量资料放在支持目录中按需加载。

## 4. 工作流编写

每个步骤尽量具备：

- 输入条件
- 执行动作
- 使用工具
- 中间产物
- 校验方法
- 失败处理
- 下一步条件

## 5. 示例设计

至少准备：

- 一个标准正例
- 一个输入不完整的例子
- 一个边界或异常例子
- 一个不应触发该Skill的反例
- 一个真实业务验收样例

## 6. 测试与调试

测试分为两层：

### 静态检查

- 元数据、目录和引用路径是否正确。
- 描述是否足以区分相似Skill。
- 是否存在矛盾、模糊动词和缺失步骤。
- 是否包含停止条件、权限和异常处理。

### 运行检查

- 应触发时能否触发。
- 不应触发时是否保持沉默。
- 缺少输入时是否提出正确问题。
- 工具失败时是否安全退出或给出替代路径。
- 输出是否符合格式、业务规则和验收标准。

## 7. 发布与维护

- 记录Owner、版本、更新时间和适用范围。
- 保存测试输入、实际输出和失败修复记录。
- 外部规则、接口或平台变化后重新运行关键样例。
- 重大修改先验证再覆盖正式版本。

## 最终交付物

一个完整Skill至少应包括：

- 任务契约
- 可运行的Skill目录
- 输入与输出说明
- 异常和停止规则
- 正反例
- 测试与验收记录
- 负责人和版本信息
